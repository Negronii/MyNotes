# 简单提示失败后，怎样选择并评估提示技巧？

[模型这次能看见什么，提示词该怎样写成可验收的契约？](model-input-and-prompt-contract.md)给出了一个清楚的 zero-shot (零样本) 基线：四部分提示词加 11 字段的构建报告契约。本章回答基线在一批案例上出错之后该怎么办：先判断失败属于哪一类，再按症状选最小的改动，最后在固定的开发集上比较、冻结候选、用独立案例验收。各种技巧名称叠在一起，不会让提示变好。

案例仍是 CI 诊断助手的构建 42：`c1` 读到 `unit-tests` 步骤中测试 `reject_empty_name` 预期 HTTP `400`、实际 `200`，`exit_status=1`。本章另造的网络中断、缺日志等情形都是合成夹具，它们的调用编号写作 `f2`–`f5`（f 表示夹具），只在本章内有效，不是 `c1` 那次运行的后续调用。

## 先分清三类失败

基线出错，原因大致有三类，只有第一类主要靠改提示词解决：

1. **提示有歧义。** 模型看到了 `c1` 的观察，却写成“输入校验器必然有缺陷”。这是推断越界，改提示词、收紧根因的推断边界是对的。
2. **输入缺证据。** 观察根本没进入本次调用的上下文。这时追加“请认真思考”也补不回日志，应该补材料或调用工具。比如开发者在新一轮追问“按当前手册要不要重跑”，应用就得从运行记录取回 `c1`，再检索当前手册；怎样组装这一轮输入见[每次调用的上下文预算该怎样分配，哪些状态必须留在应用里？](context-budget-and-state-layers.md)。
3. **需要下游校验。** 输出形状合格，内容却和来源不符。任何提示词都不能保证这种错误不再出现，该由应用逐字段核验并拒收。

对第 2 个例子，合适的回答是：`c1` 是断言失败；按 `CI-RETRY-v3`，断言失败不能自动重跑，应先调查；调查后能否人工重跑，手册没有规定。即使 API 会自动续接对话，也要核实这一轮的实际输入里确实有运行记录和手册。

## 按症状决定先改哪里

排除了证据交接问题后，检查一批有代表性的错误，按症状选改动。下表是本章的骨架，后面各节逐行展开：

| 可见症状 | 先改哪里 | 用什么检查改动有效 |
|---|---|---|
| 观察值被混淆，或缺证时猜根因 | 先写清字段和未知值；仍反复出错，再加对照示例 | 同一组固定样本上的字段正确率、缺证停答、无依据主张 |
| 输出形状合格，事实与来源不符 | 应用端逐字段比对来源，不符就拒收 | 应用错误放行率 |
| 多步推理中途出错 | 让模型交回可核对的中间字段 | 中间字段与来源逐项比较 |
| 可验证的离散答案随采样波动 | 规范化答案后试自一致性投票，保留独立验证 | 正确数、验证拒绝数、额外生成成本 |
| 中间结果可检查，下游确有独立步骤 | 只拆出能门控的阶段，失败就停 | 各阶段通过率与端到端通过率，新增时延和费用 |
| 已确认是指令歧义，多轮手改仍失败 | 生成少量不同候选，在开发集上筛选 | 开发集增益与回归，最后用留出集确认 |
| 本轮缺必需事实，或依赖外部最新状态 | 由应用经授权取证 | 实际传入的结果能否支持主张 |

## 少样本示例：只在边界不清时才加

Few-shot examples (少样本示例) 是在上下文里放几组输入和正确输出，让模型看清类别边界和输出模式。只有代表性样本显示零样本指令反复混淆不同事件时，才值得加。

构建 42 里容易混的是“断言失败”和“日志取不到”。一组对照示例可以这样设计，两例都遵守同一份 11 字段契约，下表只列有区别的字段：

| 字段 | 示例一：`c1` 取到日志 | 示例二：`f5` 读取请求被拒 |
|---|---|---|
| `evidence_status` | `available` | `unavailable` |
| `source_call_id` | `c1` | `f5` |
| `step` / `failed_test` | `unit-tests` / `reject_empty_name` | `null` / `null` |
| `expected` / `actual` / `exit_status` | `HTTP 400` / `HTTP 200` / `1` | 全为 `null` |
| `root_cause_status` / `root_cause` | `unknown` / `null` | `unknown` / `null` |
| `explanation` | “预期 HTTP 400，实测 HTTP 200；根因未确认。” | “日志取回失败，无法判断测试是否启动或失败原因。” |

示例二要教给模型的边界是：没有日志不等于测试没有运行。真正的“测试启动前网络中断”必须有独立观察明确记录，不能从 `f5` 这样的取证失败推出来。

示例应来自可复现的错误类型，而不是照抄某个测试用例。重复的示例会拉长输入，还可能让模型记住无关措辞。如果模型只在与示例原句相同的输入上变好，说明改动没有解决边界问题。用来挑示例的开发集要固定下来，另外留出一批没参与编写和挑选的案例。

## 思维链有帮助的证据有边界

Chain-of-thought (思维链，CoT) 提示让模型在最终答案前先写出中间推理。结论先说：它是否有帮助取决于模型和任务，不能默认加一句“逐步思考”就会变好，要对目标模型实测。

> [!info]- 文献：CoT 的证据从哪里来，又到哪里为止
> - **早期结果。** Wei et al. 在若干大模型的算术、常识和符号推理任务上，报告带推理示例的 CoT 提示带来改进。Kojima et al. 的 zero-shot CoT 不给示例，只加一句提示语，在其测试基准上也观察到收益。
> - **推理模型。** OpenAI 针对 reasoning models 的当前指南建议从直接、简短的提示开始，先试零样本；对这类模型显式要求“逐步思考”可能没有收益，有时反而降低表现。这只针对 OpenAI 的推理模型。
> - **示例的作用。** Cheng et al.（Findings of EMNLP 2025）在 Qwen2.5 系列的数学任务上发现，相对零样本 CoT，CoT 示例没有提升推理表现，主要作用是规范输出形式。
> - **反例。** Liu et al. 测试六类任务，在隐式统计学习、人脸识别和含例外规则的分类三类上观察到 CoT 降低表现，其余三类结果有好有坏。
>
> 每项结论只覆盖论文测试的模型、提示和任务。

## 用可核对的中间字段代替冗长推理

如果失败是模型在多步处理中途出错，比如没能保持 `c1` 中各个值的对应关系，不必让它写冗长的推理，让它交回能核对的中间字段就够了：`step`、`failed_test`、`expected`、`actual`、`root_cause_status`、`root_cause`。这些正是报告契约里的字段，应用可以逐项与工具结果比较。

难点在多个相互依赖的转换时，同样把检查点拆成程序能验证的结构化结果。这样能看出错误发生在哪一步。它不能证明模型写出的解释忠实反映了内部计算，所以判定依据始终是可核对的字段，而不是解释文字。

## 自一致性：票数最多也不是证据

Self-consistency (自一致性) 对同一问题采样多条推理路径，再汇总各路径的最终答案。答案是离散值时，常见做法是先把答案规范化，再取出现次数最多的那个（相对多数，不要求过半）。无法解析的答案不计票；票数并列时交给独立验证器，或者把结论记为未知。

构建 42 的报告不适合演示投票，下面换一道能验证答案的小算术题：

> [!example] 规范化后投票（手工演算，不是模型采样结果）
> 求 $17 \times 23$。两条可核算的路径：$17 \times (20+3)=340+51=391$，$(10+7) \times 23=230+161=391$。
>
> 假设五次采样的最终字符串是 `391`、` 391 `、`391`、`392`、`392`。去掉首尾空白、按十进制整数解析后，得到 `391, 391, 391, 392, 392`，计数 `391: 3`、`392: 2`，投票选 `391`。最后仍由独立的乘法验证确认结果。

票数只是候选之间的聚合。所有样本犯同一个错误、或都漏掉同一条证据时，投票会一致地错。采样数从 1 增加到 $m$，生成计算量大约增加到 $m$ 倍，收益还取决于采样多样性、答案规范化和验证器。

回到构建 42：多采样几次，也不能让模型知道日志里没有记录的代码根因。只有固定案例显示单次输出不稳定、而答案又能由工具或代码校验时，才值得比较不同采样数。

## 提示词链：只有阶段能独立检查时才串联

Prompt chaining (提示词链) 把一个任务拆成几次依次进行的模型调用，阶段之间由程序检查、分支或停止。

`c1` 已经是结构化字段，不需要模型再抽取一遍，应用直接把核验过的字段映射到报告即可。只有日志来源是必须由模型归纳的自由文本、并且第二步确实承担独立的回答职责时，才考虑拆成两段。设想另一个返回自由文本的日志接口：

1. **抽取。** 这次调用 `f4` 由应用的请求元数据绑定到 `build_id=42`，日志正文是：“unit-tests：reject_empty_name 断言失败；expected HTTP 400，observed HTTP 200；进程 exit 1；日志没有说明代码根因。”第一次模型调用按报告契约抽取字段：`build_id` 取自应用元数据，`source_call_id=f4`，未观察到的根因字段设为 `unknown` / `null`。
2. **门控。** 应用把 `build_id` 与可信的调用元数据比较，把步骤名、测试名、预期、实际和退出状态与 `f4` 原文比较，并按缺证规则检查根因状态。元数据缺失、字段不一致或无法核验时，拒收并显示“日志字段无法核实，尚不能生成解释”，不发起第二次调用。
3. **回答。** 全部通过后，第二次调用把已核验的数据写成答案：“构建 42 的 `unit-tests` 中，`reject_empty_name` 预期 HTTP 400、实际 HTTP 200，进程退出状态为 1；日志没有确认代码根因。”应用再按同样的字段核对其中的事实主张。

如果只需要这句固定格式的话，用模板生成比第二次模型调用更简单。串联只有在第二阶段的自然语言任务确有价值时才值得评估。

多一次调用不会白白增加可靠性。记 $S_1$ 为第一步抽取通过门控，$S_2$ 为在 $S_1$ 通过后第二步回答也通过核验，则端到端通过率为

$$
P(S_1 \cap S_2) = P(S_1)\,P(S_2 \mid S_1).
$$

这是条件概率的乘法公式，不要求两步独立。取一组玩具数值 $P(S_1)=0.95$、$P(S_2 \mid S_1)=0.95$，端到端通过率为 $0.95 \times 0.95 = 0.9025$，即 90.25%，比任一步都低。真实系统里，共享的输入错误、门控和重试都会改变这个数，所以要实测各阶段通过数 / 到达该阶段的任务数，以及端到端通过数 / 符合条件的任务数。

比固定链条更开放的是 ReAct：模型在推理和工具动作之间交替，拿到观察后再决定下一步。本例开头模型先请求 `read_build_log`、应用执行后交回 `c1` 再继续，就是这种反馈回路。它不会创建工具、授予权限或自己执行动作；什么时候该让模型决定下一步，见[什么时候该让模型决定下一步？](../actions/when-the-model-decides.md)。

## 自动生成提示候选，也要过同一套验收

前面的改动都靠人写。也可以让模型生成提示候选。Automatic Prompt Engineer (APE，自动提示工程) 把指令当作待搜索的候选：先根据输入–输出示范生成一批指令，再把每个候选用到任务输入上，按执行得分排序。原论文在 24 个 Instruction Induction 任务和筛选出的 21 项 BIG-Bench Instruction Induction 任务上评估。下面按错误信号生成候选，是工程上的变体，不是论文原样的方法。

设固定的失败信号是：`c1` 上 `expected` 与 `actual` 被对调。比较时固定模型版本、JSON schema、可用工具、`c1` 观察、解码配置和报告契约，只改提示：

- **基线 P0：**“解释构建 42 为什么失败，并指出代码根因。”
- **候选 P1：**“只使用应用提供的 `build_id`、`evidence_status`、`source_call_id` 和本轮记录；`expected`、`actual` 须按来源原样填写。没有独立根因证据时必须输出 `root_cause_status=unknown`、`root_cause=null`。日志不可用时不得推断测试是否启动。使用中文解释。”

下面两份输出是手工编写的评分夹具，不是模型的真实调用结果。两份在其余六个字段上相同，只列出差异：

| 字段 | P0 的错误输出 | P1 的输出 |
|---|---|---|
| `expected` | `HTTP 200` | `HTTP 400` |
| `actual` | `HTTP 400` | `HTTP 200` |
| `root_cause_status` | `confirmed` | `unknown` |
| `root_cause` | “空名称校验器失效” | `null` |
| `explanation` | “日志显示空名称校验器失效。” | “预期 HTTP 400，实测 HTTP 200；日志未确认代码根因。” |

评分前先定下整份报告的硬条件：11 个字段符合契约；可观察字段与绑定来源一致；根因状态与证据相符；每条事实性解释都有来源支持。本例的开发指标只看 `expected` 和 `actual` 两个字段：P0 两个都错，得 0/2；P1 得 2/2。字段得分不是整份报告的通过率；P0 还违反了根因硬条件。

再看两条留出夹具。它们没有参与示例编写或候选选择，表中只列决定能否通过的字段：

| 留出观察 | P1 必须给出的字段 | 预期判定 |
|---|---|---|
| `f2`：日志记录工作节点在测试启动前断连 | `evidence_status=available`，`source_call_id=f2`，`step=worker-setup`；测试断言与退出字段为 `null`；根因 `unknown` / `null`。解释可以说“启动前断连”，不能写成代码根因。 | 通过：忠实报告直接观察，没有越界。 |
| `f3`：日志取回超时，测试是否启动未知 | `evidence_status=unavailable`，`source_call_id=f3`；未观察字段为 `null`；根因 `unknown` / `null`。 | 通过：超时只说明没取到日志，和 `f5` 的拒绝一样，都推不出测试未启动。 |

这组夹具只说明示例与规则彼此吻合，不能证明 P1 的提示效果。`f2`、`f3` 只列了期望字段，没有模型运行输出。所以 P1 仍是待评估候选：真实评估要预先定好开发指标和留出硬条件、冻结留出集，实际结果满足全部门槛才验收，也不根据留出集上的错误反复改提示。P0 只是实验对照，它违反了事实与根因硬条件，不能当作上线后的回退版本。候选没通过时不发布，生产继续使用最近已验收的提示和应用校验；还没有已验收版本时，继续拒收不合格输出并交人工复核。

实际比较时，让候选生成器提出少量不同改动即可，不让它自己宣称候选有效。已经参与示例编写或候选选择的案例属于开发集；反复改写并报告同一批失败的分数，会把提示过拟合到已知例子。

## 实例：多模块提示的预算化搜索（DSPy、GEPA）

当应用由多个模型调用组成时，可以把提示搜索交给优化器。DSPy 把语言模型调用组织成可组合的程序模块，用任务指标编译、比较候选；不同优化器可以搜索指令、示例或模型权重。GEPA 是一种反思式提示优化器：反思模型查看任务运行轨迹和逐模块反馈，提出新的指令候选，并保留在不同任务上表现互补的候选。在原论文的对照里，GEPA 只改提示文本，任务模型权重冻结。

GEPA 与 GRPO 改的对象不同：GEPA 改模块指令，GRPO 用奖励更新模型权重（机制见[可验证奖励怎样训练推理能力？](../evaluation-and-release/reward-based-reasoning-training.md)）。在相同的基座模型、任务分布和结果指标下比较，才能判断哪种方法在给定预算内留出表现更好。GEPA 论文表 1 用 Qwen3-8B 做了六项任务的对照：

- GEPA 在五项上高于 GRPO；聚合分 54.85 对 48.91，约高 6 个百分点；单项最大差距在 HotpotQA，62.33 对 43.33，差 19 个百分点。
- AIME-2025 上 GEPA 32%、GRPO 38%，GRPO 更好。
- 表 1 的 GRPO 用 LoRA，每项任务 24,000 次 rollout；GEPA 部分设置的 rollout 数最多少约 35 倍。

35 倍只比较了 rollout 次数。完整费用还要算反思模型调用、候选复评、输入输出 token、训练时长、工具执行和评分器调用。DSPy 当前的优化器指南提醒，某些 GEPA 或 MIPROv2 编译一次就可能产生数百美元的模型调用费用。

这类方法适用的前提是：已经有可组合的模型程序；有可复核的任务指标，以可观察结果判定成败，文字反馈指出失败字段和证据；能从运行轨迹辨认提示错误；基础模型本身具备完成任务的能力。评分器应接受所有满足同一结果契约的有效路径，轨迹主要用于诊断；授权、动作或外部状态要求可以列为独立硬门禁。评估器不可靠时，优化会放大评审偏差。

> [!example] 演算：为构建 42 的四个提示模块预算一次搜索
> 假设诊断系统有四个可单独编辑的指令模块：抽取结构化字段、选择证据行、判断根因与下一步、组织最终说明。每个模块只有当前版本和一个候选版本，另有十道适用于该契约的独立任务。
>
> 先看两种搜索方式的规模。穷举四个模块的全部组合有 $2^4=16$ 种配置；十题都用于开发时要跑 $16 \times 10 = 160$ 次完整任务。只测四个单模块改动加当前配置，要跑 $5 \times 10 = 50$ 次，但看不到模块之间的交互。
>
> 再按“四道训练题、两道验证题、四道最终留出题”切分。训练题的轨迹用于生成和解释候选；验证题只按预先定好的规则评分、选出候选 B，不提供反思反馈；验证题参与了选版，所以也是开发证据。最终题直到候选冻结后才运行。按这种切分，全组合搜索加最终配对验收需 $16 \times 6 + 8 = 104$ 次；只测五种单模块配置加最终验收需 $5 \times 6 + 8 = 38$ 次。下表在后者基础上加测一个交互：
>
> | 步骤 | 运行安排 | 完整任务运行数 |
> |---|---|---:|
> | 开发基线 | 最近已验收的版本 A 在六道开发题（训练 + 验证）上各跑一次 | 6 |
> | 单模块筛选 | 四个候选各在同一组六道开发题上跑一次 | 24 |
> | 检查一个交互 | 对事先认为会互相影响的两个模块测试双改组合，与已测的两个单模块候选比较 | 6 |
> | 最终配对验收 | 冻结候选 B 后，A、B 各在四道最终题上跑一次 | 8 |
> | 合计 | | **44** |
>
> 预算按完整程序的运行次数计，反思模型、token 和工具调用另行核算。两道验证题和四道最终题只够演示流程，区分不了小的差异；真实验收的样本量见下一节链接的章节。

> [!info] 实例：DSPy GEPA 优化器的预算入口（官方指南 2026-11-25 复核）
> 配置时在 `auto`、`max_full_evals` 和 `max_metric_calls` 三种预算入口中选一个，三者互斥；实现会把前两种换算成指标调用预算。一次完整程序运行可能包含多次模型或工具调用，所以还要另外计量并限制反思调用、输入输出 token、实际费用和总耗时。验证集用于选候选，最终测试集单独保留。接口会演进，运行时核对安装版本。

## 评估整套变更，而不是提示的外观

比较提示文本时，固定模型版本、工具可用性、检索证据、输出 schema 和解码配置，只改提示。如果评估的是工具接入、采样或编排，就固定原始任务和其他不受测的条件，允许受测策略及其产生的中间状态变化，评估完整流程。每个案例是一项任务，记录提示版本、输入材料、模型和解码配置。

留出集至少要区分四种情形：断言 `400 → 200`；有明确“测试启动前中断”观察；日志取回失败；新一轮追问中需要按当前 `CI-RETRY-v3` 回答。每个追问案例都要单独提供该案例上一轮的调用记录和本轮检索到的手册；`c1` 和本章的手册只示范这类输入的形态，不进最终留出集。追问的评分要检查：断言失败不得自动重跑、应先调查；手册没说调查后能否人工重跑。基线和候选在同一组独立任务上、按预先固定的条件配对比较；开发证据与独立验收的划分和配对统计见[候选 B 比 A 好，是真改善还是抽样波动？](../evaluation-and-release/holdout-acceptance-and-paired-statistics.md)。

输出质量和应用防线要分开报告，每个指标先写清分子和分母：

| 指标 | 分子 / 分母 |
|---|---|
| 字段对调率（按报告） | `expected` 与 `actual` 被对调的形状合格报告数 / 形状合格且两个来源值都可核对的报告数 |
| 应用错误放行率 | 与来源不一致却被应用接受的报告数 / 提交给校验器的不一致报告数 |
| 事实支持率 | 有来源支持的原子事实主张数 / 受评报告中的原子事实主张总数 |
| 字段准确率 | 正确字段数 / 有证据且契约要求的字段总数 |
| 无证根因率 | 缺少根因证据仍断言根因的可评分案例数 / 缺少根因证据的可评分案例数 |

几条容易算错的地方：

- 一次对调是两个字段错误，按报告计却只是一份不一致输出。所以字段对调率代替不了应用错误放行率，两者衡量的是不同的东西。
- 原子主张指只承载一项可独立核验的事实；只有列出的来源确实蕴含它才算支持。
- 格式错误和缺失字段单独计为契约失败。第一个指标只统计形状合格的报告，不能借此把无效输出从整体结果里隐去。
- 分母为零时，指标标为未定义并写出样本数，不能记作零错误。

系统开销与流程指标按各自的阶段计数：端到端通过数 / 符合条件的任务数、工具调用数 / 任务数、验证器拒绝数 / 送验候选数、每任务总费用，有任务通过时再算每通过任务费用；端到端时延按符合条件的任务报告分位数。多阶段方法另报各阶段通过数 / 到达该阶段的任务数；自一致性报告投票后正确任务数 / 固定任务数，以及实际采样数和额外生成成本。指标分母的一般原则见[上线后，怎样从一条错误建议找回可修复的证据？](../evaluation-and-release/production-traces-and-metric-denominators.md)。语气更顺、解释“看起来更完整”都不是通过条件。

## 提示改不动的错误交给谁

本章给出了基线失败后的一套做法：先分清是提示歧义、缺证据还是需要下游校验；按症状选最小改动；所有候选在固定开发集上比较，冻结后用独立案例验收。产出是一个已验收的提示版本，或者一个明确的结论：这个错误不是提示能修的。

后一种情况要换别的改动对象。缺证据的问题回到上下文组装和检索，见[怎样从授权文档里找到回答依据？](rag-indexing-and-retrieval.md)；该改工具、脚手架还是权重，以及怎样把一次失败变成可验收的新版本，见[让助手以后不再误诊，该改提示词、工具、脚手架还是权重？](../evaluation-and-release/choosing-what-to-change.md)。
