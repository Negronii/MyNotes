# 一次 AI 回答经过了哪几步？

用户发出一句问题，几秒后收到一段有依据的回答。中间并不是“模型直接答了”：应用先决定模型看见什么，模型只产出文本或一段请求，真正读数据、执行动作、保存结果的都是应用。本章沿一次完整运行走过这五步，只讲到工程层；每一步结束时，点出它引出的问题和负责回答的主线。

## 案例：CI 诊断助手解释 build 42

一位开发者在用接入构建系统的 AI 助手。构建系统会对每次代码改动跑自动检查，build `42` 失败了。开发者问：`Why did build 42 fail?`

失败详情存在日志服务里。助手不能直接访问日志服务，但应用为它提供了一个 tool (工具) `read_build_log`，可以按构建编号读取失败记录。开发者需要的是一段以日志为依据的解释，而不是猜测。这是一个虚构的案例，主线二、三、五还会沿用这个助手。

这次运行调用了两次模型：第一次，模型发现缺证据，生成一条读日志的请求；应用执行后，第二次调用才生成回答。如果问题本身已经带有足够证据，第一次调用就可以直接回答。

~~~mermaid
flowchart TD
    Input["1 应用组装输入<br/>指令 + 问题<br/>+ 工具定义"]
    Model["2 模型生成输出"]
    Choice{"输出是什么？"}
    Tool["3 应用检查 c1<br/>核对权限后执行<br/>读 build 42 日志"]
    Next["4 结果回到<br/>下一次输入<br/>追加调用与结果"]
    Answer["5 应用保存终态<br/>并返回"]
    Input --> Model --> Choice
    Choice -->|工具请求| Tool
    Tool -->|日志或错误结果| Next
    Next -->|下一次模型调用| Model
    Choice -->|最终回答| Answer
~~~

下文把协调模型和工具的应用代码称为 harness。它记录调用者身份，为每次模型调用挑选输入，执行工具，并判断运行何时结束。

## 第一步：应用组装这次调用的输入

第一次模型调用有三项输入：

| 输入 | 本例内容 |
| --- | --- |
| 应用指令 | 根据现有证据解释构建失败。 |
| 用户消息 | `Why did build 42 fail?` |
| 工具定义 | `read_build_log` 接受整数 `build_id`，返回该构建日志里的失败记录。 |

模型只看见应用这次交给它的内容。它不会自己连上日志服务或应用数据库，也不会自动记得用户以前说过的所有话。工具定义只告诉模型“有这样一个操作可用”，日志内容要等应用真正取回后才会进入输入。调用者身份不交给模型，由应用自己保留，留给后面的权限检查。

服务端会按所用模型的 chat template (对话模板) 把这三项排成一段文本，再交给模型。较长的对话里，应用还要决定保留哪些旧消息和旧证据。

**这一步引出的问题：模型每次该看见什么，才能凭证据回答？** 输入怎样写成可验收的契约、上下文预算怎样分、证据从哪里检索，见主线二的第一章[模型这次能看见什么](../context/model-input-and-prompt-contract.md)。

## 第二步：模型生成文本或一段工具请求

模型读入整段输入，然后一次生成一个 token (词元)。它生成的既可以是给用户看的回答，也可以是按模型约定格式写出的工具请求。本例中模型缺日志，于是生成了一段请求。

推理服务按模型的工具调用协议解析这些词元，把完整的工具名和参数作为结构化条目交给应用。用简化记法写，应用收到的是：

`tool_call(c1, read_build_log, {build_id: 42})`

`c1` 是这次调用的 ID，之后的工具结果也要带上它。同时有多个待处理的调用时，模型靠这个 ID 才知道哪条结果对应哪个请求。服务还要确认生成是否完整：输出被截断时，残缺的参数不能当作可执行的调用。

**这一步引出的问题：模型怎样把输入算成下一个词元，代价又落在哪？** 从分词、attention 到采样，再到 KV 缓存怎样决定一台服务能接多少请求，见主线一的第一章[模型怎样把提示词算成下一个词元](../model/next-token-computation.md)。

## 第三步：应用检查请求，再执行工具

`c1` 只是一个请求，执行与否由应用决定。应用依次检查：

- `read_build_log` 是否对本次运行可用；
- `build_id` 是否为整数；
- 调用者是否有权读取 build `42`。

前两项保证请求能被正确解释，第三项是 authorization (授权)。授权依据的是应用保存的调用者身份，而不是模型生成的任何内容。全部通过后，应用才读取日志，拿到模型此前缺的证据：

| `c1` 结果字段 | build `42` 的值 |
| --- | --- |
| 失败步骤 | `unit-tests` |
| 失败测试 | `reject_empty_name` |
| 失败断言 | 空名称请求应返回 HTTP `400`，实际返回 `200` |
| 进程退出状态 | `exit_status=1` |

如果授权失败，应用就为 `c1` 返回一条失败结果，让模型在下一次调用里说明拿不到证据。读日志不改变任何外部状态；如果工具会改变状态，例如重跑构建或创建工单，放行前要过的关就多得多。

**这一步引出的问题：模型提出的动作，应用凭什么放行？** 工具请求的形状、调用者权限和内容真实性是三件不同的事；写操作还需要对精确草稿的审批。见主线三的[模型“调用工具”时实际发生了什么](../actions/tool-calls-are-requests.md)和[应用要过哪几道关才能放行](../actions/authorization-gates-for-actions.md)。

## 第四步：结果回到下一次模型输入

应用发起第二次模型调用。输入在第一次的基础上追加两条：模型发出的 `tool_call(c1, …)`，以及与它配对的 `tool_result(c1, …)`。前者记录模型请求了什么，后者给出工具实际观察到的内容。如果还允许模型继续调用工具，应用要按所用接口再次提供工具定义，或保留对它的有效引用。

第二次调用用的仍是同一个模型、同一组训练好的参数，只是输入更长了，多了 `unit-tests`、`reject_empty_name`、预期 `400`、实际 `200` 这些细节。新证据改变的是模型这次能依据的信息，不是模型本身，所以不需要重新训练。

证据仍有缺口时，模型可以再请求一次工具。应用在配置的调用次数、耗时和成本上限内重复“检查、执行、回填”；到达上限时，按已有证据返回未完成或失败的结果，而不是无限循环。

**这一步引出的问题：动作执行到一半出事，怎样既不丢结果也不重复？** 这个循环跨越多次模型调用和工具执行。如果工具已经执行、第二次调用还没发出时进程崩溃或用户断线，应用需要知道哪些事已经发生、凭什么继续。见主线四的第一章[一次 AI 运行断线或崩溃后，凭什么恢复](../runs/run-identity-and-authoritative-state.md)。

## 第五步：应用保存终态并返回

有了日志，模型可以只陈述日志能证实的内容：

> [!example] 根据日志返回的说明
> build 42 在 `unit-tests` 步骤失败。测试 `reject_empty_name` 预期空名称请求返回 HTTP `400`，实际收到 `200`，测试进程以状态 `1` 退出。要确认根本原因，请对照预期行为检查请求校验逻辑。

第一次模型调用以工具请求结束，所以应用还要继续；第二次调用以回答结束。应用先保存回答，把这次运行（编号 `run-r42-6`）标记为完成，再把结果返回给开发者。即使是边生成边流式返回，也要记录这次生成最终是正常完成还是中途失败。

这段回答区分了“观察到哪条断言失败”和“缺陷的根本原因”：日志只证明前者。这个区分本身就可以变成验收标准：修改提示词或模型后，回答仍应如实引用日志里的值，不臆造原因；日志缺失或无权访问时，也要给出正确的说明。

**这一步引出的问题：“回答得好”怎样检查，改动怎样证明值得上线？** 见主线五的第一章[“回答得好”怎样写成可检查的任务契约](../evaluation-and-release/task-contracts-and-quality-dimensions.md)。

## 五条主线分别从哪一步接手？

| 运行中的一步 | 它引出的问题 | 主线 |
| --- | --- | --- |
| 2 模型生成输出 | 模型怎样算出下一个词元，代价落在哪？ | [主线一：模型](../model/next-token-computation.md) |
| 1 组装输入 | 模型每次该看见什么，才能凭证据回答？ | [主线二：上下文](../context/model-input-and-prompt-contract.md) |
| 3 检查并执行 | 模型提出的动作，应用凭什么放行？ | [主线三：动作](../actions/when-the-model-decides.md) |
| 4 结果回填与循环 | 执行到一半出事，怎样既不丢结果也不重复？ | [主线四：运行](../runs/run-identity-and-authoritative-state.md) |
| 5 保存终态并返回 | 改动怎样证明值得保留并上线？ | [主线五：评估与发布](../evaluation-and-release/task-contracts-and-quality-dimensions.md) |

主线一从第二步拿到的那段完整输入开始，打开模型内部的计算。开发者的追问则把主线二推向前：“预期的 `400` 符合接口契约 `HTTP-CONTRACT-v1` 吗？这次能自动重跑吗？”回答它需要应用从授权文档里检索契约和重试手册 `CI-RETRY-v3`，并确认用的是现行版本，而不是已撤回的 `CI-RETRY-v2`。
