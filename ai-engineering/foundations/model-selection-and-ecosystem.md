# 如何为具体任务选择模型，并让部署约束进入决策？

先把任务成功条件写成可测的契约，再淘汰不满足硬约束的候选模型。若只把当前模型换掉来比较模型本身的影响，应固定提示词、工具和应用路径；若要选择最终可部署方案，可让候选在开发集使用各自支持的提示词、结构化调用与配置，冻结后再按相同任务契约、输入集合、评估协议和预算比较。模型名称、排行榜和供应商档位只能帮助初筛，不能替代目标任务上的验证。本篇交付候选集、验收门槛和基线假设；[如何测量 AI 服务的时延与成本](../systems/ai-latency-and-cost-optimization.md)接着量化工作负载，[如何选择 AI 部署方式并安全回滚](../systems/ai-deployment-patterns.md)再据此选运行位置和发布路径。

~~~mermaid

flowchart TD
  A["任务与数据契约<br/>输入、授权、验收条件"] --> B["候选硬门槛<br/>端点能力、数据规则、责任团队"]
  B -->|满足| C["开发与候选比较<br/>按共同契约评测，选定并冻结方案"]
  C -->|候选达标| D["负载与部署核验<br/>真实端点、峰值、成本、故障恢复"]
  D -->|运行条件通过| E["独立验收<br/>使用未参与调优与选择的数据"]
  E -->|验收通过| F["交给发布流程"]
~~~

图中沿箭头前进意味着前一项已经通过；尚未验证的条件也不能算通过。出现问题时，返回哪一步取决于改了什么：

| 未通过的位置 | 下一步 |
|---|---|
| 候选硬门槛 | 淘汰当前候选；替换模型后重新检查硬门槛。 |
| 开发与候选比较 | 调整当前候选的提示词或配置后重新比较；若更换候选，先重查硬门槛。 |
| 负载或部署核验 | 修正运行方案，重查受影响的能力、数据边界和质量，再复测负载。 |
| 独立验收 | 失败样本可成为开发证据；修订并重新冻结后，另用未参与这轮决策的数据验收。 |

## 从月报助手的任务契约开始

> [!example] 虚构案例：为月报生成可核对的摘要
> 一家虚构的报表助手接收已经过应用授权的区域销售汇总，回答“哪些区域环比变化率的绝对值超过 8%，总额变化多少？”。模型输入包含行号、区域名和两期原始金额；租户隔离和行级权限由应用完成，这是案例约定，不代表有真实系统已实现或通过审计。
>
> 以下数据是教学用的合成数值，单位为万元。表中前两期是模型输入；“环比变化”和“合计”是这道教学例的参考答案，不发送给模型，也不是实际评测的留出集。候选比较应在配置冻结后使用共同的比较集；最终组合确定后，还要另备未参与提示词、配置或候选选择的独立验收集。行号必须随原始输入保留：
>
> | 行号 | 区域 | 2026-09 原始输入 | 2026-10 原始输入 | 环比变化验收参考 |
> |---|---|---:|---:|---:|
> | r1 | 华东 | 120 | 132 | +12（+10%） |
> | r2 | 华北 | 80 | 72 | -8（-10%） |
> | r3 | 华南 | 50 | 55 | +5（+10%） |
> | 合计 | — | — | — | 250→259；+9（+3.6%） |
>
> 验收参考答案：华东 +12 万元（+10%，r1）、华北 -8 万元（-10%，r2）、华南 +5 万元（+10%，r3）；三行总额 250→259 万元，净增 +9 万元（+3.6%，依据 r1–r3）。只有变化率绝对值**严格大于** 8% 的区域才入选；区域、变化额、变化率、总额和支持它们的行号都是必填项。总变化率以两期总额计算，不得臆测促销、季节等原因。

> 边界行为也要成为契约，而不是留给模型猜测：100→108 万元恰好 +8%，不满足“严格大于 8%”，不列为命中；上期为零时变化率不可计算，可报告已知变化额但放入需复核项，不按阈值分类，两期金额齐全时仍计入各期总额；上期为负数时本例不使用百分比自动分类，标记需业务复核；两期金额齐全时仍按原符号计入各期总额。任一期金额缺失时变化额/变化率不可完整计算，报告该行缺值并把总额标为不完整、交回数据责任方补齐。以上只是独立的契约边界例，不加入三行主例的合计。

把此类要求写成验收契约，而不是“回答得好”：

| 维度 | 月报助手的检查方式 |
|---|---|
| 任务正确性 | 按变化率绝对值严格大于 8% 筛选；变化额、变化率、总额和行号与授权输入一致，引用确实支持相应说法 |
| 边界行为 | 上期为零时比率不可算；负基数交业务复核；缺金额则标记总额不完整；单位混用先由应用换算或拒绝；冲突和无数据按约定报告或升级 |
| 指令与格式 | 不猜测原因；输出能通过目标接口的结构校验 |
| 时延 | 约束明确是首 token、完整报告还是两者；按真实峰值与区域测量 |
| 成本 | 计算模型、重试、数据准备、托管、评测和人工复核后的每份成功报告成本 |
| 数据与运维 | 输入是否可发给托管服务，谁负责密钥、扩缩容、更新、监控和故障响应 |

**适用边界：** 对这类报表，算术可以留给模型并被严格评测，也可以由应用确定性地预先计算、让模型只负责解释。两种实现都要评估端到端结果；如果授权和计算交给模型猜测，就没有落实任务契约。

## 如何建立可比较的候选集？

先应用硬门槛：必要模态和输入形状是否支持；目标 API、模型版本或本地引擎是否能实现需要的结构化输出与工具调用；数据处理方式是否符合合同和内部规则；是否有承担故障与运维责任的运行团队。只要候选不满足一项硬门槛，就不应靠低价格或高公开基准分补偿。

能力要核到准确的模型和接口。例如，OpenAI Responses API 用 `text.format` 的 JSON Schema 约束面向用户的结构化响应；连接应用工具则用 function calling（函数调用）。严格结构输出只支持 JSON Schema 子集，而且通过结构校验仍不证明金额、事实或引用正确，内容仍须单独验收。

再在相同条件下做代表性评测：

1. 固定应用侧授权、可见业务证据、工具所能执行的业务能力、校验规则与错误分支；消息格式、schema 或工具调用的 API 表达可按各候选能力适配并随候选冻结。若只比较“替换模型”的影响，则提示词和整个调用路径也保持不变。
2. 用开发集迭代提示词和配置；冻结候选后，可用同一比较集进行候选比较。任何用于反复调优或挑选赢家的数据都不再是独立留出集；最终组合确定后，再用从未参与这些决策的独立验收集检查它。
3. 覆盖普通请求、零值/缺失值、负基数和格式边界。越权输入由应用授权入口拦截或过滤，确认未授权行不会送入模型；不能把访问控制寄托在模型拒答上。
4. 分开记录任务通过、事实/数值正确、引用支持、格式有效、拒答或升级、时延和实际费用。
5. 报告样本分母和不确定性；小样本上的差异不能自动外推到生产总体。

> [!example] 教学用候选表：分开内容、格式与费用门槛
> 假设两种匿名候选都用同一组 200 个合成开发样例、同一提示词与应用路径做预筛；下表是教学设定，不是实际运行结果。这组样例不是独立留出集，也不用于最终验收。内容判定检查严格的 `|变化率| > 8%`、变化额、变化率、总额、行号、不臆测，以及前述零基数、负基数和缺值的边界契约；结构有效率单独统计。一个报告只有内容与结构都通过，才算成功。
>
> | 候选 | 内容判定通过 | 结构有效 | 成功交集 | 常规筛选的后端完整报告时延 p95 | 模型 API 直接费/成功报告 |
> |---|---:|---:|---:|---:|---:|
> | 甲 | 198/200（99%） | 200/200（100%） | 198/200（99%） | 假设 1.7 秒 | 假设 $0.007 |
> | 乙 | 199/200（99.5%） | 198/200（99%） | 197–198/200（交集未知） | 假设 1.2 秒 | 假设 $0.004 |
>
> 本例要求内容通过率至少 99%、结构有效率在本批样本中 100%（即零格式错误），并假设常规筛选负载 p95≤2 秒；只有内容与结构交集才计成功。甲交集为 198/200，样本内容/结构门槛和假设 p95 都符合预筛条件。乙的交集无法只由两项比例精确还原，但结构门槛无论如何都未通过，须先修复后重评。200/200 只表示这批样例零格式错误，不代表真实失败率为零；若真实错误率为 1% 且观察相互独立，200 次都未见错误的概率仍约为 `0.99^200 = 13.4%`。p95 和直接费用是分开设定的筛选假设，不是从这 200 个样例计算出来，也不是峰值测量。模型 API 直接费按所有尝试（含失败和重试）费用除以成功报告数；$0.01/成功报告是**直接 API 费用上限**，甲的假设值低于它。它不含人员、工程、评估、人工复核等总拥有成本，不能据此称完整成功成本已达标。所有数字均为教学假设，不是实测或模型排名。

公共基准可以帮助缩短候选列表，但基准的任务、样本、模型访问方式、评分协议和目标部署若不同，就不能直接推出本应用的质量。模型版本、上下文窗口、模态、工具和结构输出支持都会变化。上线前要核验确切模型标识、版本、接口能力、限制、区域和当前价格。

## 托管、自托管与混合部署如何进入候选筛选？

| 方式 | 可能合适的条件 | 仍需核对的成本与责任 |
|---|---|---|
| 托管 API | 希望快速试验托管推理，且合同、地域、功能和数据要求均允许。 | 精确服务条款、保留设置、速率限制、可用性、模型生命周期和按量费用由具体提供方与配置决定。 |
| 开放权重、自托管 | 模型版本或运行位置的控制是明确需求，并且团队能承担容量与运维。 | 权重可取得不自动等于 OSI 定义的开源 AI，也不代表任意用途或商业分发均获许可；还要逐个核对模型版本的许可和使用政策。团队负责硬件、服务栈、安全更新、扩缩容和 on-call（值班响应）。 |
| 混合部署 | 不同任务确实需要不同模型或不同数据边界。 | routing（请求路由）、策略一致性、回退、监控和重复基础设施会增加复杂度；必须测量净收益。 |

“开放权重”只说明参数可获得，不足以说明训练数据、训练/推理代码、架构及相关组件都可按开放源代码自由研究、修改和再分发。以具体模型的准确版本为准，检查其许可和可接受使用政策是否覆盖预期商业用途、衍生/分发、署名和规模限制，并分别核验推理代码、tokenizer 与部署依赖的条件。OSI 的定义要求标为 Open Source weights（开源权重）的交付也附有用于生成参数的代码和数据资料；仅提供可下载的权重不能据此称为开源；Meta Llama 4 则展示了某个具体社区许可的额外使用与分发条款，不能把那份许可推广到其他模型。

“前沿”“均衡”“快速”等档位只是各家产品目录中的粗略称呼，不是共享标准。高档位不证明它在此报表任务上更好，低时延标签也不代表端到端服务更快。实际选型应看同任务评测与当前文档，而非复制过期榜单。

托管服务的数据边界也要落到实际 API 端点与功能：一个组织层面的留存设置不一定覆盖每种应用状态、文件或第三方工具。OpenAI 的数据控制表就按端点和功能列出留存例外；其他供应商须查其对应条款与租户配置。

模态也要细分验证。multimodal（多模态）不说明一个模型支持哪种图片、音频或视频输入，也不说明它能否读准所需内容。若报表输入以后改成扫描件或图表，应用要用目标格式、分辨率和 API 逐项评测，不能把表格文本测试结果直接外推。

## 何时把请求路由到不同候选？

只有当不同请求类别表现出稳定、可测的需求差异，才值得增加模型路由。它可以把简单、低风险的摘要送给成本较低的候选，把经评测确实受益的请求交给其他候选；但需要把分类错误、路由时延、回退比例、维护、权限和策略一致性一起算入。

月报助手若按输入长度或报表类型路由，先给每个切片定义通过条件，再比较路由前后的成功率、每份成功报告成本和尾部时延。分类置信不足时，应回退到已验收候选或人工路径；高影响工具动作仍需应用逐项授权，模型路由本身不授予权限。不能假定“抽取”必然简单、某一行业请求必然困难。详细的请求阶段测量见[如何测量 AI 服务的时延与成本](../systems/ai-latency-and-cost-optimization.md)。

## 从候选评测交给预算与部署

候选甲只满足本表所列的教学预筛条件，可进入下一步核验；本例尚未指定真实供应商、API 端点、数据处理配置或承担运行/故障责任的团队，不能据此认定它已满足试点或部署硬门槛。独立留出集也尚未评测。服务目标暂设为每月 10,000 份通过内容与格式验收的成功报告（不是 10,000 次请求）。实际请求/重试数量、峰值并发、峰值时延、端点数据策略和完整总成本留给后续测量与部署核验。
