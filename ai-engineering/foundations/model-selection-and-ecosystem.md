# 如何为具体任务选择模型，并让部署约束进入决策？

选模型的顺序是：先把任务的成功条件写成可测的契约，再淘汰不满足硬约束的候选。比较时要先想清楚比的是什么。如果只想知道“换一个模型”本身带来多大影响，就固定提示词、工具和应用调用路径，只替换模型；如果要选出最终可部署的方案，则允许每个候选在开发集上使用各自适合的提示词、结构化调用方式和配置，调好后冻结，再用相同的任务契约、输入集合、评估协议和预算比较。模型名称、排行榜和供应商的档位划分只能帮助初筛，不能代替在目标任务上的验证。

本篇的产出是候选集、验收门槛和基线假设；[如何测量 AI 服务的时延与成本](../systems/ai-latency-and-cost-optimization.md)接着量化工作负载，[如何选择 AI 部署方式并安全回滚](../systems/ai-deployment-patterns.md)再据此选运行位置和发布路径。

~~~mermaid

flowchart TD
  A["任务与数据契约<br/>输入、授权、验收条件"] --> B["候选硬门槛<br/>端点能力、数据规则、责任团队"]
  B -->|满足| C["开发与候选比较<br/>按共同契约评测，选定并冻结方案"]
  C -->|候选达标| D["负载与部署核验<br/>真实端点、峰值、成本、故障恢复"]
  D -->|运行条件通过| E["独立验收<br/>使用未参与调优与选择的数据"]
  E -->|验收通过| F["交给发布流程"]
~~~

图中沿箭头前进，表示前一项已经通过；尚未验证的条件不能算作通过。某一步没通过时，该退回哪一步取决于要改动什么：

| 未通过的位置 | 下一步 |
|---|---|
| 候选硬门槛 | 淘汰当前候选；替换模型后重新检查硬门槛。 |
| 开发与候选比较 | 调整当前候选的提示词或配置后重新比较；若更换候选，先重查硬门槛。 |
| 负载或部署核验 | 修正运行方案，重查受影响的能力、数据边界和质量，再复测负载。 |
| 独立验收 | 失败样本可成为开发证据；修订并重新冻结后，另用未参与这轮决策的数据验收。 |

## 从月报助手的任务契约开始

> [!example] 虚构案例：为月报生成可核对的摘要
> 某公司（虚构）要做一个月报助手：它接收应用已完成授权检查的区域销售汇总，回答“哪些区域的环比变化率绝对值超过 8%，总额变化了多少？”。模型输入包含行号、区域名和两期原始金额；租户隔离和行级权限由应用负责。这只是案例设定，不代表某个真实系统已经实现或通过了审计。
>
> 以下是教学用的合成数据，单位为万元。两期金额是模型输入；“环比变化”列和“合计”行是本例的参考答案，不发给模型，也不是实际评测用的留出集。真实评测中，候选比较在配置冻结后使用共同的比较集；最终组合确定后，还要另备一份没有参与过提示词、配置或候选选择的独立验收集。行号必须随原始输入一起保留，供答案引用：
>
> | 行号 | 区域 | 2026-09 原始输入 | 2026-10 原始输入 | 环比变化验收参考 |
> |---|---|---:|---:|---:|
> | r1 | 华东 | 120 | 132 | +12（+10%） |
> | r2 | 华北 | 80 | 72 | -8（-10%） |
> | r3 | 华南 | 50 | 55 | +5（+10%） |
> | 合计 | — | — | — | 250→259；+9（+3.6%） |
>
> 验收参考答案：华东 +12 万元（+10%，r1）、华北 -8 万元（-10%，r2）、华南 +5 万元（+10%，r3）；三行总额 250→259 万元，净增 +9 万元（+3.6%，依据 r1–r3）。只有变化率绝对值**严格大于** 8% 的区域才入选；区域、变化额、变化率、总额和支持它们的行号都是必填项。总变化率以两期总额计算，不得臆测促销、季节等原因。

> 边界情况也要写进契约，不能留给模型猜：
>
> - 100→108 万元恰好 +8%，不满足“严格大于 8%”，不算命中。
> - 上期为零时变化率无法计算：可以报告变化额，但把该行放入“需复核”，不参与阈值筛选。
> - 上期为负数时，本例不用百分比自动分类，而是标记为需业务复核。
> - 以上两种情况只要两期金额齐全，仍按原符号计入各期总额。
> - 任一期金额缺失时，变化额和变化率都算不完整：报告该行缺值，把总额标为“不完整”，交回数据负责方补齐。
>
> 这些边界例只用来说明契约，不计入上面三行主例的合计。

把这些要求写成逐项可检查的验收契约，而不是笼统的“回答得好”：

| 维度 | 月报助手的检查方式 |
|---|---|
| 任务正确性 | 按变化率绝对值严格大于 8% 筛选；变化额、变化率、总额和行号与授权输入一致，引用确实支持相应说法 |
| 边界行为 | 上期为零时比率不可算；负基数交业务复核；缺金额则标记总额不完整；单位混用先由应用换算或拒绝；冲突和无数据按约定报告或升级 |
| 指令与格式 | 不猜测原因；输出能通过目标接口的结构校验 |
| 时延 | 约束明确是首 token、完整报告还是两者；按真实峰值与区域测量 |
| 成本 | 计算模型、重试、数据准备、托管、评测和人工复核后的每份成功报告成本 |
| 数据与运维 | 输入是否可发给托管服务，谁负责密钥、扩缩容、更新、监控和故障响应 |

**适用边界：** 对这类报表，算术既可以交给模型、再严格评测，也可以由应用用确定性代码预先算好，模型只负责组织和解释。两种做法都要评估端到端结果；如果让模型去猜授权范围或自行估算数字而不加校验，任务契约就没有落实。

## 如何建立可比较的候选集？

第一步是硬门槛：是否支持所需的模态和输入形式；目标 API、模型版本或本地推理引擎能否提供所需的结构化输出与工具调用；数据处理方式是否符合合同和内部规则；有没有团队负责运行、运维和故障处理。候选只要有一项不满足，就应淘汰，不能用低价或高公开基准分来弥补。

能力要核对到具体的模型和接口。例如，OpenAI Responses API 用 `text.format` 中的 JSON Schema 约束返回给用户的结构化响应；让模型调用应用的工具，则用 function calling (函数调用)。严格的 structured outputs (结构化输出) 只支持 JSON Schema 的一个子集；而且输出通过了结构校验，也不能证明金额、事实或引用是正确的，内容仍须单独验收。

通过硬门槛的候选，再在相同条件下用有代表性的样本评测：

1. 固定应用侧的授权、模型能看到的业务数据、工具能执行的业务操作、校验规则和错误处理分支。消息格式、schema 和工具调用的 API 写法可以按各候选的能力适配，适配后随候选一起冻结。如果只比较“替换模型”的影响，则提示词和整个调用路径也保持不变。
2. 用开发集迭代提示词和配置；候选冻结后，用同一个比较集比较它们。凡是被用来反复调优或挑选胜者的数据，都不再算独立留出集；最终组合确定后，要用从未参与这些决策的独立验收集再检查一次。
3. 样本要覆盖普通请求、零值或缺失值、负基数和格式边界。越权输入应由应用的授权入口拦截或过滤，评测时确认未授权的行不会送进模型；不能指望靠模型拒答来实现访问控制。
4. 分别记录：任务是否通过、事实和数值是否正确、引用是否支持结论、格式是否有效、是否拒答或升级、时延和实际费用。
5. 报告样本量（分母）和不确定性；小样本上的差异不能直接外推到生产环境。

> [!example] 教学用候选表：分开内容、格式与费用门槛
> 假设两个匿名候选甲、乙用同一组 200 个合成开发样例、同一提示词和应用路径做预筛；下表是教学设定，不是实际运行结果。这组样例不是独立留出集，也不用于最终验收。“内容判定”检查是否按 `|变化率| > 8%` 严格筛选、变化额/变化率/总额/行号是否正确、是否没有臆测原因，以及前面零基数、负基数和缺值的边界约定；“结构有效”单独统计。一份报告只有内容和结构都通过，才算成功。
>
> | 候选 | 内容判定通过 | 结构有效 | 成功交集 | 常规筛选的后端完整报告时延 p95 | 模型 API 直接费/成功报告 |
> |---|---:|---:|---:|---:|---:|
> | 甲 | 198/200（99%） | 200/200（100%） | 198/200（99%） | 假设 1.7 秒 | 假设 $0.007 |
> | 乙 | 199/200（99.5%） | 198/200（99%） | 197–198/200（交集未知） | 假设 1.2 秒 | 假设 $0.004 |
>
> 本例的预筛门槛是：内容通过率至少 99%；结构有效率在这批样本中为 100%（零格式错误）；常规负载下 p95 不超过 2 秒（假设值）；模型 API 直接费用不超过 $0.01/成功报告。
>
> - **甲**：内容和结构都通过的交集是 198/200，内容、结构、p95 和费用都满足预筛条件。
> - **乙**：只知道两项各自的通过数，交集无法精确还原（最少 199+198−200=197，最多 198），但结构有效率已经不是 100%，无论交集是多少都未过门槛，须修复后重评。
>
> 读这张表时要注意三点。第一，200/200 只说明这批样例没有出现格式错误，不代表真实错误率为零：假如真实错误率是 1% 且各次相互独立，200 次全部无错的概率仍有 `0.99^200 ≈ 13.4%`。第二，p95 和费用是单独设定的假设，不是从这 200 个样例算出来的，也不是峰值实测。第三，“模型 API 直接费”是全部尝试（含失败和重试）的费用除以成功报告数；$0.01 只是**直接 API 费用的上限**，不含人员、工程、评测、人工复核等总拥有成本，所以甲低于它并不说明完整成本已经达标。表中所有数字都是教学假设，不是实测结果或模型排名。

公共基准可以帮助缩短候选列表，但只要基准的任务、样本、模型访问方式、评分协议或部署条件与本应用不同，就不能直接推出本应用的质量。模型版本、上下文窗口、模态、工具和结构输出支持都会变化。上线前要核验确切模型标识、版本、接口能力、限制、区域和当前价格。

## 托管、自托管与混合部署如何进入候选筛选？

| 方式 | 可能合适的条件 | 仍需核对的成本与责任 |
|---|---|---|
| 托管 API | 希望快速试验托管推理，且合同、地域、功能和数据要求均允许。 | 精确服务条款、保留设置、速率限制、可用性、模型生命周期和按量费用由具体提供方与配置决定。 |
| 开放权重、自托管 | 模型版本或运行位置的控制是明确需求，并且团队能承担容量与运维。 | 权重可取得不自动等于 OSI 定义的开源 AI，也不代表任意用途或商业分发均获许可；还要逐个核对模型版本的许可和使用政策。团队负责硬件、服务栈、安全更新、扩缩容和 on-call（值班响应）。 |
| 混合部署 | 不同任务确实需要不同模型或不同数据边界。 | routing（请求路由）、策略一致性、回退、监控和重复基础设施会增加复杂度；必须测量净收益。 |

“开放权重”只说明模型参数可以获得，并不说明训练数据、训练和推理代码、架构等组件都能像开源软件那样自由研究、修改和再分发。按 OSI 的 Open Source AI Definition，要称为 Open Source weights (开源权重)，还必须同时提供生成这些参数所用的代码和数据信息；只提供可下载的权重，不能据此称为开源。

实际使用时，要针对具体模型的准确版本，检查其许可和可接受使用政策是否覆盖预期的商业用途、衍生与再分发、署名和规模限制，并分别核验推理代码、tokenizer 和部署依赖各自的许可条件。例如 Meta 的 Llama 4 社区许可就带有额外的使用与分发条款；这只是一份具体许可的例子，不能推广到其他模型。

“前沿”“均衡”“快速”这类档位只是各家产品目录里的粗略叫法，没有统一标准。高档位不能证明模型在这个报表任务上更好，标着“低时延”也不代表端到端服务更快。选型应以同任务评测和当前文档为准，不要照搬过期的榜单。

托管服务的数据边界也要落实到具体的 API 端点和功能：组织层面的一个留存设置，不一定覆盖所有应用状态、文件或第三方工具。例如 OpenAI 的数据控制文档就按端点和功能分别列出了留存例外；其他供应商要查各自的条款和租户配置。

模态支持也要细分验证。标着 multimodal (多模态)，并不说明模型支持哪些图片、音频或视频格式，也不说明它能否准确读出所需内容。如果月报的输入以后改成扫描件或图表，就要按目标格式、分辨率和 API 逐项评测，不能把纯文本表格的测试结果直接套用过去。

## 何时把请求路由到不同候选？

前面的流程默认所有请求用同一个候选。只有当不同类别的请求表现出稳定、可测量的需求差异时，才值得引入模型路由：把简单、低风险的摘要交给成本较低的候选，把经评测确实能从更强模型获益的请求交给其他候选。代价是要把分类错误、路由带来的时延、回退比例、维护负担，以及权限和策略的一致性一并算进去。

如果月报助手按输入长度或报表类型路由，先给每一类（切片）定义通过条件，再比较路由前后的成功率、每份成功报告成本和尾部时延。分类器把握不足时，应回退到已验收的候选或人工处理；高影响的工具操作仍需应用逐项授权，路由本身不授予任何权限。也不要先入为主地认为“抽取”类请求一定简单、某个行业的请求一定困难。详细的请求阶段测量见[如何测量 AI 服务的时延与成本](../systems/ai-latency-and-cost-optimization.md)。

## 从候选评测交给预算与部署

到这里，候选甲只是通过了上面教学表里的预筛条件，可以进入下一步核验。本例还没有指定真实的供应商、API 端点、数据处理配置或负责运行与故障处理的团队，也还没有在独立留出集上评测，因此不能认定它已经满足试点或部署的硬门槛。交给下一步的服务目标暂定为：每月 10,000 份通过内容与格式验收的成功报告（注意不是 10,000 次请求）。实际请求和重试次数、峰值并发、峰值时延、端点的数据策略和完整总成本，留给后续的测量与部署核验。
