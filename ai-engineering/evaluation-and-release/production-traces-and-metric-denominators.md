# 上线后，怎样从一条错误建议找回可修复的证据？

回到 build 73 最初被发现的时候：线上的版本 A（提示词 p12）把它误诊成业务断言失败。服务这边看一切正常：HTTP 200，JSON 结构合法。唯一的信号是用户点了踩，并留了一句纠正。本章回答：一次请求要留下哪些可关联的记录，才能从这一下点踩追到出错的环节；线上指标的分母该怎样选；反馈怎样变成可验收的修复，而不是直接拿去改模型。读者手上有[任务契约](task-contracts-and-quality-dimensions.md)和一条点踩记录。

## HTTP 200 和点踩各证明了什么

用户的纠正是：“构建日志记载服务未就绪，因此集成测试被跳过。”这句话描述的是日志里看得到的状态，还不足以断定根因是进程启动慢、探针目标配错还是别的原因。

手上的两类信号各只证明一部分：

- **HTTP 200 和 schema 合法**：请求得到了响应，输出形状正确。不说明诊断对。
- **点踩**：这位用户不满意。不说明错在日志获取、检索、模型判断，还是评价预期本身。

要找到错的那一环，得把这次任务的服务过程、所用版本和最终结果连起来，同时控制收集的数据量。做法是先记录请求级证据，再把后来的反馈和结果核验挂回同一个任务：

~~~mermaid
flowchart LR
    Request[任务 ID<br/>与用户请求] --> Trace[关联追踪<br/>与运行版本]
    Trace --> Outcome[记录交付、工具状态<br/>与费用]
    Outcome --> Feedback[关联反馈<br/>与结果核验]
~~~

## 一次请求留下哪些可关联的记录

一条 trace (追踪) 把请求的根 span 与子 span 串成一次端到端操作。span (追踪片段) 记录一个阶段的耗时、状态和关联版本，例如身份检查、读取构建日志、检索运行手册、模型生成、结构校验和结果交付。日志可以通过 trace ID 和 span ID 挂到对应 span 上。通用的 trace、metrics、日志怎样配合排障，见[服务信号与故障定位](../../engineering-foundations/reliability/observability-slos-and-incident-response.md)；这里只讲 AI 应用要额外关联的东西。

AI 应用的一次任务往往不止一次调用，所以关联键要分层：

- 一个 `task_id` 可以对应多次 `attempt_id`。重试时沿用任务 ID，产生新的尝试 ID；每条 trace 指向某一次尝试。
- 尝试之下还有应用的模型调用 ID、SDK 内部的重试、`runId` 与 worker 尝试、每次工具调用的 `tool_call_id`。
- 每条记录带上版本：模型部署、提示词、检索索引、工具、来源文档。

这些 ID 各自的含义和谁持有它们，见[运行身份与权威状态](../runs/run-identity-and-authoritative-state.md)。分层的意义在于区分三种“又调用了一次”：客户端重试、运行恢复，以及 Agent 自己反复发起却没有进展的循环。后一种怎样识别，见[多阶段编排](../actions/multi-stage-orchestration.md)。

## 每个阶段记什么，默认不存什么

记录要够定位，又不能把用户数据复制到处都是。下表按阶段列出：

| 阶段 | 可用于定位的记录 | 默认不保存 |
|---|---|---|
| 接收请求 | trace ID、任务类别、地区、时间、受限访问的会话引用、入口状态 | 未脱敏的用户姓名、完整的自由文本问题 |
| 读取构建产物 | 构建编号、制品版本、读取状态、耗时、允许访问的范围 | 完整原始日志、未经筛选的环境变量 |
| 检索运行手册 | 索引版本、候选数、证据引用 ID、耗时、权限结果 | 不必要的文档正文、对用户不可见的权限字段 |
| 模型调用 | 模型部署版本、提示词版本、结束状态、输入输出 token 数、耗时、费用 | 完整 prompt、答案和工具参数 |
| 验证与交付 | schema 结果、证据引用是否存在、拒答或升级、是否成功交付 | 把私密正文复制进通用应用日志 |
| 结果复核 | 任务 ID、业务系统确认的结果或审核标签及其来源版本；未复核记为未知 | 把 HTTP 状态、schema 合法或模型自评当作正确标签 |

最后一行最容易出错。交付成功、结构合法、模型自评高分，都不是“诊断正确”的标签。正确性只能来自业务系统的确认或审阅者对照原始来源的核验。

## build 73 的 trace：把误诊定位到解释层

> [!example] build 73 的 trace（标识均为教学假设）
> - 关联键：`task_id=ci-build-73`，`attempt_id=1`，`trace_id=trace-build-73-1`。
> - 读取构建制品：成功；受控存储中的标识为 `build-73-report@r4`。
> - 检索：成功；`index=runbook-index-v12`，返回 `runbook/service-readiness@v7#startup`。
> - 实际组装给模型的证据：`build-73-report@r4#L20-L22` 与 `runbook/service-readiness@v7#startup`；提示词 p12，模型部署 `log-assistant-2026-10-31`。
> - 模型生成：1.1 秒，主类别 `assertion_failure`，引用第 20 行。
> - schema 校验与交付：均成功。
> - 事后审核：审阅者按同一版本的 build 73 日志核实第 20 行连接被拒、第 21 行重试耗尽、第 22 行服务未就绪并跳过集成测试；根因仍未确认。

沿着 trace 逐段排除：日志读到了；检索取回了相关的运行手册；第 20–22 行确实进了模型的上下文。证据都在，模型却给出了 `assertion_failure`。所以这次失败定位在“证据已提供但解释错误”这一层，而不是读取或检索。如果 trace 显示模型收到的证据缺行、索引过期或权限过滤错了，结论就要改成数据或检索层。

这里有三样东西要分开记录：trace 记下的交付状态和当时实际使用的证据；审阅者给出的正确性标签；根因判断。trace 证明不了分类对错，分类对错来自审阅者对同版本原始日志的核验。

从来源缺事实、到取不到、到没进上下文、到进了上下文仍用错，这条逐层排查链是 RAG、记忆和线上排查共用的，权威说明见[回答的主张核对与失败定位](../context/claim-verification-and-failure-localization.md)。线上排查在这条链之外，还多出两类只在生产中出现的情况：

| 线上现象 | 可检查的证据 | 首要调查方向 |
|---|---|---|
| 日志读取或工具调用失败 | 工具返回码、超时、重试、目标版本 | 连接、凭证、依赖健康、调用契约 |
| 结构有效，用户仍无法行动 | 输出 schema 与用户实际要做的事、升级路径 | 任务契约、界面、缺失的上下文或产品策略 |
| 用户报告内容错误，trace 却缺证据 | 采样策略、脱敏策略、原始记录指针 | 可观测性缺口；不能用缺失的日志假装错误不存在 |

一个事件可能同时有表现与根因：模型给错分类，检索也漏了片段。两者都记下，别让一个标签抹掉调查路径。修复针对经检查的那一层；只凭相关性就去改模型，可能掩盖权限或数据问题。

## 指标分母：先定观察单位

线上要看的不只是任务结果，还有服务信号：端到端时延和首个词元时延 (TTFT)、吞吐、排队、超时和错误、尝试成本、工具调用成功率、权限拒绝、交付、人工升级和用户纠正。这些指标最常见的错误是分母选错。规则是：**先确定每个指标的观察单位，再写分子和分母。**

一个任务可以有多次尝试，一次尝试可以有多次工具调用。三个层级的数量不同，不能混用：

| 指标 | 观察单位与计算 | 口径提醒 |
|---|---|---|
| 任务完成率 | 已确认完成的任务数 ÷ 全部符合条件任务数 | 每个任务只计一次；不能用尝试数作分母 |
| 尝试失败率 | 失败尝试数 ÷ 全部符合条件尝试数 | 重试会增加尝试数，不增加任务数 |
| 工具调用成功率 | 成功工具调用数 ÷ 全部符合条件工具调用数 | 按唯一 `tool_call_id` 去重；不能用任务数或尝试数作分母 |
| 每次尝试成本 | 全部符合条件尝试的推理与工具费用 ÷ 符合条件尝试数 | 分子包括失败、重试和未完成尝试的费用 |
| 每个已完成任务成本 | 全部符合条件尝试的总费用 ÷ 已确认完成任务数 | 分子仍含未完成任务的费用；只报这个会掩盖失败成本 |
| 审核样本正确率 | 审核样本中契约通过的任务数 ÷ 已取得可信标签的审核任务数 | 是被审核子集的结果，不能直接除以全部任务数 |
| 标签覆盖率 | 有可信标签的任务数 ÷ 全部符合条件任务数 | 未核实的记为未知，不默认为通过或失败 |

> [!example] 合成计数：同一批数据，五个分母
> 假设一段时间内有 100 个符合条件任务、101 次尝试（一个任务重试了一次）、60 次工具调用。80 个任务已确认完成。从全部 100 个任务中随机抽 20 个，取得了可信标签，其中 17 个满足契约。60 次工具调用中 57 次成功。101 次尝试的总费用记为 `$C`。
>
> - 任务完成率 = 80/100 = 80%。
> - 工具调用成功率 = 57/60 = 95%。
> - 审核样本正确率 = 17/20 = 85%；标签覆盖率 = 20/100 = 20%。
> - 每次尝试成本 = `$C/101`；每个已完成任务成本 = `$C/80`。未完成尝试的费用仍在两个分子里。
>
> 85% 是 20 个被审核任务的观测比例。如果有人把 17 除以 100，得到 17%，就把未审核的 80 个任务全当成了失败；把 17 除以 80 个已完成任务，又混进了两个不同的样本。

**什么时候能从审核样本外推总体。** 只有抽样过程和实际取得标签的过程都足以支持外推时，才估计总体正确率。抽样权重只能校正已知的抽取概率。如果已完成或成功的任务更容易拿到标签，就要按结果和任务类别检查标签缺失，补充审核或限制结论；权重修复不了系统性缺失。

**哪些数据不能当分母。** 任务完成和交付用全量计数；正确性只在可信标签上算；尝试失败与费用按全部尝试算。诊断 trace 可能经过采样，点踩只是用户自选的子集，都不能直接充当总体正确率的分母。

每个已完成任务成本只是成本口径之一。把重试、人工复核、失败任务的费用都摊进去的完整单位成本，见[每个成功任务的完整成本](model-selection-and-unit-cost.md)。

## 分位数不能相加

时延指标常按阶段拆开看。一个常见错误是把各阶段的 p95（第 95 百分位）相加，当作端到端 p95。这样算出的数可能偏低，也可能偏高，取决于慢请求是不是同一批。

> [!example] 两个阶段，两种结果（合成数据，100 个请求）
> 检索平时 0.2 秒、慢时 1.2 秒；模型平时 1.0 秒、慢时 3.0 秒。p95 取排序后第 95 个值。
>
> **情形一：各有 4 个慢请求，且不是同一批。** 检索 p95 = 0.2 秒，模型 p95 = 1.0 秒，相加得 1.2 秒。端到端：92 个请求 1.2 秒，4 个 2.2 秒（检索慢），4 个 3.2 秒（模型慢）；第 95 个值落在 2.2 秒那组。真实 p95 = 2.2 秒，相加的结果低估了近一倍。
>
> **情形二：各有 6 个慢请求，且不是同一批。** 检索 p95 = 1.2 秒，模型 p95 = 3.0 秒，相加得 4.2 秒。端到端：88 个 1.2 秒，6 个 2.2 秒，6 个 3.2 秒；第 95 个值是 3.2 秒。相加的结果高估了 1 秒。
>
> 只有各阶段时延在请求之间的排序完全一致（每个阶段最慢的都是同一批请求，且慢的程度排序相同）时，相加才恰好成立。

原因是分位数描述的是单个阶段的分布，而端到端时延取决于各阶段时延在同一请求上怎样组合。请求之间的相关性、排队和尾部都会改变结果。所以服务目标按用户可感知的端到端指标来设，再用阶段 span 找出预算被谁消耗。

## 反馈是有偏的自选样本

**两类反馈信号。** 显式反馈包括评分、用户纠正和“转人工”；隐式信号包括重复提问、重试、接受建议、任务是否完成。

**它们的含义都不唯一。** 不同用户反馈的意愿不同，偏差方向无法只从反馈事件推出。停留时间长可能代表投入，也可能是困惑；接受建议可能只说明用户赶时间。所以反馈要和版本、任务类别、结果阶段、稳定任务 ID 关联；不能把“没投诉”当正确标签，也不能用反馈子集估计总体成功率。

**收集时做 data minimization (数据最小化)。** 只保留解决问题需要的字段。默认不写入完整输入、输出、系统提示词和工具参数。需要复核正文时，用受控访问的脱敏存储、短期保留和明确授权，而不是把正文复制进普通日志。敏感数据在采集或处理阶段按需过滤、删除、遮蔽或转换。低熵标识符（例如工号、短订单号）的散列仍可被猜出，不能称为匿名化。

收到 build 73 的纠正时，先只记录：任务类别、出错版本、可引用的日志行范围、用户明确的修正、隐私审查状态和来源标识。必须打开原文时，按权限访问原始构建系统并记录访问审计，到保留期限后删除。外部系统的授权、用户同意和保留时长由实际服务约束决定，不能由模型推断。

> [!info] 实例：OpenTelemetry GenAI span 约定（2026-11-12 核对主分支）
> 该约定说明输入输出消息和工具参数可能包含敏感内容，默认不记录，并建议生产中谨慎使用外部受控存储。约定标为 development 级，字段和稳定性在部署时要重新核对，不要把正在变化的字段当固定标准。

## 从线上失败到可验收的修复

线上信号告诉你该去哪里查；可验收的修复还要经过下面几步：

1. **收集候选事件。** 把诊断 trace 与模型、提示词、索引和工具版本关联。请求总量、符合条件任务数和完成数来自未采样的计数；trace 与反馈只用于定位事件。
2. **抽样审查并去重。** 检查显式纠正、重试、超时和长期未解决的任务；清除不必要的个人或敏感信息。
3. **分类并确认标签。** 依据可信来源或人工裁定，记录类别、行号和可接受的下一步。保留交付状态、schema 结果与后续正确性审核的来源、版本和裁定者。证据缺失与过度推断可以同时记为缺陷；看不清的标为不确定。
4. **修复对应的层。** build 73 已定位到解释层，候选就从提示词或分类校验入手；如果是源报告不完整，先修取数。
5. **用独立任务验收。** 开发样本调候选，未参与调参的新样本验收。build 73 本身已是开发样例，不能再算作一条线上验收标签。规则见[独立验收与配对统计](holdout-acceptance-and-paired-statistics.md)。
6. **分阶段发布。** 小流量阶段观察同类错误、拒答和副作用，触发预设回滚条件就回滚，并保留诊断 trace。各阶段的判断见[上线、放量与回滚](deployment-rollout-and-rollback.md)。

已审查的线上失败可以进入开发回归集帮助复现。同一事件不能同时用于调候选、选赢家和宣称独立验收。一个稳定的规则评分器可以复用于新的独立样本。如果打算把反馈用作监督微调或偏好训练数据，还要额外审查标签质量、用户同意、数据切分和敏感性。

> [!info] 实例：OpenAI Performance Factory（2026-11-19）
> 这是一条生产中的诊断与恢复链路。告警创建持久任务；Agent 查阅指标、日志与追踪并记录诊断；独立的对抗评审尝试推翻根因解释；工程师审核并决定是否合并修复。发布后，另一个 Agent 检查性能是否回到基线，部分恢复时为剩余问题新建调查。文章报告三个多月跟踪了 1,700 多次调查、定位 600 多个根因案例；人工抽查 100 条根因建议，70% 被评为准确。这个比例描述的是建议质量，不是修复或发布成功率。
>
> 这套流程也用故障改进调查工具本身：反复出现的工具或权限错误进入待办，Agent 提出修复、工程师审核合并，再重放原先卡住的案例，看能否越过同一阻塞点。检验调查能力时，把原始告警放进新会话，只开放当时能取得的证据，隔离事后复盘、旧记忆和已知答案。用于修工具的那次重放是回归证据；新版是否值得保留，仍要用未参与改动的案例验收。
>
> 对 build 73 可以照同一顺序做：核对原始证据，复核根因建议，审批候选提示词，小流量期间观察原误诊是否复现。

> [!info] 实例：生产 Agent 团队怎样评估（*Measuring Agents in Production*，ICML 2026）
> 这项调查的 Figure 8 / Appendix G QO1 是一道多选自报题：31 个回答中 23 个选择人工参与评估，16 个选择模型评估，同一回答可多选。它描述受访团队用哪些办法判断输出质量，不是被人工审核的输出比例、正确率或各办法的效果。对 build 73 来说，点踩、trace、模型自评和经来源核查的审核标签是四种不同的证据；只有最后一种在边界清楚、未被用来挑选候选时，才能承担独立评估标签。

## 阈值来自服务要求

时延、错误、费用和隐私的阈值来自用户体验、工作负载和合规要求，没有适用于所有 AI 服务的通用数字。上线前固定当前基线和需要分层观察的任务切片。变化可能来自提示词、模型提供方、外部数据、索引、工具或产品界面；重要组件更新后重跑代表性评估，比较版本和失败切片。

一次点踩触发调查是合理的；一次点踩就自动改权重、自动发布，不是可靠的改进闭环。已确认的硬权限违规与一般质量差异在放量时怎样区别对待，见[上线、放量与回滚](deployment-rollout-and-rollback.md)。

## 定位到解释层之后：决定改哪一层

本章从一条点踩出发，借助分层关联的 trace 和事后审核，把 build 73 定位到“证据已提供但解释错误”，并把它记成一条带版本、行号和标签的开发案例。同时给出了线上指标的分母规则和分位数的用法。

知道错在解释层，还没决定怎么修：改提示词、加一个分类校验工具、改脚手架，还是训练权重？每种改动怎样变成可重放、可验收、可回滚的新版本，见[选择改动对象](choosing-what-to-change.md)。
