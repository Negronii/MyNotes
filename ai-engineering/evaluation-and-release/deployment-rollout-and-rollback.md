# 候选版本从离线通过到全量，要经过哪些关，回滚又撤得回什么？

离线通过只说明：一个冻结的版本组合在验收集上达标。上线还要证明它在真实端点、真实数据边界、峰值负载和运维责任下仍然成立，并且出事时能退回。

本章有两个输入。一是[选型章](model-selection-and-unit-cost.md)交来的月报助手候选甲：任务契约、预筛门槛、每月成功报告目标和成本公式，但还没碰过真实端点。二是主线五的 CI 诊断助手候选 B：它已经按[独立验收与配对统计](holdout-acceptance-and-paired-statistics.md)通过离线发布决策，等着进入小流量。本章依次回答：部署决策看哪些证据，发布的到底是什么，上线分哪几关，小流量时怎样判断停还是放，失败时退到哪里，回滚又撤不回什么。

## 部署决策要把哪些证据放在一起

选部署方式时，要把四类证据放在一起：候选在目标任务上的评测结果、真实流量的形状、数据边界、团队的运维能力。只有一类证据，定不了方式：

- 任务评测通过，不说明真实端点的限流、区域和数据策略允许这样用；
- 托管推理省掉自己运营服务的工作，但服务条款、留存和模型生命周期由提供方决定；
- 自托管能控制模型版本和运行位置，容量、更新、安全和 on-call（值班响应）也随之落到团队身上；
- “自托管”“端侧”这类标签本身证明不了更便宜、更私密或更快。

四种部署方式各自适合什么条件、要核对哪些责任，对照表在[选型章的部署方式一节](model-selection-and-unit-cost.md)，这里不重抄。

如果考虑自托管，先用[KV 缓存与服务容量](../model/kv-cache-and-serving-capacity.md)估计每个活跃序列的 KV 内存和批处理容量，再在目标硬件上回放代表性峰值负载，检查满足时延目标时的吞吐。没测过同一工作负载，部署选型就还没定；只凭账单或公开基准做不出盈亏平衡结论。

## 总拥有成本由哪几部分组成

比较部署方式的成本时，不能只拿 API token 价格和 GPU 租赁价对比。total cost of ownership (总拥有成本，TCO) 至少包括：

$$
\begin{aligned}
\text{TCO}={}&\text{推理运行成本}+\text{检索与额外存储}\\
&+\text{工程与运维}+\text{评估与风险控制}
\end{aligned}
$$

算的时候守住几条口径：

- **推理按实际走的路径计费。** 走托管 API 计调用费，走自托管计算力和运行时存储，不要两边都算；混合流程先后或并行调用了几处服务，就逐次累加。
- **检索索引和业务数据存储另列。**
- **把看不见的项算进来**：低谷与峰值、冗余、闲置、扩容、支持、更新、故障响应、质量差异带来的返工和人工复核。
- **写明单位**：每请求、每成功报告、每用户还是每月。比较方案时用同一个单位。
- **用时延目标约束容量方案。** 平均 token 量够用，不证明峰值时显存也够；自托管容量要在目标硬件、模型精度、输入/输出长度、并发和批处理条件下实际回放。

TCO 是一期的总账。把它按[每份成功报告的完整成本](model-selection-and-unit-cost.md)的口径除以成功报告数，才能在托管、自托管和人工流程之间按同一个“质量合格报告”单位比较。真实 API 价格、缓存和区域规则以部署时的官方价格页为准，选型章里的价格都是教学值。

## 发布的是一个版本组合

模型发布不是替换一个二进制文件。下面这些配置要作为一个整体管理，用不可变的 release ID（发布标识）记录：

- 服务商、API 端点和 SDK 版本；
- 托管模型 ID 与修订，或自托管的权重摘要、精度和推理运行时；
- 提示词、工具定义、输出 schema 和推理参数；
- 数据源、检索、权限和区域配置；
- 应用服务镜像；
- 评估数据版本、评分规则和门槛。

供应商侧更新模型时，记录响应里实际调用到的模型标识；若供应商不提供固定快照，就把每次重要变化当成新候选。

任一组件变化，就是一个新组合。它要按受影响的门槛重新核验：

| 变化 | 要重查什么 |
|---|---|
| API 提供方、端点、模型或 SDK | 测试凭据、数据用途和费用条件；端点与输出结构的兼容性。可能影响候选输出时，重跑受影响的任务验收；请求路径或负载变了，重跑容量回放 |
| 提示词、工具定义、schema、应用代码或业务规则 | 与拒答、不完整、错误响应的兼容；可能影响输出时，用未参与调优的验收样本重验内容与结构 |
| 数据源、租户权限、留存或区域配置 | 数据契约与访问授权；格式、语义或分布的变化可能影响输出时，用代表性输入重验内容。未授权前不发真实数据 |
| 精度、推理运行时、硬件、输入/输出长度、并发或批处理 | 在目标环境重跑容量回放；可能影响输出时，也重跑受影响的任务验收 |
| 生产监控、值班责任、停止或回滚流程 | 重查生产流量的准入与恢复责任；关键责任没明确前，不接真实用户或生产载荷 |

## 上线分两段、七个阶段

上线按“是否接触真实用户或生产数据”分成两段。第一段四个阶段，都不碰生产：

~~~mermaid
%%{init: {"flowchart": {"nodeSpacing": 12, "rankSpacing": 30}}}%%
flowchart LR
  A["① 本地 mock<br/>合成准备"] --> G["② 冻结候选组合<br/>真实端点<br/>合成测试"] --> C["③ 冻结版实际输出<br/>独立最终验收"] --> D["④ 上线前容量回放<br/>代表性峰值负载"]
~~~

独立验收和容量回放都通过、生产条件也就绪后，才进入第二段的三个阶段：

~~~mermaid
%%{init: {"flowchart": {"nodeSpacing": 12, "rankSpacing": 30}}}%%
flowchart LR
  G["真实流量前<br/>生产授权<br/>线上监控<br/>值班与回滚责任"] --> S["⑤ 影子（可选）<br/>执行就须通过"] --> P["⑥ 受控小流量<br/>全部准入通过"] --> M["⑦ 真实月末实测<br/>完整 TCO 达标<br/>扩至全面生产"]
~~~

两段的分界，是测试请求和生产请求的区别：

- **本地 mock（模拟响应）** 只验证应用怎样处理各种响应，不代表候选模型的实际输出。
- **把公开合成数据发给真实端点**，虽然不是生产流量，仍是一次真实服务请求：要有确定的端点和模型、有效凭据、允许该数据用途的条款、费用约束，以及能监控并随时停止测试的责任人。它不需要生产 on-call。
- **真实用户请求或生产载荷**（包括影子）则必须先有生产授权、线上监控、值班、故障处置和回滚责任。

| 阶段 | 验证或运行什么 | 进入下一阶段的条件 |
|---|---|---|
| ① 本地 mock 与合成准备 | 用公开合成输入检查应用对正常、拒答、不完整和错误响应的处理 | 可以随时开始；不碰真实数据和实际端点。mock 不能替代模型输出 |
| ② 真实端点合成测试 | 用公开合成请求检查准确的 API、模型和 SDK 的能力、schema、限流和计费 | 调用前确认端点与模型可用、凭据有效、条款允许该数据用途和测试额度，并指定测试责任人 |
| ③ 冻结候选的独立最终验收 | 在未参与调优的独立数据集上，让冻结组合生成实际输出，评内容与结构，记录两项比例与交集 | 用到真实数据先过数据授权；生成输出所需的端点请求先满足 ② 的条件。必须在任何影子或试点前通过 |
| ④ 上线前容量回放 | 在目标硬件、运行时和端点组合上回放代表性峰值负载、目标长度、并发和批处理，记录容量与端到端 p95 | 端点调用仍按 ② 的条件管理。这是上线前的容量证据，不是上线后的真实峰值表现 |
| ⑤ 生产影子（可选） | 在允许的数据策略下复制真实载荷给候选处理，不展示结果、不触发写入 | 生产授权、监控、值班、故障和回滚责任就绪，且 ③④ 通过。可以跳过；一旦执行就必须通过 |
| ⑥ 受控小流量 | 少量获准用户实际使用候选 | 同 ⑤ 的生产条件；影子若执行过则已通过。判断规则见下一节 |
| ⑦ 扩至全面生产 | 在获准的小流量里，测真实代表性峰值窗口（月报助手是月末）中的内容、结构、p95、失败与重试、限流和费用 | 真实峰值表现和完整 TCO 都达标；未测或未定不扩量，失败就停止候选并回退 |

> [!info] 实例：真实端点测试的凭据与支出控制（OpenAI，核对于 2026-11-12）
> OpenAI 的 Production best practices 与 API keys 文档建议：应用使用项目服务账号；给密钥设期限，并按“替换 → 验证 → 撤销”的顺序轮换；硬支出上限会在跟踪费用达到上限时停止受影响的 API 流量。这些是 ② 阶段“凭据有效、费用受控”的一种落地方式，不替代团队自己的 on-call 和故障预案。

## 月报助手现在停在第一阶段

按[选型章的结论](model-selection-and-unit-cost.md)，候选甲只在合成开发样例上通过了预筛，选型章算出的月度模型直接费也只是 TCO 分子里的一项。没有人工基线、单位价值和完整 TCO，就不能声称投资回报率为正，也不能据此选定托管、自托管或混合方案。

对照七个阶段，甲现在能做的只有 ①：

- **可以做**：用公开合成数据做本地 mock 准备。
- **不能做 ②**：真实 API 提供方、确切的端点和模型、凭据、数据使用条件、费用约束和测试责任人都还没确定，所以不调用真实端点。
- **不能做 ⑤⑥**：真实数据路径、生产权限、监控和值班责任、独立最终验收集、代表性峰值负载都没验证，所以不接生产载荷，也不做影子或小流量。

选型章的模型 API 直接费上限只适用于托管调用路径；自托管等路径按完整 TCO 另行比较。自托管能力和责任团队仍未知时，也不能把它假设成可用或不可用的基线。

## 小流量期间：停、维持还是放量

候选 B 走的是同一条路，只是已经走得更远。CI 诊断助手的当前版本 A（提示词 p12）在服务，B（提示词 p13）通过了离线发布决策：

~~~mermaid
%%{init: {"flowchart": {"wrappingWidth": 280}}}%%
flowchart TD
    Freeze[冻结 B 与验收协议<br/>预先设定门槛] --> Offline{离线验收通过？}
    Offline -->|否| Keep[B 停止<br/>A 继续服务]
    Offline -->|是| Canary[B 小流量试运行<br/>A 作为回滚目标]
~~~

小流量阶段要分清两件事：“已经观察到违规”和“还没有足够证据放量”。按下面的顺序判断，质量、服务与成本门槛都按预先约定的观察窗口和核验规则：

| 小流量观测 | 动作 |
|---|---|
| 确认系统实际执行了越权读取或写入 | 立即停止 B 的流量，恢复 A。按授权规则正确拒绝的 403 不算越权 |
| 没有越权，但已触发预设的质量、服务或成本回滚条件 | 停止 B 的流量，恢复 A，保留调查证据 |
| 没触发回滚条件，也还没满足放量条件 | 维持当前小流量，不扩量。核验没完成就继续预定核验；已完成却不达标，就调查原因 |
| 独立核验完成，质量、服务与成本都达到预设放量门槛 | 进入下一阶段放量，继续监控 |

两条规则容易用反：

- **缺标签不等于不合格。** 例如 B 的 20 个预定核验任务目前只取得 12 个可信标签，又没触发任何回滚条件，就维持小流量、补完核验，而不是回滚。标签够了也只是核验的一部分，还要用这些标签确认质量是否达标。
- **已确认的回归不能拿“继续收标签”推迟回滚。** 预设条件一旦确认触发，就停。

越权这类硬违规由安全和系统策略设为硬停止条件，一次就停；一般质量差异要连同样本数、分母和不确定性判断。如果小流量期间修改了 B，就要重新冻结候选和协议，用新的独立题验收。门槛的数值来自服务要求，没有通用数字；线上信号怎样定分母、怎样关联版本，见[生产 trace 与指标分母](production-traces-and-metric-denominators.md)。

## 停止门槛与退回检查点

月报助手进入 ⑥⑦ 时，用下面这组停止门槛。门槛数值沿用[选型章的预筛门槛](model-selection-and-unit-cost.md)：

| 检查项 | 门槛 | 触发后的动作 |
|---|---|---|
| 跨租户或越权数据泄漏 | 零容忍 | 立即停止候选请求，转人工月报并调查 |
| 输出结构 | 审核窗口内应输出结构化报告的候选结果全部结构有效；应用必须拦截无效结果 | 停止候选流量，修复后重跑兼容性和离线门禁。拦截不能代替结构有效率监控 |
| 内容（严格阈值筛选、变化额/变化率/总额、行号引用、不臆测原因） | 审核样本通过率不低于选型章的内容门槛 | 低于门槛就停止候选、退回人工流程。若产品要求某类内容错误零容忍，上线前另设硬门槛 |
| 后端完成 p95 | 约定观测窗口内不高于选型章的时延门槛；④ 回放通过，⑦ 前在真实峰值窗口通过 | 回放失败不启动试点；实际超限就停止扩量，退回人工或上一个可用版本 |
| 托管 API 直接费 | 只针对托管调用路径：所有尝试费用 ÷ 成功报告数，不高于选型章的上限 | 超额就暂停托管候选。这是试点调用费保护，不替代部署方式之间的 TCO 比较 |
| 完整 TCO | 全面生产前设定统一预算和比较口径，按同一成功报告单位验证 | 未设定或未测出就保持已获准范围；实际超限就停止候选并回退 |

某一关失败时，退回的检查点如下：

| 发现的问题 | 退回动作 |
|---|---|
| ② 真实端点测试或 ③ 独立验收失败 | 不进生产流量；修订并冻结新组合，另留未用于调优的独立样本，重做实际输出验收。mock 通过不能替代 |
| 测试端点、凭据、数据用途或费用条件缺失 | 暂停实际服务请求，可以继续 ①；补齐条件、指定测试责任人后再测 |
| 生产授权、监控、值班或回滚责任未就绪 | 不做生产数据请求、影子或小流量；解决对应条件后再评估准入 |
| ④ 容量回放不达标 | 不启动试点；调整目标环境或负载方案，重跑回放及受影响的兼容与验收检查 |
| ⑤ 影子检查失败 | 停止复制请求，保持人工流程；修订后重新冻结，重查相关门槛。不能绕过影子失败直接进小流量 |
| ⑥⑦ 中触发安全、内容、结构、时延或费用停止门槛 | 停止候选的新请求；切回仍可运行的上一套已验收组合，没有就转人工。核对在途任务、已交付结果和外部回执 |
| 真实峰值窗口或完整 TCO 尚无测量 | 不扩大已获准范围；先完成代表性观测和同单位 TCO 验证，测得超限就停止候选并回退 |

## 回滚只恢复平台管理的部分

“切回上一个版本”能撤回的，只有部署平台自己管理的那部分配置。

> [!info] 实例：Kubernetes Deployment 回滚了什么（v1.37，核对于 2026-11-12）
> Kubernetes Deployment 可以渐进替换副本，也能回退到之前的修订。官方文档“Rolling Back a Deployment”明确：回滚的是 Pod template。外部的提示词、供应商模型和 API 配置、数据版本、业务状态都不会因此恢复。用 Kubernetes 时，保留带变更记录的修订历史，并确认回退已完成；其他平台也要能把流量切回一个完整、兼容的已验收版本组合。

所以回滚的对象应当是整个[版本组合](deployment-rollout-and-rollback.md#发布的是一个版本组合)，而不只是服务镜像。

更大的边界在外部副作用。如果生成的报告会发邮件、写入别的系统，切回旧版本只是停止新的候选输出，已经发送或写入的内容撤不回来：

- 按应用侧稳定的 run ID 或报告 ID 查交付记录和外部回执；
- 未完成或结果未知的写入，先查询、对账或转人工，不要盲目重发；
- 不把“本地回滚成功”当成“外部效果已取消”；
- 确认错误报告已交付的，走应用定义的更正或撤回流程，保留原版本和回执以便审计。

外部写入在超时或结果未知时怎样对账、什么条件下才能同键重放，见[外部写入与对账](../runs/external-writes-and-reconciliation.md)；运行记录为什么必须由应用自己持有，见[运行身份与权威状态](../runs/run-identity-and-authoritative-state.md)。

## 全量之后，版本靠线上证据决定去留

走完七个阶段，一个版本组合才算全面上线：它有不可变的 release ID，有可退回的上一套已验收组合，有停止门槛和责任人。上线不是终点。线上的错误建议怎样关联到这个 release ID、变成可修复的证据，回到[生产 trace 与指标分母](production-traces-and-metric-denominators.md)；下一轮该改提示词、工具还是权重，见[选择改动对象](choosing-what-to-change.md)。

主线五到这里结束。[AI 系统设计案例](../design-cases/ai-system-design-cases.md)把五条主线放进三道设计题，从风险一路推到各自的发布证据。

> [!info]- 来源
> - **托管服务的数据与留存条件按端点、功能和设置核对**（“部署决策要把哪些证据放在一起”）：OpenAI，[Data controls](https://developers.openai.com/api/docs/guides/your-data)，核对 2026-11-12，“Storage requirements and retention controls per endpoint”说明应用状态与零数据保留资格有功能级例外。不能代替其他提供方合同和本地数据处理审查。
> - **模型标识、生命周期、API 结构和价格会变化**（“发布的是一个版本组合”“总拥有成本”）：OpenAI，[Responses API](https://developers.openai.com/api/reference/resources/responses/methods/create)、[List models API](https://developers.openai.com/api/reference/resources/models/methods/list)、[Deprecations](https://developers.openai.com/api/docs/deprecations)、[API pricing](https://developers.openai.com/api/docs/pricing)，核对 2026-11-12；创建响应使用模型 ID，模型目录列出 ID 和可选 `shutdown_date`，退役页给出迁移信息；价格页只用于查具体调用路径，不代表完整 TCO。

> - **凭据与支出控制**（“上线分两段、七个阶段”实例）：OpenAI，[Production best practices](https://developers.openai.com/api/docs/guides/production-best-practices) 的“API keys”“Managing billing limits”“MLOps strategy”，以及 [API keys and service accounts](https://developers.openai.com/api/docs/guides/api-keys) 的“Manage credentials through their lifecycle”，核对 2026-11-12；项目服务账号、密钥期限、替换—验证—撤销轮换、硬支出上限停止受影响流量，MLOps 部分强调跟踪数据/模型版本与部署工件。
