# 让助手以后不再误诊，该改提示词、工具、脚手架还是权重？

build 73 的误诊已经[从线上定位到解释层](production-traces-and-metric-denominators.md)：证据进了上下文，模型却把连接被拒判成了业务断言失败。工程师要的不是这一次答对，而是以后的请求都不再犯同样的错。本章回答：同一个失败可以从哪几层修，为什么一次只改一层，一个候选从提出到被接受要走完哪条流水线，以及什么时候才轮到训练权重。读者手上有[任务契约](task-contracts-and-quality-dimensions.md)、这条已定位的开发案例，以及[独立验收的规则和 200 题的结果](holdout-acceptance-and-paired-statistics.md)。

## 改进是留下一个新版本

在对话里纠正助手的结论，只改变那一次运行。要让后续请求受益，就要留下一个能**重放、验收、回滚**的系统版本：

- **可重放**：记下了产生它的全部配置，任何人都能在同样输入上复现它的行为。
- **可验收**：能在冻结后首次使用的独立任务上，和当前版本按同一契约比较。
- **可回滚**：上一个已接受的版本登记在案，出问题时能退回去。

纳入版本管理的可以是提示词、任务策略、检索配置、工具和模型权重。会被反复复用的经验和相关运行设置，也要写进可复现的配置记录。

所以“Agent 自我改进”不是指模型在一次对话里改写了自己的参数。单次运行里的状态变化（读了什么、调了什么工具）属于运行本身，见[什么时候该让模型决定下一步](../actions/when-the-model-decides.md)；本章讲的是跨运行保留下来的改动。

## 改进对象分层，一次只改一层

同一个失败可以从不同层修。改其中一层时，其余条件保持不变，才知道结果的变化来自哪里。下表的 harness（运行脚手架）指包在模型外面的提示词、工具接入和控制代码。

| 改动对象 | 对 build 73 的候选改动 | 要验证什么 |
|---|---|---|
| harness 中的提示词 | 只加一条规则：照实报告连接被拒、重试耗尽、服务未就绪和测试跳过，不写成已证实的因果 | 分类、引用、不确定性是否符合契约；难例是否仍正确拒答 |
| 其他 harness 组件 | 加日志检索、引用校验、结构化输出验证 | 证据是否更完整，验证器能否拦住格式错误，成本和故障路径是否可接受 |
| 优化阶段的候选排序器 | 估计哪些提示词或检索设置更值得先测，减少搜索成本 | 是否真的省了搜索成本；选中的候选实测是否有收益。预测分本身不是收益 |
| 部署路径中的决策预测器 | 决定先查哪类证据、是否调工具、是否转人工 | 作为运行系统的一部分，和检索、工具、界面一起验收端到端影响 |
| 基础模型权重 | 用筛选过的样本做 supervised fine-tuning (SFT，监督微调) 或奖励训练 | 训练信号、数据切分和更新是否值得；训练奖励不是新题上的泛化证据 |

候选 B 只改了 harness 中的系统提示词：p12 换成 p13，模型、检索索引、工具、输出格式和生成参数都不动。固定这些便于归因，但消除不了生成的随机性和外部状态的变化，所以 A、B 仍要在相同任务上按预定方案比较。

两种预测器要分开对待。如果改的是优化阶段的候选排序器，先比较这套搜索流程能否在同等预算下找到更好的候选，再单独验收最终部署的提示词。只有预测器也参与线上动作决策时，才把它纳入部署版本一起验收。

如果一次同时改提示词、索引、工具和模型，指标变了也不知道该归功于谁，出了回归也不知道该撤哪一项。

## 先确认要修的行为，再产生候选

进入候选搜索前，先按授权读取助手当时实际读到的日志版本和输出，确认错误行为确实是“把连接问题分类为业务断言失败”，并把服务为何未就绪留作未知。build 73 可以用来修改分类与证据表达规则，它从此是开发证据。

产生候选后，先做低成本的契约筛查：

- 引用的行号是否存在；
- 结论是否超出原始日志的支持范围；
- 未知的根因是否被写成定论。

筛查失败的候选记下理由后淘汰。筛查通过只说明它可以进入完整开发集；这些案例和检查条件参与了候选的形成，仍是开发证据。

## 完整的验收流水线

下图是一个候选从提出到被接受或放弃的全过程。每个“否”都有明确去处，没有一条路能绕过独立验收直接上线。

~~~mermaid
%%{init: {"flowchart": {"wrappingWidth": 280}}}%%
flowchart TD
    Signal[核对线上失败<br/>确认可见证据与版本] --> Scope[固定任务契约、改动对象与预算]
    Scope --> Propose[产生候选<br/>记录版本与搜索依据]
    Propose --> Screen{低成本契约筛查通过？}
    Screen -->|否| Drop[记录失败理由<br/>淘汰该候选]
    Drop -->|预算内继续| Propose
    Drop -->|预算耗尽或全局停止| Keep[保留 A，不放量]
    Screen -->|是| Develop[开发集迭代<br/>A/B 同题对照，记录成本]
    Develop -->|候选违约| Drop
    Develop -->|预算耗尽或全局停止| Keep
    Develop -->|冻结候选、协议与门槛| Holdout[A/B 在同一批独立新题上<br/>按冻结协议运行]
    Holdout --> Review[独立人工核验标签<br/>复核关键输出]
    Review --> Gate{预设门槛全部达标？}
    Gate -->|是| Retain[接受候选，小流量发布<br/>登记 A 为回滚目标]
    Gate -->|否| Reject[保留 A<br/>已用验收题转入开发集]
    Reject -->|预算内继续且未触发全局停止| Propose
    Reject -->|预算耗尽或触发全局停止| Keep
~~~

**冻结时记下什么。** 版本标识；模型与提示词修订；索引和工具版本；任务集版本；评估配置；参与运行的经验或记忆快照的引用；日志脱敏规则。通过和未通过的运行都要能按这份记录复核。

**用 B 走一遍。**

1. 信号与范围：build 73 已定位到解释层；契约固定；改动对象只限系统提示词。
2. 候选与筛查：B（p13）在开发案例上引用的行都存在，没有把根因写成定论，通过筛查。
3. 开发迭代：在开发集上与 A 同题对照，记录成本；没有违约，于是冻结 B、评估协议和六项门槛。
4. 独立验收：在 200 道冻结后首次使用的新题上，A 通过 162 道，B 通过 180 道。不一致的 30 道里，B 修复 24 道、回归 6 道。
5. 人工核验：独立审阅者按同版本原始日志核对标签和关键输出。
6. 门槛：McNemar 双侧 p≈0.00143；B 的 Wilson 下界 85.0593% ≥ 85%；格式 199/200；权限边界用例 0 次越权；压测 p95 3.4 秒；每请求 0.024 美元。全部达标。逐项计算见[发布决策的四类条件](holdout-acceptance-and-paired-statistics.md)。
7. 结果：接受 B，小流量发布，登记 A 为回滚目标。

**两个方向都要看。** 6 道回归题说明 B 在某些情形下比 A 差。门槛通过不代表这些回归可以忽略：它们要逐题查看，弄清是哪类日志让新规则误伤，作为下一轮的开发案例。如果 B 仍把连接被拒报成业务断言失败，它就没解决目标问题；如果分类改善但权限测试回归，也不能接受。

**“否”分支的去处。**

- 筛查或开发阶段违约：记下理由，淘汰这一版，预算内可以继续提出新候选。
- 最终门槛未达标：A 继续服务。这 200 道题已经被看过，转入开发集；修订后的候选要另备一批独立新题，不能拿旧集合再宣称最终验收。
- 不论 B 是否被接受，这 200 道题都已用于一次决策；下一轮候选若在它们上面调参，它们就成了开发证据。

## 搜索前写下预算契约和停止条件

候选可能不止一个，尤其是自动搜索时。开始前写明：

- 最多尝试多少个候选，每个候选运行几次；
- 模型与工具调用次数或实际费用上限；
- 最长运行时限和检查点。

**停止条件分三层。**

- **淘汰一版**：候选给出无证据的根因，或导致关键任务回归。
- **复核一次**：到达无进展检查点时，复核任务定义、评分是否稳定、候选是否足够多样。
- **结束整轮**：发生预先约定的全局停止事件，例如评估环境被污染，或预算耗尽而门槛未过。此时继续用 A。

> [!info] 实例：程序搜索与长时优化的预算参照
> Google Cloud 的 AlphaEvolve 最佳实践（2026-11-10 更新）建议从约 100 次程序评估起步，困难任务扩展到数千次；约 1,500 次评估仍看不到清晰趋势时，暂停复核问题定义或软惩罚，同时提醒困难搜索可能在长平台期后突破。Infrathon v2 的 150 次长运行中，有 135 次在预算后半段刷新了最佳成绩，模型排序也随任务和预算变化。两项都面向程序和 AI 基础设施优化，只能作为设计预算的参照；诊断助手的候选上限要按自身风险与费用预定。

## 冻结后的人工核验

自动检查能核对的有限。行号检查和 schema 检查能确认引用存在、结构合法；但“这个诊断是否正确”的标签，要由独立审阅者依据原始材料，在未参与候选调整和选择的新题上核验，并裁定重要分歧。候选能否放量，再由预设的质量、服务和成本门槛决定。

> [!info] 实例：把自动评价和人工、外部验证分开的研究流程
> Co-Scientist v2 把自动排序、领域专家盲审、科学家反馈和外部验证放在不同环节。Anthropic 关于黑洞物理的文章（2026-11-17）报告用 Lean 形式化并由物理学家复核主要结果；但其链接的 modular bootstrap 论文源码页只列出 TeX 主文件与图件，没有 Lean 文件。也就是说，形式化覆盖了哪些命题、它们与物理假设怎样对应，读者无法自行检查，仍需人工审查。自动检查通过了什么，要和它没覆盖什么一起报告。

## 多根因：设计能区分假设的下一项观察

改提示词修的是“分类说错了”。服务为什么没就绪，是另一个问题。诊断它时，要避免过早认定一个原因。

> [!example] build 73 的两种根因假设
> - **假设一**：服务在重试窗口结束后才开始监听目标端口。
> - **假设二**：服务当时已在另一个端口监听，构建请求仍指向 8081。
>
> 两者也可能同时成立。`ECONNREFUSED` 与两种假设都相容，第 20–22 行区分不了它们。
>
> 下一项观察要让两种假设给出**不同的预测**：
> 1. 先确认三次连接尝试属于同一构建步骤、同一轮就绪探测。
> 2. 按原时间戳，把这个重试窗口与同一进程、同一网络命名空间里的就绪和监听事件对齐；同时核对实际监听的端点、调用目标，以及中间有没有端口映射。
> 3. 若目标端口在窗口结束后才开始监听，支持假设一；记录“窗口内目标端口尚未监听”，其原因仍留作未知。
> 4. 若进程在窗口内已监听另一端口且没有映射，支持假设二。

这个做法是：用已知日志约束候选原因，再挑一项新的、可核对的记录来区分它们。仍然相容的多个原因都保留，直到新证据排除其中一些；不要把最先想到的原因升格成已证实的结论。

> [!info] 研究参照：构造、约束、解释
> Anthropic 的 *Teaching AI to Build Scientific Models*（2026-11-06）把建模概括为 build（构造模型结构）、constrain（用已有观察约束参数）、interpret（比较仍成立的解释，并思考哪项观察能区分它们）。它链接的 ModelSMC 研究（Wahl et al.）用既有观察搜索并重加权候选模型，本身不挑选或执行下一项实验。上面的 build 73 诊断是借用这一思路的工程推演，不是论文里的实验。

## 什么时候才轮到改权重

权重在改动对象表的最后一行，因为它最贵、最难归因、最难回滚。通常要先确认三件事：

- **差距稳定**：同一类行为错误在许多独立任务上复现，不是一两个个案。
- **外层修不了**：调整提示词、补检索证据、加工具或校验都试过，或者明显不对症。缺事实是检索问题，不是权重问题；RAG、长上下文和微调各解决什么，见[从授权文档里找回答依据](../context/rag-indexing-and-retrieval.md)。
- **有可用的数据**：经过审查、切分清楚、同意与敏感性都核过的样本。

即便如此，训练出来的权重也只是又一个候选，要走同一条流水线：训练中奖励上升只说明它更会满足优化目标，泛化与否要在未参与训练、调参和筛选的新题上验收。怎样判断该不该微调、LoRA、SFT、DPO 各改了什么，见[微调：LoRA、SFT 与 DPO](fine-tuning-lora-sft-dpo.md)；用可验证奖励训练推理，见[可验证奖励怎样训练推理能力](reward-based-reasoning-training.md)。

## B 被接受之后

本章把“让助手不再误诊”变成了一个具体决定：只改系统提示词，得到候选 B；B 走完筛查、开发、冻结、独立验收和人工核验，在六项预设门槛上全部达标，被接受为新版本，A 登记为回滚目标。流水线里每个“否”都有去处，用过的验收题不再当验收题。

研究里有不少自动产生和筛选候选的方法，例如反思轨迹改提示词、程序搜索、用预测给候选排序、自动改整个脚手架；它们能给这条流水线借来什么，见支线[自动改进研究的证据边界](automated-improvement-research.md)。

接下来，如果改动涉及换模型，或者要算清每个成功任务的代价，见[模型选型与单位成本](model-selection-and-unit-cost.md)。B 怎样从小流量走到全量、回滚又撤得回什么，见[上线、放量与回滚](deployment-rollout-and-rollback.md)。
