# “回答得好”怎样写成可检查的任务契约？

前四条主线讲的是一个版本怎样看见证据、放行动作、在故障中恢复；这条主线问的是：改出一个新版本后，凭什么证据决定它留下并上线。要判断一个改动值不值得保留，先得说清“好”是什么。本章从一次误诊出发：CI 诊断助手读了 build 73 的日志，给出了一个格式完整、却说错了失败类别的回答。读者手上有这段日志和这条错误回答。本章把“回答得好”拆成一份逐项可检查的 task contract (任务契约)，再为每一项挑选合适的检查方法。后面几章的验收、线上定位和改进都用这份契约判分。

## 案例：build 73 的日志与一次误诊

**案例背景（合成）。** 团队的 CI 诊断助手读取构建日志，用文字给出诊断。发布工程师把失败的 build 73 交给它，要三样东西：失败属于哪一类、能逐行核对的证据、下一步该查什么。下面是日志样本；本主线的日志、版本号和后文的计数都是教学用的合成数据，这里声明一次。

> [!example] build 73 的日志
> ~~~text
> build=73 stage=integration
> line 18: starting local service at 127.0.0.1:8081
> line 19: GET /health
> line 20: connect ECONNREFUSED 127.0.0.1:8081
> line 21: retry 3/3 exhausted
> line 22: integration tests skipped: service did not become ready
> ~~~

当前线上版本记为 A，系统提示词是 p12。A 的回答结构正确，却把这次失败归为“业务断言失败”，还建议回退服务代码。

先看这六行能支持什么。诊断要找的是最早能核实、之后没有恢复的阻塞事件。能确认的事实有三条：第 20 行连接被拒，第 21 行重试耗尽，第 22 行记录服务未就绪、集成测试被跳过。如果连接错误后来恢复、后续步骤照常进行，它就不能单独算主失败；这里没有恢复记录。

再看这六行不能支持什么：

- 不能断言第 20 行的错误来自第 19 行的 `GET /health`。日志没有请求 ID 或其他关联字段。
- 不能把“服务未就绪”改写成“健康检查探针失败”，也不能说“因为进程启动太慢”。根因需要第 20 至 22 行以外的证据。
- 不是业务测试发现了代码回归。集成测试根本没跑。

所以合格的回答可以按日志顺序陈述：“连接被拒且重试耗尽；日志随后记录服务未就绪，集成测试被跳过。”这是先后次序，不是已证明的因果。证据指向第 20 至 22 行。下一步可以核对重试的时间点、服务进程是否已在 8081 端口监听、探针请求的目标地址是否正确。

两种不合格的回答值得对照。只说“构建失败”，事实没错，却没完成用户的任务。说“支付接口断言失败”，类别错了，也没有任何证据支持。A 的回答属于后一种。

## 把要求写成逐项可检查的契约

把上面的判断写成契约，每一项都要能对着日志和标注检查，而不是给一段流畅文本打个总分：

| 契约项 | build 73 的要求 | 怎样检查 |
|---|---|---|
| 主类别 | 恰好给出一个主类别：服务未就绪（连接被拒、重试耗尽），集成测试未执行 | 与标注的主类别比对 |
| 证据 | 关键说法都引用实际存在的日志行（第 20–22 行） | 行号存在，引文与原文一致 |
| 观察与推断分开 | 根因不清时写明未知，不把先后次序写成因果 | 检查是否出现契约禁止的根因断言 |
| 下一步 | 建议与证据相称，例如核对监听端口和重试时间 | 与标注的可接受下一步比对 |
| 证据不足时 | 按事先写明的规则补问或拒答 | 缺少关键行的样本上检查是否猜测 |
| 不得使用的证据 | 不把无关服务的日志当证据 | 引用的行属于本次构建 |

一道题只有在主类别正确、关键说法都引用本次构建中实际存在的日志行、下一步与证据相称、并且没有禁止的根因断言时，才算**契约通过**；证据不足的样本按事先写明的补问或拒答规则判定。任一条不满足就记为失败。反方向的错误同样算失败：把真正的业务断言失败误报成连接问题，也是类别错误。

格式是否符合约定、有没有越权读写，作为独立门禁单独统计，不混进任务正确率。原因是它们的代价不同：一次越权不能被十次答对抵消。

这份契约也定义了后面每条样本要标注什么：主类别、支持它的日志行、可接受的下一步、证据不足时该补问还是拒答。标注怎样做、歧义怎样裁定，见[独立验收与配对统计](holdout-acceptance-and-paired-statistics.md)的样本设计部分。

## 质量维度互不蕴含

“答得好”里包含几个独立的条件。通过其中一项，推不出另一项。以 factual correctness (事实正确性) 和 faithfulness (来源忠实度) 为例：第 20 行是否真的写着 `ECONNREFUSED`，可以对照日志核实；但一个说法可能事实正确，却不是来自给定来源；来源本身也可能过期。所以两项检查不能互相替代。

| 维度 | 在 build 73 中检查什么 | 通过它仍推不出什么 |
|---|---|---|
| task success (任务成功) | 类别、证据、下一步是否满足契约 | 每个说法都为真或无风险 |
| 事实正确性 | 引用的日志行、构建元数据与记录一致 | 证据支持答案里的因果解释 |
| faithfulness / groundedness (来源忠实度 / 依据充分性) | 关键说法有指定日志支撑，且没有实质矛盾 | 日志本身完整、及时、正确 |
| relevance (相关性) | 回答了失败类别和排查方向这两个问题 | 答案正确或证据充分 |
| instruction adherence (指令遵循) | 只报一个主类别、给出行号、遵守格式 | 内容属实 |
| operational quality (运行质量) | 时延、可用性、每次完成的成本达标 | 用户任务成功 |

A 的误诊回答在相关性和指令遵循上可能都通过：它确实回答了“哪类失败”，也给了行号和规定格式。它失败在事实与依据上。只看格式或相关性的评估会把它放过。

## Agent 的结果与轨迹分开评

如果助手是一个 Agent (智能体)，会自己决定查哪些日志、调哪些工具，评估就要区分任务结果和执行轨迹 (trajectory)。

- **结果**看最终诊断是否满足契约。
- **轨迹**指查询顺序、工具调用和中间内容。它用来定位错在取证还是解释，也用来核算成本，但不直接决定通过与否。两条不同的查询路径可能取到不同证据；只要每组证据都足以支撑契约要求的诊断，都应算通过。

有些要求不能折算进结果分：必要的审批、工具权限、不可逆的副作用、契约指定的外部状态。它们是独立的硬门禁。比如助手在诊断途中替用户重跑了构建，即使诊断正确也不合格。动作为什么要单独放行，见[应用怎样放行模型提出的动作](../actions/authorization-gates-for-actions.md)。

## 不把“幻觉”当分类，直接标可观察的错误

hallucination (幻觉) 在各项研究里没有统一的分类法。验收时直接标记可观察的错误更可靠：

- 与外部事实相反；
- 超出给定来源；
- 与给定来源冲突；
- 没有满足格式或动作约束。

如果团队想把“没遵守指令”也算作幻觉，要在自己的标注规则里写明，不要把某篇综述的分类当成通用定义。build 73 的误诊落在“超出给定来源”：日志里没有任何断言失败的记录。后文把“没有依据的根因归因”作为一种需要专门测试的失败模式。

## 为每个维度选相称的指标

有了契约，还要为每项检查选指标。指标要和任务的答案形态相称。

**有明确标签或可执行预期时**，用准确率、精确匹配、F1 或测试通过率；前提是标签正确、样本覆盖充分。F1 是 precision (精确率) 与 recall (召回率) 的调和平均，常用于类别不平衡时兼顾两者。但一个 F1 会掩盖漏报和误报各自的代价。如果业务认为“把连接问题误报成业务断言失败”代价很高（工程师会去回退无辜的代码），就要单独报告“业务断言失败”这一类的 precision 和 recall。

> [!info] precision 与 recall 的分母
> 以“业务断言失败”这一类为例。precision = 被助手判为业务断言失败、且标注也是这一类的题数 ÷ 被助手判为业务断言失败的题数；它回答“报出来的有多少是真的”。recall = 被助手判对的业务断言失败题数 ÷ 标注为业务断言失败的题数；它回答“真的有多少被报出来”。A 把 build 73 判成断言失败，拉低的是这一类的 precision。

**文本重合指标** BLEU 和 ROUGE 衡量输出与参考文本的词面重合。BLEU 最初用于快速评估机器翻译，ROUGE 是一组摘要评估指标。合理的改写可能与参考文本几乎不重合，错误的回答也可能重合很高，所以它们管不了事实。

**检索阶段**可以用检索的精确率、召回率和排序指标，前提是标注了相关文档或证据行。这些数取决于候选集、标注规则和 top-k，单靠它们验证不了最终答案。

如果助手先检索日志和运行手册、再据此生成，它就是一条 retrieval-augmented generation (RAG，检索增强生成) 链路。分阶段测量能帮助定位：检索是否取回了服务启动相关的日志行；基于取回内容的生成是否区分了观察和推断；端到端的诊断能否让工程师找到真正的故障。组件分数不能代替端到端结果。证据从来源到回答的哪一环会坏、怎样逐层排查，见[回答的主张核对与失败定位](../context/claim-verification-and-failure-localization.md)。RAGAS 和 ARES 是两种 RAG 评估框架：前者按上下文相关性、答案忠实度、答案相关性等维度打分，后者把自动评审、人工标注和统计估计结合。两者的维度定义不完全一致，都代替不了完整的任务契约。

## 开放式任务：rubric 与模型评审

诊断的措辞没有唯一答案。这类开放任务可以用 rubric (评分准则) 或模型评审，但准则必须给出可观察的判定锚点。上一节的契约表就是 build 73 的 rubric：每一项都能对着日志判是或否。“答案看起来专业”不是锚点，评分者不能因此给高事实分。

用一个模型去评另一个模型的输出（LLM-as-a-judge，模型评审）时，要检查评审本身：

- **遗漏证据。** 评审可能没对照日志就认可了一个流畅的根因说法。
- **位置偏好、冗长偏好、自我偏好。** 评审可能偏向先出现的答案、更长的答案，或与自己同源模型的答案。偏差大小随任务、模型和评分协议变化。
- **检测手段。** 随机交换两个候选的位置，或让人类在一组共享的校准样本上盲评，能发现一部分偏差，但不能保证评审独立或正确。

**成对比较只给出相对结论。** 评审选出的赢家只说明它相对更好，不说明它达到了任务底线。两个答案都把 `ECONNREFUSED` 说成断言失败时，较简洁的那个仍应判失败。

**评审要先校准。** 在目标任务和 rubric 上，对照一份人工裁定集检查评审的判定。评审之间一致只说明打分稳定，不证明标签正确。后果严重或需要专业判断的结论，安排人工裁定。

> [!info] 实例：MT-Bench 与 Chatbot Arena 的人机一致率（Zheng et al., 2023）
> 在这项研究里，GPT-4 评审与人工偏好的一致率，剔除平局后在 MT-Bench 和 Chatbot Arena 上分别为 85% 和 87%；把平局计入时分别为 66% 和 64%。MT-Bench 还把换序后判断不一致的样本按平局计。同一组数据，统计口径一变，一致率就差约二十个百分点。这些数描述的是当时的样本和评审模型下“与人的偏好一致”的程度；任务正确性仍要逐项对照契约和标签核验。

BLEU、ROUGE、模型评审、natural language inference (NLI，自然语言推断) 分类器、自动事实检测和二次检索，都只覆盖各自定义的那部分信号。多次生成的答案一致不代表答案为真；二次检索也可能取回过期或无关的来源。报告时写明每种检查依据什么、什么情况下会失效，不要把检测器分数写成“事实已核实”。

## 契约定下之后：候选 B 的改进要用数据检验

本章产出三样东西：一份逐项可检查的契约和“契约通过”的组合判定；与正确率分开统计的格式、权限门禁；每条样本该标注的期望结果。build 73 本身用来暴露问题，是开发样例。

针对这次误诊，团队做了一个候选版本 B：系统提示词改为 p13，只补充一条分类规则——遇到连接被拒、重试耗尽、服务未就绪这组信号时照实陈述，根因不清就写未知。按这份契约在 200 道独立题上判分，A 通过 162 道，B 通过 180 道。这 18 道的差距是真改善还是抽样波动，B 又该不该替换 A，由[独立验收与配对统计](holdout-acceptance-and-paired-statistics.md)回答。
