# 如何监控生产中的 AI 功能并安全地改进？

## Build 73 上线后，一次错误建议怎样变成可修复证据？

发布团队上线了日志助手。工程师提交 build 73 的构建报告，助手给出结构正确的答案，却把 ECONNREFUSED 误判为业务断言失败。用户点踩并指出“构建日志记载服务未就绪，因此集成测试被跳过”。这描述可观察状态，不足以判定进程启动慢、探针目标错或其他根因。单看一次 HTTP 200 或 JSON schema (结构定义) 合法，系统看起来运行正常；单看用户点踩，也还不知道错在日志获取、检索、模型判断还是评价预期。

生产 observability (可观测性) 需要把一次任务的服务过程、版本和结果关联起来，同时限制收集的数据。先记录请求级证据，再经过审查和独立验收，把新反馈闭回监控入口：

~~~mermaid
flowchart LR
    Request[任务 ID<br/>与用户请求] --> Trace[关联追踪<br/>与运行版本]
    Trace --> Outcome[记录交付、工具状态<br/>与费用]
    Outcome --> Feedback[关联反馈<br/>与任务结果核验]
~~~

只有分类并经隐私审查的反馈才能形成开发案例。修复层确定后冻结候选与协议，先过独立离线门槛，再进入小流量阶段：

~~~mermaid
%%{init: {"flowchart": {"wrappingWidth": 280}}}%%
flowchart TD
    Freeze[冻结 B 与验收协议<br/>预先设定门槛] --> Offline{离线验收通过？}
    Offline -->|否| Keep[B 停止<br/>已接受版 A 继续服务]
    Offline -->|是| Canary[B 小流量试运行<br/>A 作为回滚目标]
~~~

小流量阶段要区分“已经观察到违规”和“还没有足够证据放量”。判断顺序与动作如下；质量、服务与成本门槛按预先约定的观察窗口和核验规则判断：

| 小流量观测 | 动作 |
|---|---|
| 确认系统实际执行了越权读取或写入 | 立即停止 B 的流量，恢复 A；按授权规则正确拒绝的 403 不属于越权。 |
| 没有越权，但已触发预设的质量、服务或成本回滚条件 | 停止 B 的流量，恢复 A，并保留调查证据。 |
| 尚未触发回滚条件，但尚未满足放量条件 | 维持当前小流量，暂不扩量；核验未完成时继续预定核验，已完成时调查未达标原因。 |
| 独立核验完成，质量、服务与成本均达到预设放量门槛 | 进入下一阶段放量，继续监控。 |

取得足够标签只是完成核验的一部分，还要用这些标签核实任务质量是否达标。缺少标签不等于质量失败；已经确认的回归也不能靠“继续收集标签”推迟回滚。若修改 B，重新冻结候选与协议，并用新的独立留出题验收。

## 一条请求需要留下哪些可连起来的信号？

一次 trace (分布式追踪) 把请求根 span 与其子 span 串成端到端操作。span (追踪片段) 可记录身份检查、构建日志读取、运行手册检索、模型生成、结构校验和结果交付等阶段的耗时、状态和关联版本。OpenTelemetry trace 可以连接日志与 span；GenAI 语义约定仍在发展，避免把不断变化的模型字段约定误当固定标准。

一个 `task_id` 可以对应多次 `attempt_id`；每个 trace 明确指向某次尝试，重试时沿用任务 ID 并产生新的尝试 ID。下面的 Build 73 trace 对应第 1 次尝试，不代表整个任务没有重试或后续状态。

诊断重复调用时，再关联应用模型调用 ID、software development kit (软件开发工具包，SDK) 的调用尝试、`runId`/图线程（thread）与worker（工作进程）尝试、`tool_call_id`、规范化参数摘要、来源版本、观察数量和计划版本。这样的分层轨迹才能分开客户端重试、运行恢复和Agent（智能体）自己重复发起的无进展循环；一段 build 42 的具体 trace 见[编排中的计划执行与循环诊断](../agents/orchestration-patterns.md#计划执行何时需要重规划，怎样识别无进展循环？)。

| 阶段 | 可用于定位的记录 | 不应默认保存什么 |
|---|---|---|
| 接收请求 | trace ID、任务类别、地区、时间、受限访问的会话引用、请求入口状态 | 未脱敏的用户姓名、完整自由文本问题 |
| 读取构建产物 | 构建编号、制品版本、读取状态、耗时、允许访问的范围 | 完整原始日志或未经筛选的环境变量 |
| 检索运行手册 | 索引版本、候选数、证据引用 ID、耗时、权限结果 | 不必要的文档正文、对用户不可见的权限字段 |
| 模型调用 | 部署模型版本、提示词版本、结束状态、输入/输出 token（词元）数、耗时和费用 | 默认记录完整 prompt (提示词)、答案和工具参数 |
| 验证与交付 | schema 结果、证据引用是否存在、拒答/升级结果、是否成功交付 | 将私密正文复制到通用应用日志 |
| 任务结果复核 | 任务 ID、业务系统确认的结果或审核标签及其来源版本；未复核时记为未知 | 把 HTTP 状态、schema 合法或模型自评当作任务正确标签 |

> [!example] Build 73 的合成 trace
> - 关联键：task_id=ci-build-73，attempt_id=1，trace_id=trace-build-73-1。
> - 构建制品读取：成功；受控存储中的标识为 build-73-report@r4。
> - 检索：成功；index=runbook-index-v12，返回 runbook/service-readiness@v7#startup。
> - 实际组装给模型的证据：build-73-report@r4#L20-L22 与 runbook/service-readiness@v7#startup；记录 prompt p12、模型部署 log-assistant-2026-10-31。
> - 模型生成：1.1 秒，主类别为 assertion_failure，引用构建日志第 20 行。
> - schema 校验和响应交付：均成功。
> - 事后审核：审阅者按同一版本的 build 73 日志核实第 20 行连接被拒绝、第 21 行重试耗尽、第 22 行构建日志记载服务未就绪并跳过集成测试；根因仍未确认。因此把这条答案标为分类/解释错误，而非读取或检索错误。trace 记录当时实际使用的证据、版本和交付状态；分类是否正确来自审阅者对同版本原始日志的核验。
>
> 这些是假设的教学标识，不是真实生产 ID。逐条检查最终组装上下文后，这个案例可定位到已提供证据的解释层；若模型实际收到的证据缺行、索引过期或权限过滤错了，分类就应改为数据/检索层。把交付状态、事后正确性标签和根因判断分开记录。

任务结果要与服务信号并列：端到端延迟和time to first token（首个词元时延，TTFT）、吞吐量、排队、超时和错误、尝试成本、工具调用成功率、权限拒绝、任务交付、人工升级和用户纠正。以下各指标先固定单位，再写分子与分母：

| 指标 | 观察单位与计算 | 口径提醒 |
|---|---|---|
| 任务完成率 | 已确认完成的任务数 / 全部符合条件任务数 | 每个任务只计一次；不能用尝试数作分母。 |
| 尝试失败率 | 失败尝试数 / 全部符合条件尝试数 | 一个任务可有多次尝试；重试会增加尝试分母，不增加任务数。 |
| 工具调用成功率 | 成功工具调用数 / 全部符合条件工具调用数 | 用唯一 `tool_call_id` 去重；不能把任务数或尝试数作分母。 |
| 每次尝试成本 | 全部符合条件尝试的推理与工具费用 / 符合条件尝试数 | 费用分子包括失败、重试与未完成尝试产生的费用。 |
| 每个已完成任务成本 | 全部符合条件尝试的总费用 / 已确认完成任务数 | 分子仍含未完成任务的尝试费用；只报这个指标会掩盖失败成本。 |
| 审核样本正确率 | 审核样本中契约通过任务数 / 已取得可信标签的审核任务数 | 这是被审核子集的结果，不能直接除以全部任务数。 |
| 标签覆盖率 | 有可信标签的任务数 / 全部符合条件任务数 | 未核实标签记为未知，不默认为通过或失败。 |

> [!example] 合成计数：任务、尝试、工具调用与标签
> 假设共有 100 个符合条件任务、101 次符合条件尝试（其中一个任务重试一次）、60 次符合条件工具调用。80 个任务已确认完成；从全部 100 个任务中随机抽取 20 个并成功取得可信标签，其中 17 个满足契约。57/60 次工具调用成功。若 101 次尝试总费用为 `$C`，则每次尝试成本是 `$C/101`，每个已完成任务成本是 `$C/80`，未完成尝试的费用仍在两个分子中。
>
> 这批数的任务完成率是 `80/100=80%`；审核样本正确率是 `17/20=85%`，标签覆盖率是 `20/100=20%`；工具调用成功率是 `57/60=95%`。85% 是 20 个被审核任务的观测比例，不能当作整体任务正确率。只有抽样过程、实际标签取得过程都足以支持外推时，才估计总体正确率。抽样权重只能校正已知的抽取概率；如果更容易给已完成或成功任务贴标签，需按结果和任务类别检查标签缺失，补充审核或限制结论，权重不能自动修复系统性缺失。

稳定任务 ID 用于把答案与后续业务结果或审核关联；未核实的任务结果标未知。任务完成与交付可用全量计数，正确性只在可信标签上计算，尝试失败与费用则按所有尝试计。诊断 trace 可能经采样，点踩反馈也只是有选择的子集，都不能直接充当总体正确率分母。

不要把独立分位数相加当端到端分位数。例如身份检查的 p95 (95th percentile，第 95 百分位) 加检索 p95 加模型 p95，不一定等于总请求 p95；请求之间的相关性、队列和尾部时延都会改变总体分布。按用户可感知的端到端指标设服务目标，再用阶段 span 定位预算被谁消耗。

## 从轨迹定位失败类型，而不是猜一个根因

收到反馈后，先给失败分配可观察类别，再决定改哪层。一个事件可能同时有表现与根因：模型可能给错分类，而检索也可能漏掉相关片段；应保留两者，避免一个标签抹掉调查路径。

| 观察到的失败 | 可检查证据 | 首要调查方向 |
|---|---|---|
| 日志读取或工具调用失败 | 工具返回码、超时、重试和目标版本 | 连接、凭证、依赖健康或调用契约 |
| 正确证据没有进入模型上下文 | 检索候选及排序、索引版本、权限过滤记录 | 数据更新、分块、检索或授权过滤 |
| 证据已提供但解释错误 | 被引用的证据 ID 与输出说法、同类样本表现 | 提示词、模型能力、训练信号或验证器 |
| 结构有效但用户仍无法行动 | 输出 schema 与用户实际任务要求、升级路径 | 任务契约、界面、缺少的上下文或产品策略 |
| 用户报告内容错误但 trace 缺少证据 | 采样、脱敏策略及可访问的原始记录指针 | 可观测性缺口；不能用缺失日志假装错误不存在 |

若模型把 ECONNREFUSED 解释为业务断言失败，而构建日志记载服务未就绪并跳过测试，现象是“证据解释/任务分类错误”，但根因仍待查；若日志读取工具返回了空文件，现象则先是数据获取失败。每次修复应针对经检查的层：来源数据、检索、prompt、工具、模型、界面或策略。只凭相关性改动模型，可能掩盖权限或数据问题。

## 反馈并非随机标签：如何降低隐私风险和偏差？

显式反馈包括评分、用户纠正和“转人工”；隐式信号包括重复提问、重试、接受建议、是否完成任务。它们有偏且含义不唯一：不同用户对反馈的意愿不同，偏差方向不能仅从反馈事件推出；停留时间长可能代表投入，也可能是困惑；接受建议可能只表示用户赶时间。反馈事件应和版本、任务类别、结果阶段及稳定任务 ID 关联，不能把“没投诉”当正确标签，也不能用反馈子集估计总体成功率。

收集时做 data minimization (数据最小化)：只保留解决问题所需的字段。默认不写入完整输入、输出、系统提示词和工具参数；需要复核正文时，用受控访问的脱敏存储、短期保留和明确授权，而不是把正文复制到普通日志。OpenTelemetry 的 GenAI span 约定说明消息和工具参数可能包含敏感内容，默认不记录，并建议在生产中谨慎使用外部受控存储；该约定目前仍是开发级，字段与稳定性需要在部署时重新核对。敏感数据处理还应在采集或处理器阶段按需过滤、删除、遮蔽或转换；低熵标识符的散列仍可被猜测，不能称为匿名化。

收到 build 73 的用户纠正时，只需先记录：任务类别、错误版本、可引用的日志行范围、用户明确的修正、隐私审查状态和来源标识。若必须打开原文，应按权限访问原始构建系统并记录访问审计；到达保留期限后删除。对外部系统的授权、用户同意与保留时长由实际服务约束决定，不能由模型自行推断。

## 把线上信号变成独立验证，而不是直接喂训练

1. **收集候选事件：** 将诊断 trace 与模型、prompt、索引和工具版本关联；请求总量、符合条件任务数和完成数来自未采样计数，trace 与反馈只用于定位事件。
2. **抽样审查并去重：** 检查显式纠正、重试、超时和长期未解决任务；清除不必要的个人或敏感信息。
3. **分类并确认标签：** 依据可信来源或人工裁定记录类别、行号和可接受下一步；保留交付 span 的 schema validity (结构校验状态)、delivery status (交付状态) 与后续正确性审核的来源、版本和裁定者；不清楚的案例标注为不确定。
4. **修复对应层：** 例中若模型忽略就绪错误，可能调整提示词或分类校验；若源报告不完整，先修取数。
5. **做配对比较和独立验收：** 用开发样本调候选，用未参与调参的新样本验收；按任务切片查看质量、硬约束、成本和时延。
6. **分阶段发布：** 小流量观察同类错误、拒答和副作用，触发预设回滚条件就回滚并保留诊断 trace。

> [!example] Build 73 的合成发布续例
> 下面延续同一故障类别，所有数值和上线结果都是教学假设，不是生产数据。基线 A 用提示词 p12；候选 B 用提示词 p13，只补充分类规则：遇到本例这些信号时，要求写明“连接被拒且重试耗尽，构建日志记载服务未就绪并跳过测试”，并把根因保留为未知。模型版本、索引、工具、输出格式和生成设置冻结不变。Build 73 是开发案例，不在最终验收集。
>
> 用目标工作负载抽取 200 个此前未参与调参或选版的独立任务；与[评估章的合成配对样本](../evaluation/llm-evaluation-methods.md#用独立验收集比较基线和候选)使用相同契约，任务通过要求分类、逐行证据、下一步和未知根因处理全部正确。A 为 162/200（81%），B 为 180/200（90%）；B 的双侧 95% Wilson 区间下界为 85.0593%，高于预设 85% 门槛。A、B 在这 200 道题上使用相同输入与协议配对运行。B 的 199/200 个输出符合格式（99.5%，门槛 98%），B 对 200 个符合条件的请求各运行一次，总推理成本 `$4.80/200=$0.024`/请求（门槛 `$0.03`），单独压测 p95 为 3.4 秒（门槛 4 秒），20 个权限边界用例全部完成，其中确认的越权为 0（要求 0）。因此这个合成离线门禁通过；相对分数提升本身不替代绝对下界、格式、成本或权限检查。
>
> 小流量期间，若确认助手实际读取或写入了未获授权的数据，就停止 B 并恢复 A；按规则拒绝访问（例如正确的 403）不是越权。若按预设观察窗口已触发质量、服务或成本回滚条件，同样停止 B 并恢复 A。若尚未触发这些条件，只是20 个预定核验任务目前仅取得 12 个可信标签，则维持当前小流量，完成预定核验后再结合质量、服务与成本门槛决定是否放量。若修改 B，需重新冻结协议并用另一批新任务验收。

已审查的线上失败可以进入开发回归集，帮助复现；不要让同一事件同时用于调候选、选择赢家和宣称独立验收。一个稳定的规则评分器可以复用于**新的独立样本**，前提是它在此类输入上可靠且评分规则适用；奖励训练分数只说明策略优化了该目标，不证明未见分布上的任务质量。若打算将反馈作监督微调或偏好训练数据，需额外审查标签质量、同意、数据切分与敏感性。[评估章](../evaluation/llm-evaluation-methods.md)定义独立比较和统计门禁；[Agent 改进与版本验收](../agents/agent-improvement-and-version-acceptance.md)解释怎样把通过验收的改动保存成版本。

生产调查中的“用了什么评估”也不能替代这些标签边界。*Measuring Agents in Production* 的 Figure 8 / Appendix G QO1 是一项多选自报题，31 个回答里 23 个选择人工参与评估，16 个选择模型评估；同一回答可选多项。这描述受访者用哪些办法判断输出质量，不是被人工审核的输出比例、正确率或各办法的因果效果。案例中报告的低置信度升级与高置信度随机抽检，也只是被观察到的做法。对 build 73 来说，点踩、trace、模型自评和经来源核查的审核标签仍是不同证据；只有最后一类在边界清楚且未被用来挑选候选时，才可能承担独立评估标签。

## 由服务要求决定阈值

延迟、错误、费用和隐私阈值来自用户体验、工作负载和合规要求，没有适用于所有 AI 服务的通用数字。上线前固定当前基线与需要分层观察的任务；变化可能来自提示词、模型提供方、外部数据、索引、工具或产品界面。重要组件更新后重跑代表性评估，并比较版本和失败切片。

出现一次硬权限违规应如何处理，可由安全和系统策略设为硬停止条件；一般质量差异则应连同样本数、分母和不确定性判断。一次点踩触发调查是合理的，一次点踩自动改权重、自动发布不是可靠的改进闭环。
