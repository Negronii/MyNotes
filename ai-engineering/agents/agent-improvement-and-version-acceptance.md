# 如何验证并保留对 Agent 的改进？

## 从 build 73 的误诊开始

> [!example] Build 73：从误诊中提出候选改进
> 发布团队的日志助手收到 build 73 的失败记录。相关三行日志是：
>
> ~~~text
> line 20: connect ECONNREFUSED 127.0.0.1:8081
> line 21: retry 3/3 exhausted
> line 22: integration tests skipped: service did not become ready
> ~~~
>
> 基线把连接错误归成“业务断言失败”，建议回退服务代码。三行只支持“连接失败后，集成测试未执行”这一可观察类别；第 22 行是探针状态，不证明进程启动慢、监听地址错或其他根因。工程师需要一项可持续的改进：助手引用证据、区分观察和推断，并在根因尚不清楚时保留不确定性。

一次回答中修正结论只改变当前运行状态；要让后续请求也受益，需要留下能重放、验收并回滚的系统版本。版本化范围可包括提示词、任务策略、检索配置、工具和模型权重；持续复用的经验与相关运行设置也应纳入可复现的配置记录。“Agent 自我改进”不表示模型在一次对话中自行改写参数。单次运行中的状态变化由[智能体基础](agent-fundamentals.md)说明；本章关注跨运行保留的改动。

将当前已接受版本记为 A。Build 73 的最小候选 B 只在 harness 的 system prompt (系统提示词) 中补一条规则：把“连接失败导致测试未执行”与“业务断言失败”分开；引用日志中的连接、重试和测试状态，并且在缺少根因证据时不把探针状态解释成启动慢。候选没有修改模型、检索索引、工具、格式或生成设置。固定这些条件有助于归因，但不能消除生成随机性或外部状态变化；仍需在相同任务上控制运行条件并按预定方案重复评估，见[大语言模型评估方法](../evaluation/llm-evaluation-methods.md)。

配对比较要同时记录两个方向的“失败翻转”：A 失败而 B 通过，是修复；A 通过而 B 失败，是回归。只看 B 的平均分，会把两者抵消掉。用于修改候选、设置阈值或选择胜者的结果都属于开发证据；锁定候选和验收条件后，才打开此前未参与这些决定的最终留出任务。

~~~mermaid
flowchart TD
    Signal[复核失败，固定任务契约与预算] --> Develop[在开发集迭代候选 B<br/>与基线 A 同题对照，检查修复与回归]
    Develop -->|锁定候选与验收协议| Holdout[A 与 B 分别运行同一批独立新任务]
    Holdout --> Gate{预设门槛达标？}
    Gate -->|通过| Retain[标记已接受版本，分阶段发布]
    Gate -->|未通过| Reject[保留 A，旧验收题转开发回归<br/>修订后另备独立新题]
~~~

## 先说清楚哪个对象会改变

同一个失败可以由不同层面修复。改变其中一层时，其余条件先保持不变，才能知道结果来自哪里。

| 改变对象 | 在 build 73 中的候选改动 | 需要验证什么 |
|---|---|---|
| harness 中的提示词组件 | 只增加规则：将连接失败导致测试未执行与业务断言失败分开，并保留根因未知。 | 分类、引用和不确定性是否符合任务契约；难例是否仍能正确拒答。 |
| 优化阶段的候选排序预测器 | 估算候选提示词或检索设置在哪些任务上更值得先测，以减少搜索成本。 | 是否减少实际搜索成本；排序选中的候选在真实执行中是否有收益。预测分本身不是收益。 |
| 部署路径中的决策预测器 | 例如决定先查哪类证据、是否转交工具或是否升级人工。 | 作为运行系统的一部分，与检索、工具和界面组合验收其端到端影响；离线校准不能代替部署结果。 |
| 其他 harness 组件 | 增加日志检索、引用校验和结构化输出验证。 | 证据是否完整、验证器能否拦截格式错误，以及成本和故障路径是否可接受。 |
| 基础模型权重 | 对经筛选的样本进行 supervised fine-tuning (SFT，监督微调) 或奖励训练。 | 训练信号、数据切分和更新是否值得；训练奖励本身不是新题泛化证据。 |

Build 73 的候选 B 只改 harness 中的提示词；它不改模型权重，也不动其他运行组件。若同时改优化阶段的候选排序器与提示词生成策略，先比较这套搜索流程能否在同等预算下找到更好的候选，再独立验收最终要部署的提示词。只有预测器也参与线上动作决策时，才把它纳入部署版本一并验收。若一次改提示词、索引、工具和模型，指标变化就难以归因。权重训练是另一条更新对象不同的路线，其过程与目标归属[微调策略](../fine-tuning/fine-tuning-strategies.md)和[奖励驱动的推理训练](../fine-tuning/reward-based-reasoning-training.md)；本章仍负责版本化候选及其接受证据。

## 从哪些样本和轨迹中学

线上点踩或纠正只把 build 73 指向待查事件。经授权读取原始日志、确认版本并核对第 20 至 22 行后，才把它标成开发案例；trace (追踪记录) 说明助手收到了哪些证据、输出了什么，不能单独证明业务根因。应把同类已裁定案例和边界情形加入开发集，并保留标签来源。生产信号如何审查、怎样从其中形成可复核案例，见[生产可观测性与反馈](../systems/ai-production-observability-and-feedback.md)；样本是否代表目标任务及最终留出如何隔离，见[大语言模型评估方法](../evaluation/llm-evaluation-methods.md)。

GEPA-Curator 论文把逐题轨迹用于选择下一批训练任务：执行 Agent 跑题，评估器记录轨迹和结果；Curator 选择值得再试的任务，也会暂时跳过反复稳定成功、受环境限制或评分不稳定的任务，之后再检查它们。面对一题失败，它还可找到同一道训练任务上由可信检查器验证、而非模型自评的可靠成功轨迹，交给 Reflector 对照；找不到就不提供。执行 Agent 负责产出轨迹，评估器负责记分，同一优化模型在 Curator 环节选择任务和参考轨迹，在 Reflector 环节提出提示词候选。Curator 不决定最终保留哪个提示词，也不更新模型权重。

用于 build 73 是工程推演：若同一开发任务留有可靠成功与失败轨迹，候选作者可比较两次运行是否看见同一行证据、采取了什么判读；只有一次失败时，不要伪造成功对照。候选提示词仍须在完整开发任务集上实跑。论文让提示词逐版迭代，定期在验证集评分，最后选择验证分最高的一版；它不是每次改动后都经过独立逐步门禁。最终留出测试不参与选择。凡用于修改候选、设阈值或挑选胜者的数据都属于开发证据；验证集反复承担选版后，不能再充当最终独立验收。

换题训练是更新对象不同的比较，不是候选 B 的一部分。A-RSI v1 用训练日志判断何时换到下一个预生成任务池：健康检查通过后比较训练窗口的信号；满足触发规则才换池，未触发则继续当前池并在后续合格窗口复查。在论文的 Qwen3-VL-8B-Instruct 设置里，`U` 从 239 降至 195（`195/239 ≈ 0.816`），触发换到一个 400 题新池。这里的 `U` 不是奖励总和或答对题数：同一题会采样多个回答，每个回答的总奖励相对该题组内平均值形成优势；正确性、格式和终止都影响总奖励。若同题回答总奖励相同，该组没有相对奖励差异；`U` 统计出现非零优势的不同题目数。任务池变了，策略权重仍接续训练。窗口资格、具体触发线以及优化器/学习率调度器如何处理见章末折叠来源。

论文的同进度第六窗口比较中，新池方案 Macro11 为 60.40，继续旧池为 58.35；每个策略臂各一次训练，且该结果不能隔离换题与刷新时机的作用。作者还指出完成/截断变化参与了得分差异，因此不能把增益全归于推理能力。诊断用留出任务不进入训练 reservoir，任务家族比例仍参考评估基准元数据。没有固定在三窗换题的随机刷新对照，不能据此断言自适应时机优于固定时机，也不能把换题当所有训练任务的规则。迁移到 build 73 的提示词候选时，不会更新权重或产生同类组内优势；本地应按开发轨迹定义选样信号，不能照搬论文阈值，最终仍由未参与选择的任务结果决定是否保留。

## 预测可以省实验，但必须让结果闭环

一些递归改进系统先用预测来挑值得测量的候选。这减少昂贵试验的搜索成本，却引入“预测错了”的风险。因此先固定 task contract (任务契约)：输入输出、限制、可用预算、程序检查器、成功定义和停止条件；再记录每个候选的证据来源。下面按信息来源区分 RSI-Anything 论文的四类证据；它们不是固定的质量排序，也不要求所有领域采用同一标准：

| 来源 | 代表什么 | 何时仍需外部检查 |
|---|---|---|
| E0：确定性规则或程序检查 | verifier (可执行验证器)、单测、形式化条件等可以直接执行的判据。 | 检查器是否覆盖真实任务，以及是否能被候选投机利用。 |
| E1：学习型预测或 rollout (模型展开轨迹) | 模型对结果或未来状态的估计；这里的 rollout 是模拟未来，不是实际执行。 | 预测不是结果；选中候选仍要实测。 |
| E2：模拟器或高保真模型 | 在模拟环境中执行的状态转移或任务测量。 | 仿真与实际环境存在差异时要做外部校验。 |
| E3：外部测量 | 真实任务、硬件、用户或实验系统中的观察结果。 | 仍需控制变量、预算和测量噪声。 |

RSI-Anything v1 的 world model (世界模型) 根据候选动作预测下一状态，再由领域 readout (读出函数) 把预测转成任务结果或其概率分布，并据此排列候选的实测优先级。预测只是选择下一项实验的依据，真实执行结果才是任务证据；覆盖不足时应保留不确定性，不能把“没看到反例”当成可靠。其潜在表示结构的 OPF 细节留在章末来源供查阅。

论文将 update data (候选更新数据) 用于构造候选版本，gate data (保留门禁数据) 用于选择保留版本；指定的 held-out audit set (留出审计集) 只留作最终结果报告。对策略或预测器候选先分别与当前组件配对检查：单组件门禁失败就保留该组件的当前版本；若至少一项改变，再把新组件组合与当前 policy–model pair 配对比较，组合门禁失败则保留整对。这里的论文协议不取代本地发布流程中另留未参与调参或筛选的新题作独立验收。

### 多种根因可以共存；下一项观测要让它们作出不同预测

Teaching AI to Build Scientific Models 将过程概括为 build（构造模型结构）、constrain（在给定结构下用已有观察约束可调参数）和 interpret（比较仍成立的解释，并思考哪项观察能区分它们）。这篇文章说明研究方向，不是对日志 Agent 的对照实验。对 build 73 的以下诊断是工程推演：

> [!example] build 73：用下一项观察区分诊断假设
> 一种可能是服务启动较慢，另一种是监听地址/端口与健康探针目标不一致；两者可以同时发生。第 20 至 22 行只显示连接被拒绝、重试耗尽、构建记录服务未就绪并跳过测试，尚未证实任何根因。应按原时间戳对齐三次重试窗口，检查同一进程的启动/就绪时间、实际监听地址和探针目标。首次探测尚未就绪只解释第一次失败；只有到最后一次重试仍未监听，才支持启动时序导致本次测试终止。若进程已在监听但地址或端口与探针目标不同，则支持配置错配；两者都成立时保留共同解释。再次看到 `ECONNREFUSED` 本身仍不能区分它们。

这类诊断用已知日志约束候选原因，再挑新的可核对记录来区分；它不是论文报告的日志实验。与其相关的 ModelSMC 研究搜索并重加权能解释既有数据的候选模型，本身不选择或执行下一项物理实验。工程上也应保留仍相容的多个原因，直到新证据使某些解释不再成立，而不是把最先想到的原因升格成已证实结论。

### 将预测和筛选落到具体任务

> [!example] 文档问答的工具次数预测（合成示例）
> 假设当前文档问答工作流最多调用检索工具 4 次，候选工作流把上限设为 2 次。这个改动只说明可调用次数的上界少了两次；若许多请求在第一次就找到答案，不能据此声称平均费用会少两次调用。可把“长尾成本可能下降”作为待测预测，先排它的实验优先级。两种配置仍要在同一批问题上实际运行，并比较真实费用、证据支持和权限结果；若少调用却漏掉关键条款，就不能仅凭上限较低接受它。

**工程扩展：** 对 build 73，解析器可保留原日志的时间戳和重试状态，再检查连接是否在后续尝试恢复，并验证行号引用；不要因最早出现 `ERROR` 就认定它是最终阻塞失败。只有确认重试耗尽且测试未执行，才将它归入连接失败导致测试未运行。程序检查提供 E0 证据，模型排序仍是预测；候选要在固定任务上实际运行并达到门禁。这个本地设计例子不是 RSI-Anything 论文验证过的等价预测器。

## 改进运行脚手架时如何做对照

Harness² 研究固定基础模型权重，并让每项任务从基础脚手架 H₀ 起步；检索到的前序经验仍可能因任务而异。它开放八种运行时组件供改进：system prompt (系统提示词)、guardrails (防护规则)、memory (记忆)、skills (技能)、tool guidance (工具指引)、scripts (脚本)、subagents (子 Agent) 与 middleware (中间件)。它提出 Propose–Probe–Compose：提出编辑，在配对条件下真正执行候选，比较行为差异，只组合有对照证据支持的变化；再把可复用组件或经验存入改进脚手架，供后续任务检索。经验跨任务怎样被选择并进入当前上下文，见[上下文工程原则](../context/context-engineering-principles.md)。

这里的 Probe 是一次实际运行，仍可能受模型方差、共享评委或随机工具状态影响。在线 Propose–Probe–Compose 阶段没有每题真值答案或可靠 verifier (验证器)；行为差异可提示编辑效果，但本身不认证输出正确。论文仍在实验结束后用 WorkBuddy-Bench、JobBench 和 Harvey Legal Agent Benchmark 的外部基准分数评价结果，因此“在线编辑时无 ground-truth verifier”不等于“没有外部评分准则”。生产实现还应给 Probe 限制外部写入权限和费用，否则实验候选可能造成副作用。实际任务契约仍由[独立任务评估](../evaluation/llm-evaluation-methods.md)验证。

四组 executor–harness 配置里，三个基准各自的最高单步结果分别为：WorkBuddy-Bench 平均得分 +11.5 score points (分数点)，JobBench +4.5 分数点，Harvey LAB Partial criterion pass rate (Partial 评分条目通过率) +11.8 percentage points (百分点)。前两者是基准分数的点数变化，只有最后一项是比例变化；它们是特定模型、基线和任务的单步结果，不是通用 harness 的预期提升。论文还讨论额外执行成本、行为波动以及 editor 与被编辑系统共用模型时的偏差。

**离线建池。** Harness-S 研究的是另一条权重训练路线：先从基础脚手架 `H0` 离线生成 sibling harness pool (兄弟脚手架池)，针对失败修改提示词、skills、上下文、记忆、hooks 或工具视图。局部测试也检查原本成功的任务，以观察是否引入回归；再按多种变体合起来能解决哪些验证任务，选择下一轮编辑的父代。所有有效变体都留在池中，训练开始后 sibling harness 固定。

**在 H0 全失败时重采整组。** 每题先让当前策略在基础脚手架 `H0` 上采样 8 条；至少一条成功就保留这组。只有 8 条都失败时，主配置才由路由器选 8 个不同 sibling，各自从任务初始状态重新运行 1 条轨迹，并以整组救援轨迹替换 `H0` 失败组。路由参考 `H0` 与各 sibling 的配对验证轨迹，按检查点更新校准过的行为档案，再结合任务描述和相似任务结果汇总多份独立的 LLM 排名。论文使用二元奖励，原组全失败意味着 8 条奖励全为 0；救援组中同时有成功和失败，才恢复组内奖励差异。若本地另用分档奖励，则需检查实际分数是否相同，不能只按成功标签判断。

**更新共享权重，再回 H0 验收。** 策略更新时，在同一 harness 条件和生成上下文下比较新旧策略对策略生成 token 的概率；辅助指令和工具观察仍作为条件上下文，但不进入策略 token 的训练损失。因此跨 harness 更新的是一个共享策略模型，离线 sibling 池本身不随训练改变。训练后把策略放回原始 `H0`，在包含新实例的留出任务上评估迁移。这个权重训练分支与 build 73 只改提示词的 B 是不同更新对象。

关键对照 H0-rescue 也在每个全失败任务上从 `H0` 初始状态重采 8 条，并替换旧组；它与 Harness-S 遵循相同的基础采样/救援规则和 40 次更新，便于比较“多试几次”与 sibling 上下文。但触发救援的次数不同，完整实验总 rollout 与 GPU 小时也不同，不能称为总算力匹配。本地对照应写明每题重采样规则、更新数、总采样量与实际成本。论文结果限于其模型、任务、脚手架和预算；在 `H0` 留出新任务及少量外部 harness 上观察到的行为延续，支持的是受限迁移，不证明任意 prompt、tool、memory 修改都能变成通用能力。

## 复用记录说明了什么，又没有说明什么

GitSwarm 在持久且可分支的共享产物仓库中观察 worker 如何引用、访问和组合前序工作。需要分别读三类度量，并把“访问”与“主动复用”区分开：

1. **声明依赖：** worker 在提交中将已有贡献列为 Git parent 或 informed_by 来源；这是可追溯的依赖声明，不是内容复用证明。
2. **轨迹使用：** execution trace 里的 accessed (已访问) 只说明读、搜、比较或打开过产物。actively reused (主动复用) 要求只读材料实际影响后续贡献；可执行产物必须被运行、导入、改编或作为另一计算的输入；自愿产物包还必须引用其提供者。仅仅打开文件不算主动复用。
3. **winner-linked ancestry (胜者关联祖先链)：** 最终选中提交沿 Git parent 和声明的 informed_by 边可达的贡献图覆盖率。它说明声明图上的祖先关系，不证明内容被最终代码实际继承。

设 worker A 把 `probe.sh` 存入共享仓库：worker B 只打开脚本，是“访问”；若 B 实际运行并据结果改写自己的补丁，才有轨迹证据说明它“主动复用”了产物；最后选中的补丁若通过 Git parent 或 `informed_by` 声明链追溯到 B 的贡献，则那项贡献位于“胜者关联祖先链”。反过来，声明引用前序贡献本身也不证明内容被读过或吸收。三种记录分别回答是否声明依赖、是否实际使用、最终解的声明图能否到达该贡献。

GitSwarm 的比例只能说明这些行为在特定基准和仓库设置中被观察到；打开文件不等于使用，声明链不证明内容被最终代码吸收，复用也不证明导致分数提升。研究报告的分母和数字留在章末折叠来源。

## 搜索停滞时，清除什么要由对照回答

*Scaling Discovery Requires Forgetting* 研究在外部评分的开放搜索中保留最佳候选、但清除 session 和候选历史后重启。在 AHC014 的一项对照里，四人团队从同一 plateau 状态继续或重启；每个 agent 都追加 30 个 proposal (候选提案)，重复 3 次。继续运行结果为 +1.4% ±1.3%，每次实验费用 24.67 美元；重启结果为 +9.2% ±6.9%，费用 15.32 美元。这里的收益是三次重复中“最佳新候选相对起始最佳分”的均值 ± 标准差，费用按每次重复计。

这项比较按 proposal 数量匹配，并非按费用、token 或时长匹配；重启还同时改变 session 与候选历史，不能把差异归因于清除某一个记忆源。它支持在某些受限搜索中测试重启，不建立固定重置周期。工程上要事先写下保留的最佳候选、清除的状态、实验预算和继续条件，再用相同起点及真实成本测量两种方案。

Anthropic 的实践文章建议一次只测试一个 subagent (子 Agent) 的合并，比较合并前后的端到端结果并重复运行，并分享何时把工作流合并到主循环的经验。它是特定提供方的工程经验，不是所有任务都该移除子 Agent 的因果定律；结构选择仍需测量。

## 把候选证据变成可恢复的发布版本

候选比较应使用相同任务、输入和执行预算，并保留目前已接受的版本作为基线。凡被用于修改候选、设置阈值或选择胜者的数据都属于开发证据；候选和协议冻结后，再用未参与这些决定的新任务做独立最终验收。最终留出若未过门禁，仍保留旧版；把已查看样本留档并转入开发回归，修订后另备一批独立最终任务，不能反复使用旧集合声称是最终验收。验收还要看任务类别、延迟、费用和外部副作用。指标、抽样、配对统计及发布门禁的完整算例见[大语言模型评估方法](../evaluation/llm-evaluation-methods.md)。

冻结候选和协议时，就记录版本标识、模型与提示词修订、索引和工具版本、任务集版本、评估配置及日志脱敏规则，使通过和未通过的运行都可复核。build 73 的候选若只提升证据格式，却仍把连接失败判成业务断言失败，就没有解决目标问题；若分类改善但工具权限测试回归，也不能接受。端到端结果达到预设门禁后，才将候选标记为已接受版本，登记回滚目标并小流量发布；观察中若不再满足标准，回退到最后接受的组合。

> 下列结果是教学假设，不是本地测量；门禁阈值须由团队按自己的任务、成本和权限要求预先设定。
>
> | 任务切片 | A 的判读 | B 的判读 | B 是否满足质量契约 |

> | 服务已就绪，业务断言实际失败 | 能识别断言失败 | 保留真实断言失败及证据 | 是 |
