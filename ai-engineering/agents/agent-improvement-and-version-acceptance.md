# 如何验证并保留对 Agent 的改进？

## 从 build 73 的误诊开始

> [!example] Build 73：从误诊中提出候选改进
> 发布团队的日志助手收到 build 73 的失败记录。相关三行日志是：
>
> ~~~text
> line 20: connect ECONNREFUSED 127.0.0.1:8081
> line 21: retry 3/3 exhausted
> line 22: integration tests skipped: service did not become ready
> ~~~
>
> 当前版本的助手把连接错误归成“业务断言失败”，还建议回退服务代码。这三行能支持的只是：“连接被拒且重试耗尽，构建日志记载服务未就绪，集成测试被跳过”。它们既不能证明第 22 行与前两行来自同一个就绪探针，也不能证明根因是进程启动慢、监听地址配错或别的原因。工程师想要的是一项能长期保留的改进：助手引用证据，区分观察和推断，根因不清时如实保留不确定性。

在一次对话里纠正结论，只改变这一次运行；要让后续请求也受益，就要留下一个能重放、验收和回滚的系统版本。纳入版本管理的可以是提示词、任务策略、检索配置、工具和模型权重；会被反复复用的经验和相关运行设置，也应写进可复现的配置记录。“Agent（智能体）自我改进”不表示模型在一次对话中自行改写参数。单次运行中的状态变化由[智能体基础](agent-fundamentals.md)说明；本章关注跨运行保留的改动。

把当前已接受的版本记为 A。针对 build 73 的最小候选 B，只在 harness（运行脚手架，即包在模型外面的提示词、工具接入和控制代码）的 system prompt（系统提示词）里加一条规则：把“连接被拒且重试耗尽，构建日志记载服务未就绪并跳过测试”与“业务断言失败”区分开；回答时引用实际日志行，服务为何未就绪不清楚时就说明未知。B 没有改模型、检索索引、工具、输出格式或生成参数。固定这些条件便于归因，但消除不了生成的随机性和外部状态的变化，所以仍要在相同任务上控制运行条件，按预定方案重复评估，见[大语言模型评估方法](../evaluation/llm-evaluation-methods.md)。

在同一批任务上配对比较 A 和 B 时，要分别统计两个方向的结果翻转：A 失败而 B 通过是修复，A 通过而 B 失败是回归。只看平均分之差，两个方向的翻转会互相抵消。凡是用来修改候选、设定阈值或挑选胜者的结果，都算开发证据；锁定候选和验收条件之后，才能打开从未参与这些决定的最终留出任务（held-out task）。下图是这一流程的全貌。

进入候选搜索前，先按授权核对助手实际读取的日志版本和输出，确认错误行为发生在“把连接问题分类为业务断言失败”，并把服务为何未就绪留作未知。Build 73 可用来修改分类与证据表达规则。低成本的开发筛查可以检查引用行是否存在、结论是否超出原始日志支持范围、未知根因是否被误写为定论。筛查失败的候选记录理由并淘汰。筛查通过只表示它可进入完整开发集，这些案例和检查条件都参与了候选形成，仍属于开发证据。

## 先说清楚哪个对象会改变

同一个失败可以由不同层面修复。改变其中一层时，其余条件先保持不变，才能知道结果来自哪里。

| 改变对象 | 在 build 73 中的候选改动 | 需要验证什么 |
|---|---|---|
| harness 中的提示词组件 | 只增加规则：报告连接被拒、重试耗尽、构建日志记载服务未就绪和测试跳过；不把它们写成已证实的因果关系。 | 分类、引用和不确定性是否符合任务契约；难例是否仍能正确拒答。 |
| 优化阶段的候选排序预测器 | 估算候选提示词或检索设置在哪些任务上更值得先测，以减少搜索成本。 | 是否减少实际搜索成本；排序选中的候选在真实执行中是否有收益。预测分本身不是收益。 |
| 部署路径中的决策预测器 | 例如决定先查哪类证据、是否转交工具或是否升级人工。 | 作为运行系统的一部分，与检索、工具和界面组合验收其端到端影响；离线校准不能代替部署结果。 |
| 其他 harness 组件 | 增加日志检索、引用校验和结构化输出验证。 | 证据是否完整、验证器能否拦截格式错误，以及成本和故障路径是否可接受。 |
| 基础模型权重 | 对经筛选的样本进行 supervised fine-tuning (SFT，监督微调) 或奖励训练。 | 训练信号、数据切分和更新是否值得；训练奖励本身不是新题泛化证据。 |

Build 73 的候选 B 只改 harness 里的提示词，不改模型权重，也不动其他运行组件。如果改的是优化阶段的候选排序器和提示词生成策略，要先比较这套搜索流程能否在同等预算下找到更好的候选，再单独验收最终要部署的提示词。只有预测器也参与线上动作决策时，才把它纳入部署版本一起验收。如果一次同时改提示词、索引、工具和模型，指标变化就无法归因。权重训练改的是另一类对象，其过程和目标见[微调策略](../fine-tuning/fine-tuning-strategies.md)和[奖励驱动的推理训练](../fine-tuning/reward-based-reasoning-training.md)；本章仍负责版本化候选及其接受证据。

## 从哪些样本和轨迹中学

Build 73 已经过人工核对，但它是用来改出候选 B 的开发样例；即使它的 trace（追踪记录）被收进数据集，也不能拿来当最终验收题。对新的线上点踩或纠正，要先经授权读取原始日志、确认当时的版本并核对对应日志行，再把它标成开发案例。trace 记录了实际输入的证据和输出，但分类是否正确，要由审阅者对照同一版本的来源核验，trace 本身证明不了。生产信号如何审查、怎样从其中形成可复核案例，见[生产可观测性与反馈](../systems/ai-production-observability-and-feedback.md)；样本是否代表目标任务及最终留出如何隔离，见[大语言模型评估方法](../evaluation/llm-evaluation-methods.md)。

## 把候选证据变成可恢复的发布版本

候选比较应使用相同任务、输入和执行预算，并保留目前已接受的版本作为基线。凡被用于修改候选、设置阈值或选择胜者的数据都属于开发证据；候选和协议冻结后，再用未参与这些决定的新任务做独立最终验收。最终留出若未过门禁，仍保留旧版；把已查看样本留档并转入开发回归，修订后另备一批独立最终任务，不能反复使用旧集合声称是最终验收。验收还要看任务类别、延迟、费用和外部副作用。指标、抽样、配对统计及发布门禁的完整算例见[大语言模型评估方法](../evaluation/llm-evaluation-methods.md)。

冻结候选和协议时，就记录版本标识、模型与提示词修订、索引和工具版本、任务集版本、评估配置、参与运行的经验/记忆快照或版本引用，以及日志脱敏规则，使通过和未通过的运行都可复核。Build 73 的候选若仍把连接拒绝报成业务断言失败，就没有解决目标问题；若分类改善但工具权限测试回归，也不能接受。端到端结果达到预设门禁后，才将候选标记为已接受版本，登记回滚目标并小流量发布；观察中若触发预设回滚条件，回退到已登记的上一接受组合 A。

搜索前还要写明候选修改次数、每个候选的运行次数、模型与工具调用或实际费用上限、最长运行时限和检查点。Google Cloud 的 AlphaEvolve 最佳实践以约 100 个程序评估起步，困难任务可扩展到数千。约 1,500 次候选程序评估仍看不到清晰趋势时，指南建议暂停复核问题定义或软惩罚，同时提醒困难搜索可能在长平台期后出现突破。Infrathon v2 的 150 次长运行中有 135 次在预算后半段刷新最佳成绩，模型排序也随任务和预算变化。这两项研究面向程序和 AI 基础设施优化，可作为预算设计的参照。日志助手的候选上限应按自身风险与费用预定。无进展检查点触发对任务定义、评分稳定性和候选多样性的复核。候选给出无证据根因或导致关键任务回归时，就淘汰这一版。若发生预先约定的全局停止事件，例如评估环境已被污染，或预算耗尽且门禁未通过，则结束整轮搜索，继续使用 A。

候选锁定后，要由独立审阅者按同版本原始日志核对预先抽取的新题、证据引用和任务标签，并裁定重要分歧。Co-Scientist v2 把自动评价、领域专家评价、科学家反馈和外部验证放在不同环节。Anthropic 关于黑洞物理的文章报告 Lean 形式化和物理学家检查主要结果。其链接的 modular bootstrap 论文源码页列出 TeX 主文件与图件，没有列出 Lean 文件。因此，形式化覆盖的命题和物理假设之间的对应关系仍需人工审查。对 Build 73，行号和 schema 检查可以核对引用与结构。独立标签仍需评审者依据原始材料核验未参与候选调整和选择的新题。候选能否放量再由预设的质量、服务和成本门槛决定。

## 研究如何产生改进信号

上一节说明了候选怎样被验收；本节看研究中的候选从哪里来。GEPA 是一种提示词优化方法：让模型反思执行轨迹，据此逐版改写提示词。GEPA-Curator 论文在此基础上用逐题轨迹挑选下一批训练任务，分工如下：

- 执行 Agent（智能体）跑题并产出轨迹，评估器记录结果。
- 任务筛选器（Curator）挑出值得再试的任务；对反复稳定成功、受环境限制或评分不稳定的任务，会暂时跳过，之后再检查。某道训练任务失败时，Curator 还会在同一任务的历史记录中找一条结果较一致的成功轨迹，交给反思器（Reflector）对照；找不到合适的例子就不提供。
- 反思器根据这些材料提出新的提示词候选。Curator 和 Reflector 由同一个优化模型担任；Curator 不决定最终保留哪个提示词，也不更新模型权重。

历史成功是一条可以回查的线索。如果任务状态由程序记录，可以核对当时实际产生的结果。如果成功只靠模型评审，两次一致的判决也可能有同一种偏差。v2 的实验还说明，挑选更有信息量的任务本身有成本。以 WebArena 的四个网站为例，论文估算 GEPA 的一次训练与验证合计约 594 美元，加上 Curator 的效率优化版本约 777 美元，均未计最终测试和网站托管。应用应记录筛题、反思和实际执行的全部开销，再判断提高的正确率是否值得。

把这一思路用到 build 73，属于工程推演：如果同一开发任务既有可靠的成功轨迹也有失败轨迹，候选作者可以比较两次运行是否看到了同一行证据、各自怎样判读；只有一次失败记录时，不要编造成功对照。候选提示词仍须在完整的开发任务集上实际运行。还要注意论文的选版方式：提示词逐版迭代，定期在验证集上评分，最后选验证分最高的一版，并不是每次改动都过一道独立门禁；最终留出测试不参与选择。按本章的划分，验证集既然反复参与选版，就属于开发证据，不能再充当最终的独立验收。

另一类研究改的是训练用的题目，而不是提示词，因此它不是候选 B 的一部分。A-RSI v1 研究多模态模型在没有人工标注数据时的自我改进：模型在一个预先生成的任务池上做强化学习训练，论文用训练日志决定何时换到下一个任务池。

它读取的关键信号记为 `U`。`U` 不是奖励总和，也不是答对题数：论文每题采样 8 个回答，用每个回答的总奖励减去同题 8 个回答的平均奖励，再按组内尺度归一化，得到 advantage（优势）。例如奖励为 `[1,0,0,0,0,0,0,0]` 时，组内优势不全为零，这道题给 `U` 加 1；8 个奖励全相同时优势全为零，不计入 `U`。也就是说，`U` 统计的是还能提供学习信号的不同题目数（非零按数值容差判断）；格式奖励和停止奖励也会影响计数。

换池规则是：同一池已累计至少三个通过训练健康检查的连续窗口后，比较当前窗口与两个窗口之前的信号；若 `U` 降到先前值的 85% 或以下，或记录的正确率上升至少 10 个百分点，就刷新任务池。在论文的 Qwen3-VL-8B-Instruct 设置里，同池 `U` 从 239 降到 195（`195/239 ≈ 0.816`），触发换到一个 400 题的新池；同期正确率只提高 7 个百分点，没有触发另一条件。换池后策略权重继续训练，不从头开始。论文还发现四个模型对“自己会不会答错”的自评 ROC 曲线下面积（AUC）约 0.50，几乎不能据此排序哪些题会答错，因此控制器读取训练日志而不依赖模型自评。这个信号负责训练时机，不是发布门禁；无论任务池刷新触发器还是模型预测分，都不能单独决定候选上线。优化器/学习率调度器如何处理见章末折叠来源。

在训练进度相同的第六个窗口上，新池方案的 Macro11（11 个基准准确率的等权平均，每题最多输出 8,192 个 token）为 60.40%，继续旧池为 58.35%，差值为 2.05 个百分点；每个策略臂各一次训练，且该结果不能隔离换题、刷新时机与池规模从 500 变为 400 题的作用。作者还指出完成/截断变化参与了得分差异，因此不能把增益全归于推理能力。诊断用留出任务不进入训练题库（reservoir），任务家族比例仍参考评估基准元数据。没有固定在三窗换题的随机刷新对照，不能据此断言自适应时机优于固定时机，也不能把换题当所有训练任务的规则。迁移到 build 73 的提示词候选时，不会更新权重或产生同类组内优势；本地应按开发轨迹定义选样信号，不能照搬论文阈值，最终仍由未参与选择的任务结果决定是否保留。

真实任务反馈也是检查“自我改写”是否有效的必要信号。一项涵盖六个模型、三个基准的研究报告，SkillsBench 技能经 30 轮无任务反馈重写后，平均通过率下降 14.6 个百分点。SkillDiff 保留技能正文，只标记十份模型自写技能都没有覆盖的内容，在同批 SkillsBench 评估中平均提高 4.8 个百分点。论文里的“prior”是按主题让模型自写十份技能形成的操作性参照。用于 Build 73 时，提示词的反复改写只能提出候选，是否保留仍由来源核对和新任务结果决定。

FunSearch 与 AlphaEvolve 展示了候选程序可以交给可执行评估器筛选和排序。FunSearch 把预训练模型与系统评估器组成进化搜索，8 维 cap-set 问题中规模为 512 的构造只在 140 次实验中的 4 次找到。AlphaEvolve 的程序库兼顾高分与多样性，提示采样器会选一个待改的父程序，并可加入其他高分程序作灵感。模型生成的代码差分应用到父程序后，候选先过小规模检查，再按由易到难的评估级联逐层测试，只有达到前序门槛的才进入更重测试，评估结果会写回程序库供后续采样。此类搜索要求目标可由自动评估器检验。权限和正确性等不能由性能分补偿的硬约束应作为独立淘汰门。Build 73 的行号、结构和权限检查可以廉价淘汰明显违约候选，语义正确性则仍要依据独立任务标签判断。

## 预测可以省实验，但必须让结果闭环

上面的信号决定训练或搜索的时机；还有一些递归自我改进系统先用预测挑出值得实测的候选。这能降低昂贵试验的搜索成本，但带来了“预测错了”的风险。所以要先固定 task contract（任务契约）：输入输出、限制、可用预算、程序检查器、成功定义和停止条件，再记录每个候选的证据来自哪里。RSI-Anything 论文按信息来源把证据分为四类，如下表；它们不是固定的质量排序，也不要求所有领域采用同一标准：

| 来源 | 代表什么 | 何时仍需外部检查 |
|---|---|---|
| E0：确定性规则或程序检查 | verifier (可执行验证器)、单测、形式化条件等可以直接执行的判据；锁定测试上执行候选后的判定结果也是任务证据。 | 检查器是否覆盖真实任务，以及是否能被候选投机利用。 |
| E1：学习型预测或 rollout (模型展开轨迹) | 模型对结果或未来状态的估计；这里的 rollout 是模拟未来，不是实际执行。 | 预测不是结果；选中候选仍要实测。 |
| E2：模拟器或高保真模型 | 候选在模拟环境中的实际状态转移与任务测量，是该模拟环境范围内的结果证据。 | 仿真与实际环境存在差异时要做外部校验。 |
| E3：外部测量 | 真实任务、硬件、用户或实验系统中的观察结果。 | 仍需控制变量、预算和测量噪声。 |

RSI-Anything v1 的 world model (世界模型) 根据候选动作预测下一状态，再由领域 readout (读出函数) 把预测转成任务结果或其概率分布，并据此排列候选的实测优先级。预测只是选择下一项实验的依据；程序题要在锁定测试上运行实际候选，模拟题的仿真结果只能支持其环境范围内的判断，线上任务则要观察实际工作流。模型自评分或世界模型预测即使看似很高，也只可用于排序待测候选，不能作为发布结论；候选要经门禁数据和未参与选择的留出审计实际执行。其潜在表示结构的 OPF 细节留在章末来源供查阅。

论文将 update data (候选更新数据) 用于构造候选版本，gate data (保留门禁数据) 用于选择保留版本；指定的 held-out audit set (留出审计集) 只留作最终结果报告。逐一比较策略或预测器时，每次只替换一项、另一项仍用当前版本；若单组件门禁失败就保留该组件的当前已接受版本。若至少一项改变，再把新组件组合与当前 policy–model pair（策略–模型组合）配对比较，组合门禁失败则保留原有已接受的策略–模型组合。这里的论文协议不取代本地发布流程中另留未参与调参或筛选的新题作独立验收。

### 多种根因可以共存；下一项观测要让它们作出不同预测

上一节的预测器用来给候选排序；诊断单个失败时，同样要避免过早认定一个原因。Anthropic 的文章 *Teaching AI to Build Scientific Models* 把建模过程概括为 build（构造模型结构）、constrain（在给定结构下用已有观察约束可调参数）和 interpret（比较仍成立的解释，并思考哪项观察能区分它们）。这篇文章说明研究方向，不是对日志 Agent 的对照实验。对 build 73 的以下诊断是工程推演：

> [!example] build 73：用下一项观察区分诊断假设
> 一种可能是服务在重试窗口结束后才开始监听目标端点。另一种可能是服务当时已在其他端口监听，构建请求仍指向原端口。两种情况也可能同时发生。第 20 至 22 行只显示连接被拒绝、重试耗尽、构建日志记载服务未就绪并跳过测试，根因仍未知。先核实三次连接尝试属于同一构建步骤和同一轮就绪探针，再按原时间戳对齐该重试窗口与同一进程在相同网络命名空间中的就绪/监听事件、实际端点与调用目标，并检查中间是否存在端口映射。若同一命名空间内的监听记录显示目标端点在该重试窗口结束后才开始监听，可记录“目标端点在窗口内尚未开始监听”，并将其原因保留为未知。若进程在窗口内已监听另一端点且不存在映射，则支持端点目标不匹配。`ECONNREFUSED` 与上述两种情况均相容。

## 改进运行脚手架时如何做对照

前面的候选 B 只改了 harness 里的一条提示词；Harness² 研究的是自动、反复地改进整个 harness。它固定基础模型权重，每项任务都从基础脚手架 `H0` 起步；检索到的前序经验仍可能因任务而异。它开放八种运行时组件供改进：system prompt (系统提示词)、guardrails (防护规则)、memory (记忆)、skills (技能)、tool guidance (工具指引)、scripts (脚本)、subagents (子智能体) 与 middleware (中间件)。它提出 Propose–Probe–Compose（提出–探测–组合）：提出编辑，在配对条件下真正执行候选，比较行为差异，只组合有对照证据支持的变化；再把可复用组件或经验存入改进脚手架，供后续任务检索。经验跨任务怎样被选择并进入当前上下文，见[上下文工程原则](../context/context-engineering-principles.md)。

这里的 Probe 是一次实际运行，仍可能受模型方差、共享评委或随机工具状态影响。在线 Propose–Probe–Compose 阶段没有每题真值答案或可靠 verifier (验证器)；行为差异可提示编辑效果，但本身不认证输出正确。论文仍在实验结束后用 WorkBuddy-Bench、JobBench 和 Harvey Legal Agent Benchmark 的外部基准分数评价结果，因此“在线编辑时无 ground-truth verifier”不等于“没有外部评分准则”。生产实现还应给 Probe 限制外部写入权限和费用，否则实验候选可能造成副作用。实际任务契约仍由[独立任务评估](../evaluation/llm-evaluation-methods.md)验证。

四组执行器–运行脚手架（executor–harness）配置里，三个基准各自的最高单步结果分别为：WorkBuddy-Bench 平均得分 +11.5 score points (分数点)，JobBench +4.5 分数点，Harvey LAB Partial criterion pass rate (Partial 评分条目通过率) +11.8 percentage points (百分点)。前两者是基准分数的点数变化，只有最后一项是比例变化；它们是特定模型、基线和任务的单步结果，不是通用 harness 的预期提升。论文还讨论额外执行成本、行为波动以及编辑器（editor）与被编辑系统共用模型时的偏差。

**权重训练分支（Harness-S）。** Harness-S 针对基础脚手架 `H0` 上 8 次采样全部失败的任务，改用兄弟脚手架生成救援轨迹并训练共享策略。比较时要有按同样规则从 `H0` 重采 8 次的基线，训练结束后回到原始 `H0`，用包含新实例的留出任务验收。该分支改的是共享策略权重，不是 build 73 只改提示词的候选 B；论文在 H0 留出任务和少量外部 harness 上观察到受限迁移，不证明任意 prompt、tool 或 memory 修改都能变成通用能力。

> [!info]- Harness-S 的采样、路由和成本细节
> 离线先从 `H0` 生成兄弟脚手架池，针对失败修改提示词、技能、上下文、记忆、钩子或工具视图；局部测试同时检查原本成功的任务，观察回归，再按变体覆盖的验证任务选择编辑父代。训练开始后固定有效变体池。
>
> 每题先由当前策略在 `H0` 采样 8 条；至少一条成功就保留原 8 条整组。只有 8 条全失败时，主配置才路由到 8 个不同 sibling，各从任务初始状态运行 1 条轨迹，并以救援轨迹组替换失败组。论文使用二元奖励；若本地使用分档奖励，不能只按成功标签推断组内奖励差异是否恢复。路由基于 `H0` 与 sibling 的配对验证轨迹、检查点行为档案、任务描述及相似任务结果汇总的 LLM 排名。
>
> 更新时在同一脚手架和生成上下文下比较新旧共享策略对策略生成词元的概率；辅助指令和工具观察是条件上下文，不进入策略词元的训练损失。H0-rescue 对照也在全失败时从 `H0` 初始状态重采 8 条并替换旧组，两组均做 40 次更新；但救援触发次数不同，完整 rollout 与 GPU 小时不匹配，故须报告总采样量和实际成本，不能称为总算力匹配。

## 复用记录说明了什么，又没有说明什么

GitSwarm 在持久且可分支的共享产物仓库中观察 worker 如何引用、访问和组合前序工作。需要分别读三类度量，并把“访问”与“主动复用”区分开：

1. **声明依赖：** worker 在提交中将已有贡献列为 Git parent 或 informed_by 来源；这是可追溯的依赖声明，不是内容复用证明。
2. **轨迹使用：** execution trace 里的 accessed (已访问) 只说明读、搜、比较或打开过产物。actively reused (主动复用) 要求只读材料实际影响后续贡献；可执行产物必须被运行、导入、改编或作为另一计算的输入；自愿产物包还必须引用其提供者。仅仅打开文件不算主动复用。
3. **winner-linked ancestry (胜者关联祖先链)：** 最终选中提交沿 Git parent 和声明的 informed_by 边可达的贡献图覆盖率。它说明声明图上的祖先关系，不证明内容被最终代码实际继承。

设 worker A 把 `probe.sh` 存入共享仓库：worker B 只打开脚本，是“访问”；若 B 实际运行并据结果改写自己的补丁，才有轨迹证据说明它“主动复用”了产物；最后选中的补丁若通过 Git parent 或 `informed_by` 声明链追溯到 B 的贡献，则那项贡献位于“胜者关联祖先链”。反过来，声明引用前序贡献本身也不证明内容被读过或吸收。三种记录分别回答是否声明依赖、是否实际使用、最终解的声明图能否到达该贡献。

GitSwarm 的比例只能说明这些行为在特定基准和仓库设置中被观察到；打开文件不等于使用，声明链不证明内容被最终代码吸收，复用也不证明导致分数提升。研究报告的分母和数字留在章末折叠来源。

## 搜索停滞时，清除什么要由对照回答

*Scaling Discovery Requires Forgetting* 研究在外部评分的开放搜索中保留最佳候选、但清除 session 和候选历史后重启。在 AHC014（一道 AtCoder 启发式编程赛题）的一项对照里，由 4 个 agent 组成的团队从同一个停滞（plateau）状态出发，分别继续运行或重启；每个实验臂由 4 个 agent 各追加 30 个 proposal (候选提案)，即每次重复每臂 120 个提案；共重复 3 次。继续运行结果为 +1.4% ±1.3%，每次实验费用 24.67 美元；重启结果为 +9.2% ±6.9%，费用 15.32 美元。收益分别是三次重复中“最佳新候选相对起始最佳分”的均值 ± 标准差；两臂均值相差 7.8 个百分点，费用相差 9.35 美元/次。论文没有给出由这三个重复计算的配对差分布。

这项比较按候选提案（proposal）数量匹配，并非按费用、词元（token）或时长匹配；重启还同时改变对话会话（session）与候选历史，不能把差异归因于清除某一个记忆源。它支持在某些受限搜索中测试重启，不建立固定重置周期。工程上要事先写下保留的最佳候选、清除的状态、实验预算和继续条件，再用相同起点及真实成本测量两种方案。

Anthropic 的实践文章建议一次只测试一个 subagent (子 Agent) 的合并，比较合并前后的端到端结果并重复运行，并分享何时把工作流合并到主循环的经验。它是特定提供方的工程经验，不是所有任务都该移除子 Agent 的因果定律；结构选择仍需测量。
