# 如何验证并保留对 Agent 的改进？

## 从 build 73 的误诊开始

> [!example] Build 73：从误诊中提出候选改进
> 发布团队的日志助手收到 build 73 的失败记录。相关三行日志是：
>
> ~~~text
> line 20: connect ECONNREFUSED 127.0.0.1:8081
> line 21: retry 3/3 exhausted
> line 22: integration tests skipped: service did not become ready
> ~~~
>
> 基线把连接错误归成“业务断言失败”，建议回退服务代码。三行只支持“连接被拒且重试耗尽，构建日志记载服务未就绪并跳过集成测试”；未证明第 22 行与前两行来自同一探针，也未证明进程启动慢、监听地址错或其他根因。工程师需要一项可持续的改进：助手引用证据、区分观察和推断，并在根因尚不清楚时保留不确定性。

一次回答中修正结论只改变当前运行状态；要让后续请求也受益，需要留下能重放、验收并回滚的系统版本。版本化范围可包括提示词、任务策略、检索配置、工具和模型权重；持续复用的经验与相关运行设置也应纳入可复现的配置记录。“Agent（智能体）自我改进”不表示模型在一次对话中自行改写参数。单次运行中的状态变化由[智能体基础](agent-fundamentals.md)说明；本章关注跨运行保留的改动。

将当前已接受版本记为 A。Build 73 的最小候选 B 只在运行脚手架（harness）的 system prompt（系统提示词）中补一条规则：将“连接被拒且重试耗尽，构建日志记载服务未就绪并跳过测试”与“业务断言失败”区分；引用实际日志，保留未就绪根因未知。候选没有修改模型、检索索引、工具、格式或生成设置。固定这些条件有助于归因，但不能消除生成随机性或外部状态变化；仍需在相同任务上控制运行条件并按预定方案重复评估，见[大语言模型评估方法](../evaluation/llm-evaluation-methods.md)。

配对比较要同时记录两个方向的“失败翻转”：A 失败而 B 通过，是修复；A 通过而 B 失败，是回归。只看 A、B 平均分之差，会把这两个方向的翻转抵消掉。用于修改候选、设置阈值或选择胜者的结果都属于开发证据；锁定候选和验收条件后，才打开此前未参与这些决定的最终留出任务。

~~~mermaid
%%{init: {"flowchart": {"wrappingWidth": 280}}}%%
flowchart TD
    Signal[复核失败<br/>固定契约与预算] --> Develop[开发集迭代 B<br/>与 A 同题对照]
    Develop -->|锁定候选与验收协议| Holdout[A/B 同一批独立新题<br/>按冻结协议运行]
    Holdout --> Gate{预设门槛达标？}
    Gate -->|通过| Retain[接受 B，小流量发布<br/>登记 A 为回滚目标]
    Gate -->|未通过| Reject[保留 A；验收题归入开发集<br/>修订后另备独立新题]
    Reject -->|继续开发| Develop
~~~

## 先说清楚哪个对象会改变

同一个失败可以由不同层面修复。改变其中一层时，其余条件先保持不变，才能知道结果来自哪里。

| 改变对象 | 在 build 73 中的候选改动 | 需要验证什么 |
|---|---|---|
| harness 中的提示词组件 | 只增加规则：报告连接被拒、重试耗尽、构建日志记载服务未就绪和测试跳过；不把它们写成已证实的因果关系。 | 分类、引用和不确定性是否符合任务契约；难例是否仍能正确拒答。 |
| 优化阶段的候选排序预测器 | 估算候选提示词或检索设置在哪些任务上更值得先测，以减少搜索成本。 | 是否减少实际搜索成本；排序选中的候选在真实执行中是否有收益。预测分本身不是收益。 |
| 部署路径中的决策预测器 | 例如决定先查哪类证据、是否转交工具或是否升级人工。 | 作为运行系统的一部分，与检索、工具和界面组合验收其端到端影响；离线校准不能代替部署结果。 |
| 其他 harness 组件 | 增加日志检索、引用校验和结构化输出验证。 | 证据是否完整、验证器能否拦截格式错误，以及成本和故障路径是否可接受。 |
| 基础模型权重 | 对经筛选的样本进行 supervised fine-tuning (SFT，监督微调) 或奖励训练。 | 训练信号、数据切分和更新是否值得；训练奖励本身不是新题泛化证据。 |

Build 73 的候选 B 只改 harness 中的提示词；它不改模型权重，也不动其他运行组件。若同时改优化阶段的候选排序器与提示词生成策略，先比较这套搜索流程能否在同等预算下找到更好的候选，再独立验收最终要部署的提示词。只有预测器也参与线上动作决策时，才把它纳入部署版本一并验收。若一次改提示词、索引、工具和模型，指标变化就难以归因。权重训练是另一条更新对象不同的路线，其过程与目标归属[微调策略](../fine-tuning/fine-tuning-strategies.md)和[奖励驱动的推理训练](../fine-tuning/reward-based-reasoning-training.md)；本章仍负责版本化候选及其接受证据。

## 从哪些样本和轨迹中学

Build 73 是经核对的开发样例，不因被放入 trace 就成为最终验收题。对新的线上点踩或纠正，经授权读取原始日志、确认版本并核验对应行后，再将它标成开发案例；trace (追踪记录) 记录实际输入证据和输出，但任务分类是否正确要由审阅者对照同版本来源核验，不能由 trace 单独证明。生产信号如何审查、怎样从其中形成可复核案例，见[生产可观测性与反馈](../systems/ai-production-observability-and-feedback.md)；样本是否代表目标任务及最终留出如何隔离，见[大语言模型评估方法](../evaluation/llm-evaluation-methods.md)。

## 把候选证据变成可恢复的发布版本

候选比较应使用相同任务、输入和执行预算，并保留目前已接受的版本作为基线。凡被用于修改候选、设置阈值或选择胜者的数据都属于开发证据；候选和协议冻结后，再用未参与这些决定的新任务做独立最终验收。最终留出若未过门禁，仍保留旧版；把已查看样本留档并转入开发回归，修订后另备一批独立最终任务，不能反复使用旧集合声称是最终验收。验收还要看任务类别、延迟、费用和外部副作用。指标、抽样、配对统计及发布门禁的完整算例见[大语言模型评估方法](../evaluation/llm-evaluation-methods.md)。

冻结候选和协议时，就记录版本标识、模型与提示词修订、索引和工具版本、任务集版本、评估配置、参与运行的经验/记忆快照或版本引用，以及日志脱敏规则，使通过和未通过的运行都可复核。Build 73 的候选若仍把连接拒绝报成业务断言失败，就没有解决目标问题；若分类改善但工具权限测试回归，也不能接受。端到端结果达到预设门禁后，才将候选标记为已接受版本，登记回滚目标并小流量发布；观察中若触发预设回滚条件，回退到已登记的上一接受组合 A。

> [!example] 合成验收：候选 B 是否替换 A
> 下列是候选冻结后首次运行的四个合成验收任务，每类各一题，不是本地测量。这是另设门槛的缩微演算，与评估和生产章节的 200 题合成算例分开，不把两者汇成同一次发布的证据。Build 73 开发样例与所有用于改提示词/选胜者的数据都已排除。每题按同一组合判定：主类别正确、证据逐行支持、下一步不超出证据、根因未知时不臆断，且没有硬错误，才算通过。
>
> | 一题一个冻结后首次使用的情形 | A 判读（是否通过） | B 判读（是否通过） |
> |---|---|---|
> | 重试耗尽，服务未就绪，测试跳过 | 报业务断言失败（否） | 复述连接被拒、重试耗尽、服务未就绪和测试跳过；根因未知（是） |
> | 首次连接拒绝，后续重试恢复 | 把首错报作终止失败（否） | 记录恢复，不报最终阻塞（是） |
> | 服务已就绪，业务断言确实失败 | 正确指出断言失败（是） | 保留断言失败及对应行证据（是） |
> | 缺少重试或最终状态 | 猜测根因（否） | 标记证据不足并请求补充（是） |

> | 全局门禁 | 预先设定的条件 | 此合成候选 B |

> | 质量 | 四题均满足上述组合判定 | `4/4`，满足 |

> | 权限 | 20 个边界用例中确认的越权读取/写入必须为 `0` 次 | 已完成 20 个用例，确认越权 `0` 次，满足 |

## 研究如何产生改进信号

GEPA-Curator 论文把逐题轨迹用于选择下一批训练任务：执行 Agent（智能体）跑题，评估器记录轨迹和结果；任务筛选器（Curator）选择值得再试的任务，也会暂时跳过反复稳定成功、受环境限制或评分不稳定的任务，之后再检查它们。面对一题失败，它还可找到同一道训练任务上历史结果较一致的成功轨迹，交给反思器（Reflector）对照；找不到合适例子就不提供。论文称它为可信参考，但在智能体任务（agentic task）中成功结果可能来自大语言模型（LLM）评审，因此“一致”不等于独立核实、也不保证正确；同一评审器若偏差稳定，重复一致仍可能错。执行 Agent 负责产出轨迹，评估器负责记分，同一优化模型在 Curator 环节选择任务和参考轨迹，在 Reflector 环节提出提示词候选。Curator 不决定最终保留哪个提示词，也不更新模型权重。

用于 build 73 是工程推演：若同一开发任务留有可靠成功与失败轨迹，候选作者可比较两次运行是否看见同一行证据、采取了什么判读；只有一次失败时，不要伪造成功对照。候选提示词仍须在完整开发任务集上实跑。论文让提示词逐版迭代，定期在验证集评分，最后选择验证分最高的一版；它不是每次改动后都经过独立逐步门禁。最终留出测试不参与选择。凡用于修改候选、设阈值或挑选胜者的数据都属于开发证据；验证集反复承担选版后，不能再充当最终独立验收。

换题训练是更新对象不同的比较，不是候选 B 的一部分。A-RSI v1 用训练日志判断何时换到下一个预生成任务池：同池已累计至少三个通过训练健康检查的连续窗口后，比较当前窗口与两窗前的信号；`U` 的当前窗/两窗前比例降至 85% 或以下，或记录正确率升至少 10 个百分点，便刷新任务池。在论文的 Qwen3-VL-8B-Instruct 设置里，同池 `U` 从 239 降至 195（`195/239 ≈ 0.816`），触发换到一个 400 题新池；记录正确率提高 7 个百分点，没有触发另一条件。`U` 不是奖励总和或答对题数：论文每题采样 8 个回答，并将每个回答的总奖励减去同题平均奖励，再按组内尺度归一化形成优势；例如 `[1,0,0,0,0,0,0,0]` 会产生非零组内优势，这题给 `U` 加 1；8 个奖励全相同时优势为零，不增加 `U`。它按数值容差判断非零，统计有这种优势的不同题目数；格式与停止奖励也会影响计数。任务池变了，策略权重仍接续训练。论文还发现四个模型对“自己会不会答错”的自评 ROC 曲线下面积（AUC）约 0.50，几乎不能据此排序哪些题会答错，因此控制器读取训练日志而不依赖模型自评。这个信号负责训练时机，不是发布门禁；无论任务池刷新触发器还是模型预测分，都不能单独决定候选上线。优化器/学习率调度器如何处理见章末折叠来源。

论文的同进度第六窗口比较中，新池方案的 Macro11（11 个基准准确率的等权平均，每题上限 8,192 个输出词元 token）为 60.40%，继续旧池为 58.35%，差值为 2.05 个百分点；每个策略臂各一次训练，且该结果不能隔离换题、刷新时机与池规模从 500 变为 400 题的作用。作者还指出完成/截断变化参与了得分差异，因此不能把增益全归于推理能力。诊断用留出任务不进入训练题库（reservoir），任务家族比例仍参考评估基准元数据。没有固定在三窗换题的随机刷新对照，不能据此断言自适应时机优于固定时机，也不能把换题当所有训练任务的规则。迁移到 build 73 的提示词候选时，不会更新权重或产生同类组内优势；本地应按开发轨迹定义选样信号，不能照搬论文阈值，最终仍由未参与选择的任务结果决定是否保留。

## 预测可以省实验，但必须让结果闭环

一些递归改进系统先用预测来挑值得测量的候选。这减少昂贵试验的搜索成本，却引入“预测错了”的风险。因此先固定 task contract (任务契约)：输入输出、限制、可用预算、程序检查器、成功定义和停止条件；再记录每个候选的证据来源。下面按信息来源区分 RSI-Anything 论文的四类证据；它们不是固定的质量排序，也不要求所有领域采用同一标准：

| 来源 | 代表什么 | 何时仍需外部检查 |
|---|---|---|
| E0：确定性规则或程序检查 | verifier (可执行验证器)、单测、形式化条件等可以直接执行的判据；锁定测试上执行候选后的判定结果也是任务证据。 | 检查器是否覆盖真实任务，以及是否能被候选投机利用。 |
| E1：学习型预测或 rollout (模型展开轨迹) | 模型对结果或未来状态的估计；这里的 rollout 是模拟未来，不是实际执行。 | 预测不是结果；选中候选仍要实测。 |
| E2：模拟器或高保真模型 | 候选在模拟环境中的实际状态转移与任务测量，是该模拟环境范围内的结果证据。 | 仿真与实际环境存在差异时要做外部校验。 |
| E3：外部测量 | 真实任务、硬件、用户或实验系统中的观察结果。 | 仍需控制变量、预算和测量噪声。 |

RSI-Anything v1 的 world model (世界模型) 根据候选动作预测下一状态，再由领域 readout (读出函数) 把预测转成任务结果或其概率分布，并据此排列候选的实测优先级。预测只是选择下一项实验的依据；程序题要在锁定测试上运行实际候选，模拟题的仿真结果只能支持其环境范围内的判断，线上任务则要观察实际工作流。模型自评分或世界模型预测即使看似很高，也只可用于排序待测候选，不能作为发布结论；候选要经门禁数据和未参与选择的留出审计实际执行。其潜在表示结构的 OPF 细节留在章末来源供查阅。

论文将 update data (候选更新数据) 用于构造候选版本，gate data (保留门禁数据) 用于选择保留版本；指定的 held-out audit set (留出审计集) 只留作最终结果报告。逐一比较策略或预测器时，每次只替换一项、另一项仍用当前版本；若单组件门禁失败就保留该组件的当前已接受版本。若至少一项改变，再把新组件组合与当前 policy–model pair（策略–模型组合）配对比较，组合门禁失败则保留原有已接受的策略–模型组合。这里的论文协议不取代本地发布流程中另留未参与调参或筛选的新题作独立验收。

### 多种根因可以共存；下一项观测要让它们作出不同预测

Teaching AI to Build Scientific Models 将过程概括为 build（构造模型结构）、constrain（在给定结构下用已有观察约束可调参数）和 interpret（比较仍成立的解释，并思考哪项观察能区分它们）。这篇文章说明研究方向，不是对日志 Agent 的对照实验。对 build 73 的以下诊断是工程推演：

> [!example] build 73：用下一项观察区分诊断假设
> 一种可能是同一服务在重试截止后才开始于目标端点监听，另一种是当时服务已在其他端口监听、但构建请求仍指向原端口；两者可以同时发生。第 20 至 22 行只显示连接被拒绝、重试耗尽、构建日志记载服务未就绪并跳过测试，尚未证实任何根因。应按原时间戳对齐三次重试窗口，核对同一进程在相同网络命名空间中的就绪/监听时间、实际端点与调用目标，并检查中间是否存在端口映射。若同一进程只在最后一次重试结束后才监听目标端点，支持启动晚于本次重试窗口；若进程当时已监听另一端点且不存在映射，则支持目标错配。进程始终未监听也可能是启动失败，单靠不同端口字符串也不能证明探针永远无法到达；再次看到 `ECONNREFUSED` 本身仍不能区分这些原因。

## 改进运行脚手架时如何做对照

Harness² 研究固定基础模型权重，并让每项任务从基础脚手架 H₀ 起步；检索到的前序经验仍可能因任务而异。它开放八种运行时组件供改进：system prompt (系统提示词)、guardrails (防护规则)、memory (记忆)、skills (技能)、tool guidance (工具指引)、scripts (脚本)、subagents (子智能体) 与 middleware (中间件)。它提出 Propose–Probe–Compose（提出–探测–组合）：提出编辑，在配对条件下真正执行候选，比较行为差异，只组合有对照证据支持的变化；再把可复用组件或经验存入改进脚手架，供后续任务检索。经验跨任务怎样被选择并进入当前上下文，见[上下文工程原则](../context/context-engineering-principles.md)。

这里的 Probe 是一次实际运行，仍可能受模型方差、共享评委或随机工具状态影响。在线 Propose–Probe–Compose 阶段没有每题真值答案或可靠 verifier (验证器)；行为差异可提示编辑效果，但本身不认证输出正确。论文仍在实验结束后用 WorkBuddy-Bench、JobBench 和 Harvey Legal Agent Benchmark 的外部基准分数评价结果，因此“在线编辑时无 ground-truth verifier”不等于“没有外部评分准则”。生产实现还应给 Probe 限制外部写入权限和费用，否则实验候选可能造成副作用。实际任务契约仍由[独立任务评估](../evaluation/llm-evaluation-methods.md)验证。

四组执行器–运行脚手架（executor–harness）配置里，三个基准各自的最高单步结果分别为：WorkBuddy-Bench 平均得分 +11.5 score points (分数点)，JobBench +4.5 分数点，Harvey LAB Partial criterion pass rate (Partial 评分条目通过率) +11.8 percentage points (百分点)。前两者是基准分数的点数变化，只有最后一项是比例变化；它们是特定模型、基线和任务的单步结果，不是通用 harness 的预期提升。论文还讨论额外执行成本、行为波动以及编辑器（editor）与被编辑系统共用模型时的偏差。

**权重训练分支（Harness-S）。** Harness-S 针对基础脚手架 `H0` 上 8 次采样全部失败的任务，改用兄弟脚手架生成救援轨迹并训练共享策略。比较时要有按同样规则从 `H0` 重采 8 次的基线，训练结束后回到原始 `H0`，用包含新实例的留出任务验收。该分支改的是共享策略权重，不是 build 73 只改提示词的候选 B；论文在 H0 留出任务和少量外部 harness 上观察到受限迁移，不证明任意 prompt、tool 或 memory 修改都能变成通用能力。

> [!info]- Harness-S 的采样、路由和成本细节
> 离线先从 `H0` 生成兄弟脚手架池，针对失败修改提示词、技能、上下文、记忆、钩子或工具视图；局部测试同时检查原本成功的任务，观察回归，再按变体覆盖的验证任务选择编辑父代。训练开始后固定有效变体池。
>
> 每题先由当前策略在 `H0` 采样 8 条；至少一条成功就保留原 8 条整组。只有 8 条全失败时，主配置才路由到 8 个不同 sibling，各从任务初始状态运行 1 条轨迹，并以救援轨迹组替换失败组。论文使用二元奖励；若本地使用分档奖励，不能只按成功标签推断组内奖励差异是否恢复。路由基于 `H0` 与 sibling 的配对验证轨迹、检查点行为档案、任务描述及相似任务结果汇总的 LLM 排名。
>
> 更新时在同一脚手架和生成上下文下比较新旧共享策略对策略生成词元的概率；辅助指令和工具观察是条件上下文，不进入策略词元的训练损失。H0-rescue 对照也在全失败时从 `H0` 初始状态重采 8 条并替换旧组，两组均做 40 次更新；但救援触发次数不同，完整 rollout 与 GPU 小时不匹配，故须报告总采样量和实际成本，不能称为总算力匹配。

## 复用记录说明了什么，又没有说明什么

GitSwarm 在持久且可分支的共享产物仓库中观察 worker 如何引用、访问和组合前序工作。需要分别读三类度量，并把“访问”与“主动复用”区分开：

1. **声明依赖：** worker 在提交中将已有贡献列为 Git parent 或 informed_by 来源；这是可追溯的依赖声明，不是内容复用证明。
2. **轨迹使用：** execution trace 里的 accessed (已访问) 只说明读、搜、比较或打开过产物。actively reused (主动复用) 要求只读材料实际影响后续贡献；可执行产物必须被运行、导入、改编或作为另一计算的输入；自愿产物包还必须引用其提供者。仅仅打开文件不算主动复用。
3. **winner-linked ancestry (胜者关联祖先链)：** 最终选中提交沿 Git parent 和声明的 informed_by 边可达的贡献图覆盖率。它说明声明图上的祖先关系，不证明内容被最终代码实际继承。

设 worker A 把 `probe.sh` 存入共享仓库：worker B 只打开脚本，是“访问”；若 B 实际运行并据结果改写自己的补丁，才有轨迹证据说明它“主动复用”了产物；最后选中的补丁若通过 Git parent 或 `informed_by` 声明链追溯到 B 的贡献，则那项贡献位于“胜者关联祖先链”。反过来，声明引用前序贡献本身也不证明内容被读过或吸收。三种记录分别回答是否声明依赖、是否实际使用、最终解的声明图能否到达该贡献。

GitSwarm 的比例只能说明这些行为在特定基准和仓库设置中被观察到；打开文件不等于使用，声明链不证明内容被最终代码吸收，复用也不证明导致分数提升。研究报告的分母和数字留在章末折叠来源。

## 搜索停滞时，清除什么要由对照回答

*Scaling Discovery Requires Forgetting* 研究在外部评分的开放搜索中保留最佳候选、但清除 session 和候选历史后重启。在 AHC014 的一项对照里，四人团队从同一 plateau 状态继续或重启；每个实验臂由 4 个 agent 各追加 30 个 proposal (候选提案)，即每次重复每臂 120 个提案；共重复 3 次。继续运行结果为 +1.4% ±1.3%，每次实验费用 24.67 美元；重启结果为 +9.2% ±6.9%，费用 15.32 美元。收益分别是三次重复中“最佳新候选相对起始最佳分”的均值 ± 标准差；两臂均值相差 7.8 个百分点，费用相差 9.35 美元/次。论文没有给出由这三个重复计算的配对差分布。

这项比较按候选提案（proposal）数量匹配，并非按费用、词元（token）或时长匹配；重启还同时改变对话会话（session）与候选历史，不能把差异归因于清除某一个记忆源。它支持在某些受限搜索中测试重启，不建立固定重置周期。工程上要事先写下保留的最佳候选、清除的状态、实验预算和继续条件，再用相同起点及真实成本测量两种方案。

Anthropic 的实践文章建议一次只测试一个 subagent (子 Agent) 的合并，比较合并前后的端到端结果并重复运行，并分享何时把工作流合并到主循环的经验。它是特定提供方的工程经验，不是所有任务都该移除子 Agent 的因果定律；结构选择仍需测量。
