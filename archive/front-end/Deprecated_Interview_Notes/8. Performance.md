# Web Performance Reference / Web性能参考

This note covers diagnosis, browser timing signals, batching, and frequently repeated optimization advice. Measurements depend on the page, browser, device, network, and test method; use them to locate a bottleneck, then compare the same scenario after a change.

**Core answer / 核心回答：** Separate loading problems from runtime responsiveness and visual stability, then use field or lab evidence to find the responsible work. A named optimization is only a hypothesis until measurement shows that it addresses the observed bottleneck. / 先区分加载、运行时响应和视觉稳定问题，再用真实用户或实验室数据定位原因。任何优化都只是待验证的假设，只有测量结果表明它解决了当前瓶颈，才算有效。

## Metrics and milestones / 指标与页面里程碑

### Core Web Vitals / Core Web Vitals 核心网页指标

The current Core Web Vitals are LCP, INP, and CLS. Good thresholds are evaluated at the 75th percentile of field visits, separately for mobile and desktop.

| Metric | Measures | Good threshold |
|---|---|---:|
| **LCP** | When the largest visible image or text block is rendered. | ≤ 2.5 s |
| **INP** | Responsiveness across interactions during a visit, including input delay, event-handler work, and the next paint. | ≤ 200 ms |
| **CLS** | Unexpected layout movement during the page visit. | ≤ 0.1 |

INP replaced FID as the Core Web Vital for responsiveness in 2024. FID only measured the input delay of the first interaction; INP considers the broader interaction-to-next-paint path.

### Diagnostic milestones / 诊断里程碑

| Milestone | Meaning and use |
|---|---|
| **FCP** | Time from navigation until the first text, image, SVG, or non-white canvas content is painted. It measures when something first appears, not when the main content is ready. |
| **DOMContentLoaded (DCL)** | Fires after the document has been parsed and deferred/module scripts have executed. It does not wait for all images and other page resources to finish loading. |
| **window load** | Fires after the document's eagerly loaded dependent resources finish loading; lazy-loaded resources may still be pending. Useful when the task depends on those resources, not as a universal page-ready signal. |
| **Long task / long animation frame** | A clue that main-thread work may delay input or rendering. Inspect the trace and attribute the work to script, style, layout, or other activity. |

These events are not a universal sequence for every page. In particular, LCP can happen before or after DCL or load depending on the content and resource schedule. FCP, DCL, and load are diagnostic milestones, not substitutes for the Core Web Vitals. First Meaningful Paint is a deprecated metric and should not be treated as a standardized replacement for LCP.

### Field and lab data / 真实用户与实验室数据

- **Field data** records real visits across devices, networks, locations, and user behavior. It shows the experience users actually had, often summarized by percentile.
- **Lab data** runs a controlled test with selected device and network settings. It is repeatable and useful for debugging, but does not represent every user's experience.
- INP requires interactions, so a page-load-only Lighthouse run cannot measure it directly. Total Blocking Time is a lab diagnostic that can help investigate main-thread blocking; it is not an interchangeable INP value.
- Keep page, route, device profile, throttling, cache state, and test steps consistent when comparing before and after results.

## Triage workflow / 排查流程

1. Clarify whether the symptom is slow initial content, slow interaction, visual movement, or a later operation.
2. Check Console and Network for errors, failed requests, long waits, large transfers, and unexpected duplicate work.
3. Record the relevant user flow in DevTools Performance. Inspect scripting, rendering, style recalculation, layout, paint, and long tasks around the symptom.
4. Use Lighthouse or another lab tool to reproduce loading conditions and review diagnostics. Compare with field data when the concern is user experience at scale.
5. Change the part of the system that the trace implicates, then repeat the same measurement. Keep the result and limitations with the change.

SSR, code splitting, a CDN, caching, or compression can help in a particular scenario, but none is a universal fix. For example, SSR can make content available in initial HTML while adding server work and client hydration; evaluate the full route and its data requirements.

## Browser scheduling / 浏览器调度

- **requestAnimationFrame** asks the browser to call a callback before the next repaint. It is appropriate for visual updates and animation work, and it is one-shot.
- **requestIdleCallback** asks for a callback during an idle period. The browser may delay it; use its deadline to divide optional work into small chunks. A timeout can bound waiting, but timed-out work may compete with user-facing work.
- They serve different purposes. Do not describe either callback as a JavaScript microtask or assume that idle work runs on every frame.
- React Fiber is React's reconciler architecture. Its scheduling behavior is internal to React and is not a public contract that the browser will run React work through requestIdleCallback.

~~~javascript
function processChunk(deadline) {
  let processed = 0;
  while (tasks.length > 0 && deadline.timeRemaining() > 0) {
    processOne(tasks.shift());
    processed += 1;
  }

  if (tasks.length > 0 && deadline.didTimeout && processed === 0) {
    processOne(tasks.shift()); // Do one bounded unit, then yield again.
  }

  if (tasks.length > 0) {
    requestIdleCallback(processChunk, { timeout: 2000 });
  }
}
~~~

`processOne` should be a small unit of work. A timed-out callback can have no idle time remaining, so this example still completes one unit before scheduling the rest. The timeout here is an example bound, not a universal performance threshold. Use requestAnimationFrame for visual DOM changes; keep idle work small and nonessential.

## Debounce and throttle / 防抖与节流

Debounce waits for a quiet interval after the latest call. Throttle limits calls over time. Their leading and trailing behavior depends on the implementation and options, so state which contract a caller needs.

~~~javascript
function debounce(fn, wait) {
  let timer;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), wait);
  };
}

function throttleLeading(fn, interval) {
  let lastCall = 0;
  return function (...args) {
    const now = Date.now();
    if (now - lastCall < interval) return;
    lastCall = now;
    fn.apply(this, args);
  };
}
~~~

The debounce example runs only after calls pause. The throttle example is leading-only and drops calls during the interval; it does not schedule a trailing call. These examples illustrate different contracts rather than a single library-wide default.

Use debounce for work that should follow a pause, such as a search request after typing. Use throttle when updates should be bounded during a continuous stream, such as reporting scroll position. For a concrete Lodash contract, see [Lodash Reference / Lodash参考](12.1%20Lodash.md).

## Loading and first-screen choices / 加载与首屏选择

- **Route and component splitting:** Load code when the user needs it if doing so shortens the critical path. Keep essential first-screen code available and avoid delaying content needed immediately.
- **Server rendering:** SSR can send rendered HTML before client JavaScript finishes loading. It may improve content availability for a route, but server latency, data fetching, hydration cost, and caching still matter. Multiple-page applications also commonly send server-rendered HTML.
- **Hybrid WebViews:** An application may prefetch route data and expose it to a web page through a native bridge. This is platform-specific; define data freshness, failure behavior, and bridge ownership.
- **Pagination and virtualization:** Paginate large result sets to limit fetched data; virtualize long visible lists to limit mounted rows. They address different costs.
- **Images:** Defer images below the initial viewport when appropriate and provide dimensions or aspect ratio so layout space is reserved before the image loads.
- **Caching and delivery:** Use cache headers, compression, and a CDN when the asset and data freshness requirements allow them. Measure the actual transfer and cache hit behavior.

## CSS and sprites / CSS与精灵图

CSS shorthands can reduce repeated source declarations and output bytes after minification, but they do not guarantee faster browser parsing. Prefer readable CSS unless the shorthand improves consistency or payload size.

CSS can draw simple shapes without a separate image request. For example, a triangle can be made with borders:

~~~css
.triangle {
  width: 0;
  height: 0;
  border-left: 50px solid transparent;
  border-right: 50px solid transparent;
  border-bottom: 100px solid black;
}
~~~

A CSS sprite combines small images in one asset and selects a region with background-position:

~~~css
.icon {
  width: 24px;
  height: 24px;
  background-image: url('/icons.png');
  background-repeat: no-repeat;
}

.icon-search {
  background-position: 0 0;
}
~~~

Sprites trade fewer resource requests for a combined asset that may contain unused pixels and needs coordinated updates. HTTP/2 and later transport changes reduce the request-count advantage in some cases; they do not make sprites universally obsolete. Compare the asset size, cache behavior, and maintenance cost for the actual page.

## React rendering advice / React渲染建议

### Mounting versus hiding / 卸载与隐藏

Conditional rendering removes the child from the tree when the condition is false, so its local state is discarded and its Effects clean up. CSS display:none keeps the component mounted, preserving state but also retaining its Effects and other work. Choose based on the required behavior, not an assumption that one form is always faster.

~~~jsx
return visible ? <Panel /> : null;
~~~

### Lists, fragments, and callbacks / 列表、Fragment与回调

- Give list items stable keys that identify the same logical item after insertion, removal, or reorder. An index can be appropriate for a static list, but can attach state to the wrong row when list positions change.
- Fragments group children without adding a wrapper DOM element. This is useful when an extra element would affect markup or layout; it is not a general rendering-speed guarantee.
- An inline event callback is recreated when its parent renders, but that alone is not a performance problem. Consider stable callbacks only when profiling shows that identity changes defeat a memoized child or another measured boundary.

~~~jsx
const todoItems = todos.map(todo => (
  <li key={todo.id}>{todo.text}</li>
));
~~~

### Class and function component memoization / 类组件与函数组件的跳过更新

PureComponent shallowly compares props and state. React.memo can skip rendering a function component when its props compare equal. Both are optimizations: changed context or local state can still render the component, and custom comparison must account for every prop that affects output or behavior.

~~~jsx
class TodoRow extends React.PureComponent {
  render() {
    return <div>{this.props.todo.text}</div>;
  }
}

const MemoTodoRow = React.memo(function TodoRow({ todo }) {
  return <div>{todo.text}</div>;
});
~~~

shouldComponentUpdate offers a manual class-component decision, but returning false for a prop that affects output can produce stale UI. Measure before adding a custom comparison.

Class methods that use this need binding unless defined as class fields with arrow functions:

~~~jsx
class Button extends React.Component {
  state = { count: 0 };

  handleClick = () => {
    this.setState(state => ({ count: state.count + 1 }));
  };

  render() {
    return <button onClick={this.handleClick}>Add</button>;
  }
}
~~~

For a wider account of render identity and current memoization guidance, see [Rendering and Computation Optimization](../../../frontend/performance/rendering-and-computation-optimization.md) and [Advanced React / React进阶](../../../frontend/frameworks/advanced-react.md).

## Event batching / 事件批处理

Batching combines state updates into fewer render commits. It does not make a state setter synchronous or turn it into a microtask/macrotask API. Read the state value from the current render as a snapshot; use an updater when the next value depends on pending state.

~~~jsx
function Counter() {
  const [count, setCount] = useState(0);

  function addTwo() {
    setCount(value => value + 1);
    setCount(value => value + 1);
  }

  return <button onClick={addTwo}>{count}</button>;
}
~~~

Class components have a related queue, but setState shallow-merges object updates. A functional updater is safer when multiple updates depend on the previous state:

~~~javascript
this.setState(state => ({ count: state.count + 1 }));
~~~

React 18 roots created with createRoot automatically batch updates from React handlers and many asynchronous callbacks. Older root APIs and integrations may have different behavior. Avoid relying on logs immediately after a setter to infer when a render will commit.

## Tracking analytics / 分批发送分析数据

Queue small events and send a batch when it reaches an example count or when the document becomes hidden. sendBeacon is best-effort transport: true means the browser queued the payload, not that the server stored it. It sends POST data, has a bounded queued-payload size, and does not expose the response. Use fetch with keepalive when request configuration or a response is required.

~~~javascript
const eventQueue = [];
const batchSize = 20; // Example only; choose from the payload and latency budget.
const maxQueuedEvents = 100; // Example overflow bound for this in-memory queue.
const endpoint = '/analytics';

function queueEvent(event) {
  if (eventQueue.length >= maxQueuedEvents) eventQueue.shift();
  eventQueue.push(event);
  if (eventQueue.length >= batchSize) flushEvents();
}

function flushEvents() {
  if (eventQueue.length === 0) return false;

  const batch = eventQueue.splice(0, batchSize);
  const payload = new Blob([JSON.stringify(batch)], {
    type: 'application/json',
  });
  const queued = navigator.sendBeacon(endpoint, payload);

  if (!queued) eventQueue.unshift(...batch);
  return queued;
}

document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') flushEvents();
});
~~~

This illustration drops the oldest in-memory event when its example count bound is reached. It has no server acknowledgement or durable local queue; a production client should also bound serialized payload bytes against the Beacon API limit. Add a measured periodic flush if low-volume events cannot wait for the page to become hidden. Do not rely on unload or beforeunload as a delivery guarantee.
