# Virtual DOM, React, and Next.js / 虚拟 DOM、React 与 Next.js

This reference keeps the original interview-study topics while correcting claims that depend on React or router versions. React Router examples are explicitly scoped to v5; Next.js data-fetching examples are Pages Router APIs. See the current canonical notes before applying an example to a new application.

**Core answer / 核心回答：** React describes UI as elements derived from props and state, then reconciles those descriptions with the current tree. Keys and component identity determine which state is preserved. Next.js adds routing and rendering options, but each router has its own data and caching APIs. / React 根据 props 和 state 描述界面，再把新的描述与当前树协调。key 与组件身份决定哪些 state 得以保留。Next.js 增加路由和渲染选项，但不同路由器各有数据与缓存 API。

## Virtual DOM and reconciliation / 虚拟 DOM 与协调

A React element is a lightweight description of UI; it is not a copy of the browser DOM. When state or props change, React calls components to produce a new description, compares it with the previous tree, and commits the necessary host updates.

The virtual DOM is not automatically faster than direct DOM operations. It provides a declarative model and lets React coordinate updates; performance depends on the component tree, calculation cost, committed changes, and browser work. The reconciler uses heuristics and does not promise a globally minimal edit sequence.

A useful identity model is:

- At a given parent position, a compatible element type can preserve the child's state.
- A different type at that position replaces the previous subtree and resets its state.
- A key distinguishes siblings and can preserve or reset state when list positions change.
- Keys are local to a sibling set; they are not global identifiers.

~~~jsx
function List({ items }) {
  return items.map(item => <Row key={item.id} item={item} />);
}
~~~

A stable domain identifier keeps row state associated with the same item after insertion or reorder. An array index is suitable only when the list's identity and order are stable.

## Browser scheduling and React Fiber / 浏览器调度与 React Fiber

React Fiber is React's reconciler implementation. It allows React to prioritize and coordinate rendering work, but application code should not assume Fiber is a direct wrapper around window.requestIdleCallback. React's scheduling is an internal implementation detail.

- requestAnimationFrame asks the browser to call code before a repaint and is useful for visual updates.
- requestIdleCallback schedules optional work during a browser idle period. It can be delayed; use its deadline to divide work and a timeout only when bounded waiting is required.
- These browser APIs have different timing contracts. They are not ECMAScript microtasks or interchangeable task queues.

~~~javascript
function processChunk(deadline) {
  let processed = 0;
  while (tasks.length && deadline.timeRemaining() > 0) {
    processOne(tasks.shift());
    processed += 1;
  }

  if (tasks.length && deadline.didTimeout && processed === 0) {
    processOne(tasks.shift()); // Do one bounded unit, then yield again.
  }

  if (tasks.length) requestIdleCallback(processChunk, { timeout: 2000 });
}
~~~

`processOne` should be a small unit of work. A timed-out callback can have no idle time remaining, so this example still completes one unit before scheduling the rest. The timeout is an example, not a universal threshold; check support for the target browsers and keep nonessential work small.

## JSX / JSX 语法

JSX is syntax for describing elements inside JavaScript. It is neither HTML text nor a string. The compiler and configuration determine the output: a classic transform can call React.createElement, while the automatic runtime can call functions from the JSX runtime.

~~~jsx
const title = <h1 className="title">Hello</h1>;
~~~

This classic-runtime-style output is one possible transform, not the only one:

~~~javascript
const title = React.createElement('h1', { className: 'title' }, 'Hello');
~~~

Lowercase JSX tags name built-in elements; uppercase identifiers name component values. Curly braces insert JavaScript expressions.

## Component communication / 组件通信

### Parent to child / 父组件向子组件

Props carry data and callbacks down the tree. Context can supply a value to many descendants when prop drilling becomes unwieldy.

~~~jsx
const ThemeContext = React.createContext('light');

function App() {
  return (
    <ThemeContext.Provider value="dark">
      <Toolbar />
    </ThemeContext.Provider>
  );
}

function Toolbar() {
  const theme = React.useContext(ThemeContext);
  return <button className={theme}>Save</button>;
}
~~~

### Child to parent / 子组件向父组件

Pass a callback prop down and call it when the child has an event or result to report.

~~~jsx
function Parent() {
  const handleSelect = item => console.log(item);
  return <Child onSelect={handleSelect} />;
}

function Child({ onSelect }) {
  return <button onClick={() => onSelect('chosen')}>Choose</button>;
}
~~~

For a parent that needs an imperative operation, expose a narrow ref API with useImperativeHandle. A ref is useful for focus, media controls, or another imperative capability; it should not replace state that drives visible UI. React 18 and earlier use forwardRef to receive a ref in a function component. React 19 lets a function component accept ref as a prop; the current docs mark forwardRef as deprecated for a future release.

React 18 and earlier example:

~~~jsx
const SearchInput = React.forwardRef(function SearchInput(props, forwardedRef) {
  const inputRef = React.useRef(null);
  React.useImperativeHandle(forwardedRef, () => ({
    focus() {
      inputRef.current?.focus();
    },
  }), []);

  return <input {...props} ref={inputRef} />;
});

function SearchForm() {
  const inputRef = React.useRef(null);
  return (
    <>
      <SearchInput ref={inputRef} />
      <button onClick={() => inputRef.current?.focus()}>Focus search</button>
    </>
  );
}
~~~

### Bubbling, render props, and reuse / 冒泡、render props 与复用

A DOM event bubbles from a child to its ancestors. A parent can handle a child's click without dispatching a separate custom event:

~~~jsx
function Parent() {
  return (
    <div onClick={event => console.log(event.target)}>
      <button>Child action</button>
    </div>
  );
}
~~~

Render props pass a function that decides what to render while a component owns reusable behavior. This is still a valid pattern, although a custom Hook or ordinary component composition may be simpler for a given problem.

~~~jsx
function MouseTracker({ render }) {
  const [position, setPosition] = React.useState({ x: 0, y: 0 });

  React.useEffect(() => {
    function handleMove(event) {
      setPosition({ x: event.clientX, y: event.clientY });
    }

    window.addEventListener('mousemove', handleMove);
    return () => window.removeEventListener('mousemove', handleMove);
  }, []);

  return <div style={{ height: '100vh' }}>{render(position)}</div>;
}

function App() {
  return (
    <MouseTracker
      render={({ x, y }) => (
        <img
          src="/cat.png"
          alt="Cat following the pointer"
          style={{ position: 'absolute', left: x, top: y }}
        />
      )}
    />
  );
}
~~~

Other reuse patterns include higher-order components, compound components, portals, custom Hooks, and shared state libraries. Portals change the DOM placement of children while keeping them in the React tree.

## Conditional rendering / 条件渲染

Use ordinary JavaScript control flow to choose elements. Returning null omits a component's output but does not prevent its Hooks or lifecycle from running while it remains mounted.

~~~jsx
function Greeting({ loggedIn }) {
  if (loggedIn) return <UserGreeting />;
  return <GuestGreeting />;
}

function Notice({ unread }) {
  return <div>{unread > 0 && <p>You have {unread} messages.</p>}</div>;
}
~~~

When using &&, make the left side a boolean if it can be a number. An expression such as count && <Badge /> renders 0 when count is zero.

## Error boundaries / 错误边界

An Error Boundary is a class component that catches rendering errors in descendant components and shows fallback UI. It does not catch errors thrown in event handlers, ordinary asynchronous callbacks, server rendering, or by the boundary itself. Handle those at their source or in an appropriate global reporting layer.

~~~jsx
class ErrorBoundary extends React.Component {
  constructor(props) {
    super(props);
    this.state = { hasError: false };
  }

  static getDerivedStateFromError() {
    return { hasError: true };
  }

  componentDidCatch(error, errorInfo) {
    reportError(error, errorInfo.componentStack);
  }

  render() {
    if (this.state.hasError) return <h1>Something went wrong.</h1>;
    return this.props.children;
  }
}
~~~

getDerivedStateFromError updates state for the fallback render. Put logging in componentDidCatch rather than performing side effects in the state-derivation method.

## Class component lifecycle / 类组件生命周期

| Phase | Methods and purpose |
|---|---|
| Mount | constructor initializes; render describes UI; componentDidMount runs after insertion and is a place to start subscriptions or browser-only work. |
| Update | getDerivedStateFromProps runs before render when deriving state is necessary; shouldComponentUpdate can skip work; getSnapshotBeforeUpdate reads DOM state before mutation; componentDidUpdate runs after commit. |
| Unmount | componentWillUnmount cleans up subscriptions, timers, and other resources. |
| Descendant error | getDerivedStateFromError selects fallback state; componentDidCatch receives error details for reporting. |

getDerivedStateFromProps and shouldComponentUpdate are advanced class APIs. Avoid mirroring props in state or adding comparison logic unless the component's requirements call for it. Hooks do not map one-for-one to every class lifecycle method.

## State updates and batching / 状态更新与批处理

A state setter schedules an update; reading state immediately after calling it still reads the current render's snapshot. Do not classify a state setter as a microtask or macrotask. When the next value depends on pending state, pass an updater.

~~~jsx
function Counter() {
  const [count, setCount] = React.useState(0);

  function addTwo() {
    setCount(value => value + 1);
    setCount(value => value + 1);
  }

  return <button onClick={addTwo}>{count}</button>;
}
~~~

Class setState queues updates and shallow-merges object values. Function-component state setters replace the state value instead. React batches related updates into fewer commits; React 18 roots created with createRoot extend automatic batching to many updates from promises, timers, and native events. The root API and integration can affect behavior, so code should not depend on a particular console-log order after a setter.

## Routing parameters / 路由参数

### React Router v5 / React Router v5 示例

The following pattern uses the React Router v5 API and package. Route parameters are strings matched from a dynamic path.

~~~jsx
import { Route, useParams } from 'react-router-dom';

function Post() {
  const { postId } = useParams();
  return <h1>Post {postId}</h1>;
}

function Routes() {
  return <Route path="/post/:postId" component={Post} />;
}
~~~

React Router v6 and v7 use a different route declaration shape, commonly Route with element inside Routes. Do not copy the v5 component prop into a current route without checking the installed version.

Common web-router modes in this v5 reference:

| Mode | URL and environment |
|---|---|
| **BrowserRouter** | Uses the browser history API for ordinary path URLs; the server must serve the application entry point for client routes. |
| **HashRouter** | Stores the route in the URL fragment, so route changes do not require server path configuration. |
| **MemoryRouter** | Keeps navigation entries in memory; useful in tests and environments without a browser address bar. |
| **StaticRouter** | Supplies a fixed location during server rendering. |

These modes solve different URL and host constraints; choose one based on deployment and navigation requirements.

### Next.js Pages Router / Next.js Pages Router 示例

This is the Pages Router hook imported from next/router. A dynamic page such as pages/user/[userId].js can read the userId parameter from router.query. In automatically statically optimized pages, query values may be unavailable during the initial prerender; use the router's readiness state when client-only access is required.

~~~jsx
import { useRouter } from 'next/router';

function UserPage() {
  const router = useRouter();
  const { userId } = router.query;
  return <h1>User {userId}</h1>;
}
~~~

The App Router uses APIs from next/navigation; do not use next/router's query object there. Its route parameters and page props follow different conventions.

## What Next.js adds / Next.js 增加了什么

Next.js is a React framework with file-system routing, server and client rendering options, data access patterns, code splitting, and deployment integrations. The exact API is router- and version-specific.

- Pages Router API routes live under pages/api; App Router uses route handlers under route segments.
- CSS support and bundling are integrated with the framework, while the app's configuration still affects the resulting assets.
- Static generation, request-time rendering, and client-side navigation address different data freshness and runtime requirements.
- Server rendering can make content available in HTML before client JavaScript hydrates; it does not guarantee faster overall interaction or better search ranking.
- Next.js apps can mix rendering approaches by route. A traditional React SPA is not the only way to use React; React also supports server rendering outside Next.js.

## Pages Router rendering / Pages Router 渲染方式

These APIs belong to the Pages Router under the pages directory:

| Strategy | API | When it fits |
|---|---|---|
| Request-time rendering | getServerSideProps | Data must be fetched for each request. |
| Static generation | getStaticProps and, for dynamic paths, getStaticPaths | Data can be prepared at build time. |
| Incremental static regeneration | getStaticProps with revalidate | A generated page can be refreshed after deployment. |
| Legacy page data | Page.getInitialProps(ctx) | Runs on the server for the initial page load and in the browser during client-side transitions; prefer getStaticProps or getServerSideProps for new pages. |

~~~jsx
export async function getStaticPaths() {
  return {
    paths: [{ params: { id: 'post-1' } }],
    fallback: 'blocking',
  };
}

export async function getStaticProps({ params }) {
  const post = await getPost(params.id);

  if (!post) return { notFound: true };

  return {
    props: { post },
    revalidate: 60,
  };
}
~~~

With fallback: 'blocking', a path not listed at build time can be generated on its first request. With `revalidate: 60`, a request after the interval can trigger regeneration but still receive the cached stale page while the new page is generated in the background. After a successful regeneration, a later request receives the updated page; if regeneration fails, the stale page remains available. This interval is not a maximum freshness bound.

For App Router pages, use its route conventions and data APIs instead of these functions. Cache defaults and streaming behavior have changed across Next.js versions; configure and verify caching deliberately.

## Lifecycle and hydration / 生命周期与 hydration

Server rendering and static generation produce HTML on the server or during the build. The browser parses that HTML, downloads the client code, and hydrates interactive components where applicable. Effects synchronize with external systems after a client commit; React runs cleanup before re-running an Effect with changed dependencies and on unmount. Effects do not run during server rendering and are not a substitute for server data fetching. In development StrictMode, React performs an extra render and an extra Effect setup/cleanup cycle to expose impure rendering and missing cleanup; this is a development check, not an extra production request guarantee. Component lifecycle methods describe React behavior, while Next.js controls routing, data preparation, rendering, and delivery around that behavior.

## Hooks, helpers, and memoization / Hook、工具函数与记忆化

A custom Hook is appropriate when reusable logic composes React Hooks or manages component state and Effects. A pure calculation, formatting helper, or validation rule that does not call Hooks should remain an ordinary function. Most Hooks must be called at the top level of a component or custom Hook, never in a condition or loop. React's special `use` API is an exception that can read a Context or Promise inside a condition or loop, but not inside try/catch; do not generalize this exception to useState, useEffect, or other Hooks.

useMemo caches a calculated value and useCallback caches a function according to dependencies. React.memo can skip a function component when its props compare equal. These are performance optimizations, not correctness guarantees; React may still render, and useMemo's cached value may be discarded in some situations. First make rendering correct and pure, then profile before adding memoization.

~~~jsx
const total = useMemo(() => calculateTotal(items), [items]);

const handleSubmit = useCallback(
  details => submit(productId, details),
  [productId, submit],
);

const MemoizedRow = React.memo(function Row({ item }) {
  return <div>{item.name}</div>;
});
~~~

A memoized child may still render when its own state or consumed context changes. Every value captured by a callback belongs in its dependency list unless a functional updater or another stable API removes that dependency.
