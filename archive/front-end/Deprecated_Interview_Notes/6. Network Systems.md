# Web Networking and HTTP / Web 网络与 HTTP

This interview note summarizes browser-facing network concepts. HTTP semantics come from standards; details such as browser policy, proxy behavior, and deployed protocol support can vary. For a deeper reference, see [HTTP protocols and WebSockets](../../../engineering-foundations/networking/http-protocols-and-websockets.md) and [web security and authentication](../../../engineering-foundations/security/web-security-and-authentication.md).

HTTP 方法的安全性和幂等语义不等同于 REST；CORS 控制浏览器脚本读取跨源响应的条件，不是认证或 CSRF 防护。服务端必须按资源与操作授权；WebSocket 握手后虽可双向发送帧，仍需校验 Origin、身份和消息权限。

## REST and HTTP Methods / REST 与 HTTP 方法

REST is an architectural style, not a synonym for JSON-over-HTTP. A REST interface identifies resources and uses a uniform interface; real APIs often use only some REST constraints. HTTP methods describe request semantics, while each resource decides which methods it allows.

| Method | Typical meaning | Safe? | Idempotent? |
| --- | --- | --- | --- |
| `GET` | Retrieve a representation | Yes | Yes |
| `HEAD` | Like `GET`, without response content | Yes | Yes |
| `POST` | Process content according to the target resource (often create or trigger an operation) | No | Not by definition |
| `PUT` | Replace the target resource's representation; may create it when the server permits | No | Yes |
| `PATCH` | Apply a patch document; exact semantics depend on the patch format and API | No | Not inherently |
| `DELETE` | Remove the target resource's association/current representation | No | Yes |
| `OPTIONS` | Ask about communication options for the target | Yes | Yes |

“Safe” means the client does not request a state change; it does not promise that a server has no incidental side effects such as logging. “Idempotent” means repeating the same request has the same intended effect, not necessarily the same response. `PATCH` is defined separately from core HTTP semantics; a patch format can define an idempotent operation, but clients should not assume that every PATCH is safe to retry. Use an API-level idempotency key or conditional request when a non-idempotent action must survive retries.

For a blog API, `GET /posts/42` reads a post, `PUT /posts/42` sends its complete replacement representation, and a defined patch format on `PATCH /posts/42` changes selected fields. `POST /posts` can create a post, but the exact response and resource URI are API design choices.

## Common Request Headers / 常见请求头

- `Accept` describes response media types the client can process; `Content-Type` describes the representation in this message.
- `Authorization` carries credentials such as a bearer token. Treat credentials and URLs containing tokens as sensitive.
- `Cookie` sends matching cookies; `Set-Cookie` is a response field that sets them.
- `Accept-Language` communicates language preferences. `Accept-Encoding` communicates supported content codings, usually managed by the user agent.
- `Cache-Control` controls cache behavior. `ETag` and conditional fields such as `If-None-Match` support validation.
- `Referer` identifies a referring URL subject to browser referrer policy; it can contain sensitive path or query information.
- `Accept-Charset` is generally unnecessary for modern web applications; use UTF-8 consistently rather than depending on charset negotiation.
- `Connection` is hop-by-hop connection metadata in HTTP/1.1. HTTP/2 and HTTP/3 prohibit connection-specific fields such as `Connection` and `Keep-Alive`.

## Selected Status Codes / 常见状态码

- `200 OK`: request succeeded; response content depends on the method.
- `201 Created`: request created one or more resources; a `Location` field can identify a new resource.
- `204 No Content`: request succeeded and there is no response content.
- `301 Moved Permanently` and `302 Found`: redirects with different cache and method-handling rules. `307` and `308` preserve the request method; check the specification when redirecting state-changing requests.
- `304 Not Modified`: tells a conditional `GET` or `HEAD` client it may reuse a cached representation; it is not a redirect and has no response content.
- `400 Bad Request`: request cannot be processed because of a client-side request problem.
- `401 Unauthorized`: authentication is required or failed; despite the name, it is an authentication response and includes a `WWW-Authenticate` challenge.
- `403 Forbidden`: the server understood the request but refuses it; authentication alone may not change the result.
- `404 Not Found`: no current representation was found, or the server chooses not to reveal one.
- `429 Too Many Requests`: rate limit exceeded; `Retry-After` may indicate when to try again.
- `500 Internal Server Error`, `502 Bad Gateway`, `503 Service Unavailable`, and `504 Gateway Timeout`: common server or gateway failures. Their precise recovery behavior depends on the service.

## Ajax, Fetch, and Axios / Ajax、Fetch 与 Axios

Ajax describes a browser technique for exchanging data without navigating the whole document. `XMLHttpRequest` and `fetch()` are APIs that can implement it. Axios is a third-party HTTP client, with browser and Node.js adapters; its options and defaults depend on the installed version.

`fetch()` rejects for network-level failures, but an HTTP response such as `404` still fulfills the promise. Check `response.ok` or `response.status` before treating it as success:

```js
async function getJson(url) {
  const response = await fetch(url, { headers: { Accept: 'application/json' } });
  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`);
  }
  return response.json();
}
```

In browsers, cross-origin `fetch()` remains subject to CORS whether it is called directly or through a library. In Node.js, browser CORS enforcement does not apply, though server-side authorization and network policy still do.

## OSI and TCP/IP Layer Models / OSI 与 TCP/IP 分层

The OSI model is a teaching and troubleshooting model. Protocols do not always fit a single layer cleanly, and mappings to the Internet protocol suite are approximate.

| OSI layer | Illustrative responsibilities | Approximate Internet-suite grouping |
| --- | --- | --- |
| 7 Application | Application protocols such as HTTP, DNS, SMTP | Application |
| 6 Presentation | Representation, encoding, compression, encryption concerns | Application |
| 5 Session | Session coordination concepts | Application |
| 4 Transport | End-to-end transport such as TCP or UDP | Transport |
| 3 Network | IP addressing and routing | Internet |
| 2 Data link | Local-link framing and addressing, e.g. Ethernet | Link |
| 1 Physical | Signal transmission over a medium | Link |

TLS, for example, sits between application protocols and transports in common deployments; treating it as only one OSI layer is a simplification.

## TCP Connection Setup, Shutdown, and Framing / TCP 建连、关闭与分帧

A common TCP connection establishment exchanges `SYN`, `SYN-ACK`, then `ACK` so the peers synchronize sequence numbers and confirm reachability in both directions. It is often called the three-way handshake. It is not a general guarantee that exactly three packets are observable in every capture: retransmissions, loss, and options affect what appears.

A normal close may use a FIN/ACK exchange in each direction because TCP is full-duplex; the two directions can close independently. Simultaneous close, reset, and half-closed connections mean “four-way termination” is a useful diagram, not an invariant. `TIME_WAIT` is a TCP endpoint state used in connection teardown; it is not a browser timer.

TCP presents an ordered byte stream, not a sequence of application messages. A single application write may be split across TCP segments, and multiple writes may be read together. TCP does not preserve write boundaries. Applications therefore need message framing, such as a delimiter, a fixed-length header, or a length prefix. The informal phrase “TCP packet sticking” (`粘包`) usually refers to this stream-framing mismatch, not a TCP defect.

## HTTP and UDP Are Different Layers / HTTP 与 UDP 不在同一层

HTTP is an application protocol. UDP is a transport protocol that provides datagrams without TCP-style delivery, ordering, or retransmission guarantees. UDP does include a checksum mechanism; the details depend on the IP version and context. HTTP/3 maps HTTP semantics onto QUIC, which runs over UDP and supplies reliable, ordered delivery per QUIC stream, congestion control, and TLS 1.3 security. So the useful comparison is usually TCP versus UDP/QUIC, or HTTP/1.1/2 versus HTTP/3—not “HTTP versus UDP.”

## HTTP/1.1, HTTP/2, and HTTP/3 / HTTP 版本

| Version | Connection and framing | Practical distinction |
| --- | --- | --- |
| HTTP/1.1 | Textual message syntax; persistent connections by default, with requests commonly serialized per connection | Clients often open several connections to an origin for parallel requests; intermediaries and connection reuse matter. |
| HTTP/2 | Binary frames and multiple request streams over one TCP connection | Multiplexing reduces application-level head-of-line blocking, but TCP packet loss can stall streams sharing that connection. Connection-specific fields from HTTP/1.x are prohibited. |
| HTTP/3 | HTTP semantics over QUIC streams, usually reached over UDP | QUIC provides stream multiplexing and per-stream loss recovery; it uses TLS 1.3. UDP restrictions can make a client fall back to a TCP-based HTTP version. |

HTTP/2 server push was specified, but browser and deployment support changed; for example, Chrome removed it beginning in version 106. Do not design a current delivery strategy around it without checking the actual client and server ecosystem. There is no “HTTP/3.0” name in the protocol standards; call it HTTP/3.

## CORS and Same-Origin Policy / CORS 与同源策略

The same-origin policy restricts how a document or script can read certain cross-origin resources. CORS is a server opt-in protocol that lets a browser expose eligible cross-origin responses to a calling script. CORS is not authentication, and it is not a general firewall: some cross-origin requests can reach a server even when the browser later withholds the response from JavaScript.

A cross-origin request that meets the CORS safelist conditions can be sent without a preflight. Other requests—such as one using a non-safelisted method, request header, or content type—typically cause the browser to send an `OPTIONS` preflight first. The server must allow the origin, method, and headers as applicable; credentialed requests require compatible explicit origin and credential response fields, not `*`. CORS behavior is implemented by browsers and does not protect a server from command-line clients or other backends.

For a Fetch request with cookies, both the client and server must opt into credentials, and cookie policy still applies:

```js
const response = await fetch('https://api.example.test/profile', {
  credentials: 'include',
});
if (!response.ok) throw new Error(`HTTP ${response.status}`);
```

The server must return an explicit allowed origin (not `*`) plus `Access-Control-Allow-Credentials: true` for such a response. Configure CORS for known origins and the smallest method/header set needed.

### Common Integration Patterns

- **Same-origin backend or reverse proxy:** the browser calls its own origin and the server-side proxy calls the upstream API. The proxy still needs authorization, request validation, and safe upstream routing.
- **JSONP:** legacy technique that loads a cross-origin script, effectively limited to `GET` and a cooperating server. The response executes as code, creating injection and data-exposure risks; prefer CORS where possible.
- **`postMessage`:** cross-origin window messaging, not a CORS bypass. Set an exact `targetOrigin`, then verify `event.origin`, `event.source`, and the message schema.
- **Beacon or image requests:** their use does not bypass CORS, authentication, browser privacy policy, or server authorization.

## CORS Preflight / CORS 预检

The browser may issue an `OPTIONS` preflight to ask whether a subsequent cross-origin request is allowed. The preflight is about browser policy and the planned request; it does not mean the browser sends `OPTIONS` before every cross-origin request. Preflight caching can reduce repeats, subject to browser limits and server directives. The actual request still needs a valid response that passes the CORS checks.

## Cookies, Sessions, and Tokens / Cookie、Session 与 Token

A cookie is browser-managed state scoped by attributes such as host/domain, path, expiry, `Secure`, `HttpOnly`, and `SameSite`. Cookie scope is not identical to the same-origin policy: ports affect an origin but are not a cookie scoping attribute. For session cookies, an `HttpOnly; Secure` cookie with an intentional `SameSite` policy is often preferable to exposing a bearer credential to JavaScript. `SameSite` is defense in depth; it does not replace authorization or all CSRF defenses.

A server-side session stores or references session state on the server and sends the browser a session identifier, commonly in a cookie. A bearer token is a credential the caller presents explicitly, often in the `Authorization` header. Browser requests with an `Authorization` header still undergo CORS rules and often need a preflight. Storing a long-lived bearer token in `localStorage` makes it available to scripts running in the origin, so an XSS flaw can expose it. Choose storage and session lifetime from the threat model; “token” does not automatically mean stateless, cross-origin, or safer.

JWT is a token format, not synonymous with encryption or a session architecture. A signed JWT (JWS) can be readable by anyone who has it; a JWE is encrypted. Validate signature, issuer, audience, time claims, and key policy at the relying service. Avoid putting secrets or unnecessary personal data into a readable token.

### Single Sign-On / 单点登录

SSO is a user experience built from identity-provider and relying-party protocols. Common web patterns include OpenID Connect (OIDC) on OAuth 2.0 and SAML in enterprise integrations. A browser application typically redirects to an identity provider and returns with an authorization result that the relying party validates according to the chosen protocol. The exact flow, redirect URI checks, state/nonce, PKCE use, token handling, and session establishment depend on the client type and protocol. An “SSO certificate” is not a universal browser credential format; use the provider’s protocol and validated library rather than inventing a ticket exchange.

## HTTPS, TLS, and MitM / HTTPS、TLS 与中间人攻击

HTTPS authenticates the server name and protects transport confidentiality and integrity when certificate validation and TLS configuration are correct. A TLS certificate binds a public key to an identity under the certificate-validation process; it does not mean all application data is safe or that the endpoint itself is trustworthy.

The old description “client encrypts a random session key with the server’s RSA public key” is not a general description of modern TLS. TLS 1.3 commonly negotiates ephemeral Diffie–Hellman key agreement (for example, ECDHE), authenticates the handshake with certificates and signatures, and derives symmetric traffic keys. PSK-based modes also exist. This supports forward secrecy with ephemeral key agreement and prevents a passive observer from deriving the traffic secret from a recorded exchange alone.

A MitM attacker can impersonate a server only if trust checks are defeated or a trusted endpoint/intermediary is compromised or misconfigured—for example, a fraudulent/untrusted certificate accepted by the client, compromised CA/key, malicious root certificate, or incorrect certificate validation. Keep TLS libraries and certificates configured correctly; never suppress certificate errors in production.

## Browser-Facing Security Threats / 浏览器安全风险

- **XSS:** attacker-controlled content executes in the site’s origin. Context-aware output encoding and safe DOM APIs are primary defenses; sanitize only when intentionally allowing HTML. Framework escaping helps for normal text interpolation but does not make unsafe HTML APIs, URLs, or every context safe. CSP is a useful additional control, not a substitute for correct output handling.
- **CSRF:** a browser is induced to send an authenticated request using ambient credentials such as cookies. Use appropriate `SameSite` cookies, anti-CSRF tokens or origin checks for state-changing requests, and avoid state changes on safe methods. CORS alone is not a CSRF defense.
- **Clickjacking:** a site is framed and obscured to trick user actions. Set `Content-Security-Policy: frame-ancestors ...` and, where needed for legacy clients, `X-Frame-Options`; JavaScript frame-busting is not a reliable primary defense.
- **SQL injection:** occurs when untrusted input changes query structure. Use parameterized queries and safe query APIs; validation is supplementary, not a replacement for parameterization.
- **DDoS:** exhausts network or application capacity. Mitigation is layered across infrastructure, edge controls, rate limits, capacity planning, and incident response; a front-end alone cannot stop it.

Security controls must be enforced by the server for each protected operation and resource. Client-side checks improve usability but cannot authorize access.

## WebSocket and HTTP / WebSocket 与 HTTP

A browser WebSocket begins with an HTTP opening handshake, then uses a persistent, full-duplex client-server channel. It is not peer-to-peer: the server may send a message at any time after the connection is established, but clients still need a server endpoint and network path. `ws://` is unencrypted; use `wss://` in production.

The browser WebSocket API does not perform a CORS preflight. The server should validate the handshake `Origin`, authenticate the connection, authorize each message/action as required, limit message sizes/rates, and close/revoke sessions deliberately. A WebSocket endpoint that accepts arbitrary origins with ambient cookies may be vulnerable to cross-site WebSocket hijacking.

A minimal `ws` broadcast can use the server's `wss.clients` collection instead of maintaining a second client registry; do not echo untrusted data without a protocol decision:

```js
import WebSocket, { WebSocketServer } from 'ws';

const wss = new WebSocketServer({ port: 3000 });
wss.on('error', error => console.error('WebSocket server error:', error));
wss.on('connection', (socket, request) => {
  socket.on('error', error => console.error('WebSocket client error:', error));
  if (request.headers.origin !== 'https://app.example.test') {
    socket.close(1008, 'Origin not allowed');
    return;
  }
  socket.on('message', (data, isBinary) => {
    // Authenticate/authorize the operation and validate data before use.
    for (const client of wss.clients) {
      if (client !== socket && client.readyState === WebSocket.OPEN) {
        client.send(data, { binary: isBinary });
      }
    }
  });
});
```

The `ws` server maintains `wss.clients` as its connected-client collection, so the example does not need a parallel hand-maintained set or close-removal handler. In production, validate origin during the HTTP `upgrade` before accepting the socket, and authenticate the user before or immediately after the handshake according to the application design. This illustrative snippet does not implement authentication, schema validation, rate limits, or graceful shutdown.

HTTP/1.1 keep-alive reuses a transport connection for multiple request/response exchanges; it does not let the server send a new response without a request. WebSocket changes the application protocol after its opening handshake, allowing either endpoint to send frames until the connection closes. HTTP/2 and HTTP/3 also reuse connections but use multiplexed streams and remain request/response protocols unless an extension or separate protocol changes that behavior.

## Resource Hints / 资源提示

Resource hints are browser guidance, not guaranteed network actions. Use them only when the likely benefit outweighs connection or bandwidth cost.

- `preload` starts fetching a resource needed soon by the current page, with an accurate `as` value and matching request attributes.
- `prefetch` suggests a low-priority resource that may be needed on a likely future navigation.
- `dns-prefetch` asks the browser to resolve a host in advance.
- `preconnect` may resolve DNS and establish a connection (including TLS for HTTPS) to an anticipated origin. Unnecessary preconnects consume resources and can disclose likely destinations early.
