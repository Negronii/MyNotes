# Front-End Project Design / 前端项目设计

These are reusable interview-design exercises, not descriptions of a particular employer or production system. Start by clarifying users, constraints, failure modes, and success measures; the sketches below make their assumptions explicit. For related fundamentals, see [browser performance](../../../frontend/performance/rendering-and-computation-optimization.md), [image lazy loading](../../../frontend/browser-apis/image-lazy-loading.md), [web security](../../../engineering-foundations/security/web-security-and-authentication.md), and [Agile and Scrum](../../../engineering-foundations/teamwork/agile-and-scrum.md).

设计时先确定可信的服务端业务状态、需要版本化保存的页面文档，以及只属于编辑会话的临时状态；分析事件则只在同意与字段 allowlist 下采集。以下 SDK 和低代码练习分别展开这些边界，不预设某个框架或渲染方案普遍更优。

## Design a Front-End Analytics SDK / 前端分析 SDK

A small analytics client can collect page views, explicitly selected product events, navigation timing, and client errors. Before collecting anything, define the product purpose, consent and opt-out behavior, data retention, sampling, and fields that must never leave the device. Do not put passwords, tokens, form contents, full query strings, or other sensitive values into telemetry. Keep the schema versioned and allowlist event properties rather than accepting arbitrary objects.

A practical design has four parts. Use the shared [browser error-handling guidance](../../../frontend/javascript/error-handling.md) when implementing global handlers; this exercise focuses on analytics collection and delivery boundaries.

1. **Collection:** expose `track(eventName, properties)` and router integration for page views; attach global error handlers only where useful. In a single-page app, subscribe to committed route changes and avoid duplicate initial events.
2. **Enrichment:** add a product/app identifier, schema version, timestamp, and a page identifier with sensitive query parameters removed. Navigation performance can use `PerformanceNavigationTiming`; error stacks and URLs need truncation/redaction.
3. **Delivery:** batch small events where appropriate. A same-origin endpoint avoids unnecessary CORS configuration. `navigator.sendBeacon()` is useful for small best-effort delivery when the page becomes hidden, but `true` means only that the browser queued the data; it gives no response callback or proof of server receipt. It does not bypass origin policy, privacy choices, authentication, payload limits, or server validation. A `fetch(..., { keepalive: true })` fallback has its own quota and lifecycle limits.
4. **Reliability and privacy:** the server validates the schema and size, rejects abusive input, deduplicates if retries are supported, and applies retention/access controls. Client timestamps and analytics events are untrusted input, not authorization evidence.

Illustrative same-origin implementation:

```js
const allowedEventValues = new Map([
  ['page_view', new Set(['home', 'article', 'pricing'])],
  ['action', new Set(['register', 'share'])],
]);

class AnalyticsSDK {
  constructor({ productId, endpoint = '/analytics', hasConsent }) {
    this.productId = productId;
    this.endpoint = endpoint;
    this.hasConsent = hasConsent;
  }

  track(eventName, value) {
    const allowedValues = allowedEventValues.get(eventName);
    if (!this.hasConsent() || !allowedValues?.has(value)) return false;
    const properties = eventName === 'page_view' ? { routeId: value } : { actionId: value };
    return this.#send(eventName, properties);
  }

  trackNavigation() {
    const navigation = performance.getEntriesByType('navigation')[0];
    const allowedTypes = new Set(['navigate', 'reload', 'back_forward']);
    if (!this.hasConsent() || !navigation || !allowedTypes.has(navigation.type) || navigation.loadEventEnd === 0) return false;
    return this.#send('navigation', {
      type: navigation.type,
      durationMs: Math.round(navigation.duration),
    });
  }

  #send(eventName, properties) {
    const body = new Blob([JSON.stringify({
      schemaVersion: 1,
      productId: this.productId,
      eventName,
      timestamp: Date.now(),
      properties,
    })], { type: 'application/json' });

    if (navigator.sendBeacon?.(this.endpoint, body)) return 'beacon-queued';

    void fetch(this.endpoint, {
      method: 'POST',
      body,
      credentials: 'same-origin',
      keepalive: true,
    }).catch(() => {}); // Best effort: there is no delivery guarantee here.
    return 'fallback-started';
  }
}
```

The example allowlists synthetic route/action identifiers instead of serializing arbitrary input. `NavigationTimingType` is limited to `navigate`, `reload`, and `back_forward`; prerender activation is a separate mechanism. Call `trackNavigation()` after the window's `load` event, because before it completes `loadEventEnd` and the derived duration can still be zero. A production SDK still needs a product-specific schema, bounded buffering, sampling, retry/deduplication policy, consent integration, and route lifecycle wiring. For performance metrics beyond navigation, select supported Performance Timeline entries and define how cross-origin timing restrictions affect the values. Do not treat `performance.timing` as the modern source; it is deprecated in favor of navigation timing entries.

## SPA or MPA? / 单页还是多页

SPA and MPA describe navigation and rendering approaches, not a quality ranking. The same UI framework can support client rendering, server rendering, static generation, or hybrid routes. Choose per page and user journey.

| Consideration | Questions to resolve |
| --- | --- |
| Interaction | Does the workflow need persistent client state and frequent in-place updates? How much client JavaScript is acceptable? |
| Content and discovery | Must content be available in initial HTML for crawlers, previews, or low-JavaScript clients? What rendering strategy and metadata are required? |
| Performance | Measure the real initial-load, navigation, interaction, and data costs on target devices and networks. A server-rendered page is not automatically fast; a SPA is not automatically slow. |
| Operations | Consider routing, caching, deployment, observability, accessibility, error recovery, and team familiarity across the whole lifecycle. |

A collaborative dashboard may favor persistent client state and route-level code splitting; a content-heavy site may favor pre-rendered pages. These are starting hypotheses, not fixed rules. Search indexing depends on the delivered content and crawler behavior; server rendering or static generation can help, but neither guarantees ranking or indexing.

## HTML5 Low-Code Editor: Data Model and Core Features / 低代码编辑器

A visual editor needs a component catalog, a document model, editing state, persistence/versioning, rendering, and—if simultaneous collaboration is required—a defined synchronization model.

### Document and Editing Model

Keep reusable component definitions separate from each page's instances. A component instance should have a stable ID, a registered type, validated properties, layout/style data, and an explicit parent/order relationship. Store the page schema version so document migrations can be applied when component definitions evolve. Represent sibling order explicitly rather than relying on object iteration order. Avoid storing executable source from an untrusted editor as a component property.

Selection, hover, and open inspector state are editor-session state; they need not be written into the published page document. Undo/redo can use reversible commands or a bounded operation history. Save a revision or checkpoint according to the product's recovery and audit requirements.

A minimal local React example keeps the selected ID separate from the page data and only renders known component types:

```jsx
import { useReducer } from 'react';

const page = {
  schemaVersion: 1,
  roots: ['heading', 'hero'],
  nodes: {
    heading: { id: 'heading', type: 'text', props: { text: 'Welcome' } },
    hero: { id: 'hero', type: 'image', props: { src: '/assets/hero.webp', alt: 'Mountain view' } },
  },
};

const componentRegistry = {
  text: ({ text }) => <span>{text}</span>,
  image: ({ src, alt }) => <img src={src} alt={alt} />,
};

function editorReducer(state, action) {
  if (action.type === 'select') return { ...state, selectedId: action.id };
  return state;
}

export function PageEditor() {
  const [state, dispatch] = useReducer(editorReducer, { selectedId: null });
  return (
    <main>
      {page.roots.map(id => {
        const node = page.nodes[id];
        const Component = componentRegistry[node.type];
        if (!Component) return null;
        return (
          <button key={node.id} type="button" aria-pressed={state.selectedId === node.id}
                  onClick={() => dispatch({ type: 'select', id: node.id })}>
            <Component {...node.props} />
          </button>
        );
      })}
    </main>
  );
}
```

This example renders a fixed local document; it is not a persistence format, a complete tree renderer, or a collaborative editor. A real renderer should validate component properties and asset URLs, handle nesting and layout, and keep editor controls separate from published output.

### Collaboration and Versioning

Choose synchronization only after establishing whether concurrent editing is a requirement. A WebSocket can transport updates but does not resolve conflicts. For a single-editor or low-conflict tool, optimistic saves with document revisions and conflict detection may be enough. For concurrent editing, define operations, ordering, conflict semantics, permissions, offline behavior, and recovery; OT or CRDTs are options with different costs, not automatic requirements. The server should validate operations and authorize edits to the project/document. Keep an auditable revision path if users need restore or review.

## User–Role–Permission (RBAC) / 用户—角色—权限

For a small content-management example, users receive roles and roles grant permissions. Authentication answers who is making a request; authorization checks whether that principal may perform this action on this resource in this context.

A relational schema can use:

```text
User(id, username, password_hash, ...)
Role(id, name, ...)
Permission(id, resource, action, ...)
UserRole(user_id, role_id)                 -- composite key
RolePermission(role_id, permission_id)     -- composite key
```

These join tables model many-to-many relationships and support constraints and indexes; arrays of role IDs in a user row make referential integrity and updates harder. Add tenant or organization scope to assignments when the product is multi-tenant. Role inheritance is optional; if used, define cycle handling and effective-permission calculation.

Example permissions might include `post:read`, `post:edit`, and `user:manage`. A regular editor and an administrator are policy examples, not a universal hierarchy. Enforce authorization on the server for every operation and object, deny by default, and verify ownership/tenant scope to prevent insecure direct-object references. UI hiding is only a usability hint.

Store passwords as salted hashes using a vetted adaptive password-hashing function such as Argon2id, with parameters tuned to the service—not reversible encryption or a fast general-purpose hash. A `password_hash` field contains the encoded algorithm and work parameters as supported by the library.

## Prize-Draw Page: Backend APIs and Invariants / 抽奖页面

A browser can request entry and display a result, but it cannot decide eligibility, select the prize, or decrement inventory. The backend owns those decisions and the authoritative record. Clarify whether entry is one-time or repeatable, how eligibility is determined, when a draw closes, how inventory is reserved, and how winners claim prizes.

A possible flow is:

1. `GET /draws/{drawId}` returns public rules, schedule, and currently visible status.
2. An authenticated user submits `POST /draws/{drawId}/entries` with a documented idempotency key. The server checks campaign state, account eligibility, and duplicate-entry rules.
3. In one transaction or equivalent atomic workflow, the service records the entry/result and reserves any limited prize so concurrent requests cannot over-allocate inventory. The draw algorithm and audit trail must meet the campaign's fairness and regulatory requirements.
4. `GET /draws/{drawId}/entries/{entryId}` returns the authoritative result and claim status. Do not expose another user's entry.
5. A winner submits `POST /prizes/{prizeId}/claims` with only the information required for delivery. The server validates the winner, protects personal data, and records fulfillment state.

Useful supporting APIs can include `GET /users/me/draw-history`, `GET /prizes/{id}`, and administrative campaign/prize management endpoints with stricter authorization. Statistics and share analytics are separate untrusted reporting events; they must not decide eligibility or prize outcomes.

The idempotency-key behavior is an API contract: define its scope, retention, replay response, and behavior when the first result is unknown to the client. A unique constraint for one entry per user/campaign and a transaction/locking strategy for inventory are common ways to enforce invariants; exact choices depend on the database and consistency requirements. Return explicit conflict or closed-campaign errors instead of asking the client to infer state from a failed request.

## Selecting a Technology Stack / 技术选型

Start with constraints and decision criteria, then compare candidates against them. A short prototype or migration spike is useful when the uncertain part is material; record the decision and revisit trigger in an Architecture Decision Record (ADR).

- **Product and delivery:** user workflows, rendering and discoverability, interaction complexity, accessibility, supported browsers/devices, deadlines, and expected change rate.
- **Team and ecosystem:** skills, hiring/support availability, component and testing ecosystem, documentation, upgrade path, and ability to transfer ownership.
- **Runtime and operations:** hosting/deployment model, build and CI needs, observability, security, performance targets, reliability, and integration constraints.
- **Lifecycle cost:** implementation, training, licenses, infrastructure, migration, maintenance, and eventual replacement—not only initial build speed.

React, Vue, and other frameworks do not have fixed “best” project categories. Compare the actual candidate versions, rendering modes, libraries, team experience, and operating model against the requirements. Include the option of keeping the existing stack when replacement risk exceeds the measurable benefit.

## HTML Image Lazy Loading / 图片懒加载

Prefer native lazy loading for below-the-fold images. It keeps a real resource URL in the markup while allowing the browser to defer the fetch until the image is near the viewport:

```html
<img src="/images/article-18.webp" loading="lazy"
     width="960" height="640" alt="A red bridge over a river">
```

Provide intrinsic dimensions or an aspect ratio to reserve layout space. Do not lazy-load an above-the-fold or likely Largest Contentful Paint image; load it normally and consider an appropriate fetch priority only after measurement. Browser heuristics decide how near the viewport is, so do not depend on a fixed distance.

If a custom observer is needed, `data-src` is only application data; it does not tell the browser which image to fetch. Assign the actual `src` when the image approaches the viewport, and load immediately when the observer API is unavailable:

```js
const images = document.querySelectorAll('img[data-src]');
const loadImage = image => {
  image.src = image.dataset.src;
  image.removeAttribute('data-src');
};

if (!('IntersectionObserver' in window)) {
  images.forEach(loadImage);
} else {
  const observer = new IntersectionObserver(entries => {
    for (const entry of entries) {
      if (!entry.isIntersecting) continue;
      loadImage(entry.target);
      observer.unobserve(entry.target);
    }
  });
  images.forEach(image => observer.observe(image));
}
```

This custom pattern needs a deliberate placeholder and a no-JavaScript fallback if the content must remain available without scripts. In most cases, native `loading="lazy"` is simpler.

## Agile Development / 敏捷开发

The Agile Manifesto values working software, collaboration, customer involvement, and adaptation while still recognizing the value of processes, tools, documentation, contracts, and plans. It does not prescribe one delivery framework or guarantee lower cost, faster delivery, or project success. Teams should use feedback, small increments, and retrospection to learn whether their process is working for their context.

## Scrum / Scrum 方法

The November 2020 Scrum Guide defines Scrum as a lightweight framework for generating value through adaptive solutions to complex problems. It specifies three accountabilities within one Scrum Team: Product Owner, Scrum Master, and Developers.

- **Product Owner:** accountable for maximizing product value and effective Product Backlog management.
- **Developers:** create a usable Increment, plan the Sprint, uphold the Definition of Done, and adapt their plan toward the Sprint Goal.
- **Scrum Master:** accountable for establishing Scrum as defined in the Guide and for the Scrum Team's effectiveness; serves the team and organization by coaching, enabling self-management, and helping remove impediments.

The Scrum Master is not defined as a project manager or as the team's sole owner of delivery. The Guide also defines events and artifacts; do not invent mandatory roles, estimate practices, or benefits beyond that framework. Whether Scrum fits a particular team is a separate decision.
