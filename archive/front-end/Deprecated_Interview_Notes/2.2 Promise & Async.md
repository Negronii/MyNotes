# JavaScript Promises and Async Iteration / JavaScript Promise 与异步迭代

**Core / 核心：** A Promise represents one eventual outcome; it does not start work or cancel it by itself. `Promise.all` and `Promise.race` combine outcomes, while `await` and `for await...of` determine how results are consumed. Promise 表示一个最终结果，本身不启动或取消工作；组合方法处理结果，`await` 与 `for await...of` 决定如何消费结果。

**Key terms / 关键词：** pending 待定 · fulfilled 已兑现 · rejected 已拒绝 · settled 已敲定 · thenable · Promise reaction job 反应任务 · async iterable 异步可迭代对象

## JavaScript Promises

### Definition and Basic Example
A **Promise** represents the eventual fulfillment or rejection of an operation. The executor passed to `new Promise` runs synchronously; the timer in this example schedules the later call to `resolve`.

```javascript
const promise = new Promise((resolve, reject) => {
  setTimeout(() => {
    resolve('Success!');
  }, 1000);
});

promise.then(value => {
  console.log(value); // Outputs: Success!
});
```

### States of a Promise
**Promise** objects can exist in one of three states:
- **Pending:** The initial state of a promise. The outcome is not yet known.
- **Fulfilled:** Indicates that the asynchronous operation completed successfully.
- **Rejected:** Indicates that the asynchronous operation failed.

Calling the resolving function settles the promise at most once. Resolving with another Promise or thenable adopts its eventual state, so “resolved” does not always mean “fulfilled now.” A synchronous throw from the executor rejects the new promise.

### Prototype Methods
#### Promise.prototype.then()
This method returns a new Promise. Its fulfillment and rejection callbacks, when callable, run after settlement; a returned value fulfills the next Promise, a returned thenable is adopted, and a thrown error rejects it.

```javascript
promise.then(result => {
  return result + ' and more!';
}).then(newResult => {
  console.log(newResult); // Outputs: Success! and more!
});
```

#### Promise.prototype.catch()
Used for rejection handling, this method is shorthand for `.then(undefined, rejectionHandler)`. It handles a rejection propagated through the chain; a handler's own thrown error becomes the rejection of the Promise returned by `catch`.

#### Promise.prototype.finally()
This method runs a cleanup callback after settlement and normally preserves the original value or rejection. If the callback throws or returns a rejected Promise, the Promise returned by `finally` rejects with that new failure.

```javascript
promise.finally(() => {
  console.log('Promise was settled.');
});
```

### Promise Static Methods
#### Promise.all()
Aggregates an iterable of values and Promises. It fulfills with results in input order after all fulfill, or rejects when an input rejects; it does not start the underlying operations or cancel the remaining ones. An empty iterable fulfills with `[]`.

```javascript
const promise1 = Promise.resolve(3);
const promise2 = 42;
const promise3 = new Promise((resolve, reject) => {
  setTimeout(resolve, 100, 'foo');
});

Promise.all([promise1, promise2, promise3]).then(values => {
  console.log(values); // Outputs: [3, 42, 'foo']
});
```

#### Promise.race()
Settles with the first input to settle, whether that input fulfills or rejects. It does not cancel the other operations; an empty iterable leaves the returned Promise pending.

```javascript
const promiseOne = new Promise((resolve, reject) => {
  setTimeout(resolve, 500, 'one');
});
const promiseTwo = new Promise((resolve, reject) => {
  setTimeout(reject, 100, 'two');
});

Promise.race([promiseOne, promiseTwo]).then(value => {
  console.log(value);
}).catch(reason => {
  console.log(reason); // Outputs: two
});
```

#### Promise.resolve() and Promise.reject()
- **Promise.resolve(value)** returns a Promise that adopts a Promise or thenable value, or fulfills with a non-thenable value.
- **Promise.reject(reason)** returns a promise that is rejected with the given reason.

## Understanding Promise Execution Order
### Basic Promise Execution Flow
```javascript
Promise.resolve().then(() => {
  console.log(0);
  return Promise.resolve(4);
}).then((res) => {
  console.log(res);
});

Promise.resolve().then(() => {
  console.log(1);
}).then(() => {
  console.log(2);
}).then(() => {
  console.log(3);
}).then(() => {
  console.log(5);
}).then(() => {
  console.log(6);
});
```

**Expected Output:** `0 1 2 3 4 5 6`.

**Key Points:**   
- Reactions for an already-settled Promise still run asynchronously as Promise jobs; they do not run inline with the call to `.then()`.
- Returning a Promise or thenable makes the next Promise adopt its outcome. The job steps that do this can change interleaving with other chains, as these concrete examples show.
- The language does not promise fairness between Promise chains or timers. Host scheduling details are covered in the [event-loop note](../../../frontend/runtime/event-loop.md).

### Interleaved Execution with Multiple Promises
```javascript
Promise.resolve().then(() => {
  console.log(0);
}).then(() => {
  console.log(1);
}).then(() => {
  console.log(2);
});

Promise.resolve().then(() => {
  console.log(3);
}).then(() => {
  console.log(4);
}).then(() => {
  console.log(5);
});

Promise.resolve().then(() => {
  console.log(6);
}).then(() => {
  console.log(7);
}).then(() => {
  console.log(8);
});
```

**Expected Output:** `0 3 6 1 4 7 2 5 8`.

**Explanation:**  
- Reactions from the three chains interleave as each handler queues the next reaction. This is the output for this exact program, not a general fairness guarantee.

### Delayed Execution with Nested Promises
```javascript
Promise.resolve().then(() => {
  console.log(0);
  return Promise.resolve(1);
}).then(() => {
  console.log(2);
}).then(() => {
  console.log(3);
});

Promise.resolve().then(() => {
  console.log(4);
  return Promise.resolve(5);
}).then(() => {
  console.log(6);
}).then(() => {
  console.log(7);
});
```
**Output:** `0 4 2 6 3 7`.

**Detailed Insight:**
- Returning an already-fulfilled Promise still requires the chained Promise to adopt its state through Promise jobs. The surrounding chains can therefore run between the two handlers; the exact result above belongs to this complete snippet.

### Simulating Promise Execution Order
```javascript
Promise.resolve().then(() => {
  // First beat
  const p = Promise.resolve(1);
  Promise.resolve().then(() => {
    // Second beat
    p.then(res => {
      console.log(res);
    }).then(() => {
      console.log(2);
    });
  });
});
```

Expected log order for this snippet: `1`, then `2`. The example schedules a reaction from inside another reaction and makes the dependency explicit.

## What is and when to use `for await...of`
`for await...of` consumes an async iterable, or adapts a synchronous iterable, awaiting each yielded value before the next loop body. It is useful for ordered consumption; it does not make already-started operations run sequentially.
```ts
async function processPromises() {
    function createPromise(val: number): Promise<number> {
        return new Promise((resolve) => {
            setTimeout(() => {
                resolve(val);
            }, 1000);
        });
    }

    const p1 = createPromise(100);
    const p2 = createPromise(200);
    const p3 = createPromise(300);
    const list = [p1, p2, p3];

    // These timers start while the array is created. The loop consumes their results in input order.
    for await (let res of list) {
        console.log(res);
    }

    // Performing asynchronous operations in sequence
    const arr = [100, 200, 300];
    for (let num of arr) {
        const res = await createPromise(num); // Ensure this code is inside an async function
        console.log(res);
    }
}

processPromises();
```

If the first Promise is slow, later Promises may already have settled while the loop waits for it; their values are still consumed in input order. `Promise.all(list)` instead fulfills once all inputs fulfill and passes one array in input order to its handler.

For sequential work, create and await each operation inside the loop, as the second loop above does. Promises have no built-in cancellation; cancellation must be supported by the underlying operation, for example through `AbortSignal`.
