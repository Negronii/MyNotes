## Why `0.1 + 0.2 !== 0.3` / 为什么浮点数相加不精确

JavaScript `Number` uses IEEE 754 binary64 values. Most decimal fractions, including 0.1 and 0.2, do not have an exact finite binary representation, so the stored result may differ slightly from the decimal value one expects.

```js
const sum = 0.1 + 0.2;
console.log(sum); // 0.30000000000000004
console.log(sum === 0.3); // false
```

Do not compare approximate results with one universal epsilon. Choose tolerance from the scale and error budget of the calculation; for money, integer minor units or a decimal arithmetic library is usually clearer.

## Browser Components / 浏览器组成

A browser is a multi-component application, and its process model differs by product and version. A useful conceptual map includes:

- **User interface:** address bar, navigation controls, tabs, and browser menus.
- **Networking:** resolves and fetches resources, reuses connections, and applies security and cache rules.
- **Rendering engine:** parses markup and styles, computes layout, paints, and coordinates compositing.
- **JavaScript engine:** parses and executes ECMAScript, often using interpreters and optimizing compilers.
- **Storage and platform integration:** cookies, Web Storage, IndexedDB, cache, media, fonts, and operating-system services.
- **Process and isolation model:** browser, renderer, GPU, and utility processes may be separated for responsiveness and security; the details are implementation-specific.

This is a teaching map, not a fixed list of one process per component. Historical browser plugins such as Flash are not a normal modern extension model; current browsers rely on built-in web APIs and managed extensions.

## Front-End Storage Options / 前端存储方式

| API | Lifetime and scope | Useful properties | Limits and cautions |
|---|---|---|---|
| `localStorage` | Origin-scoped and normally persists across browser restarts until removed or evicted. | Simple string key/value preferences. | Synchronous; quota and eviction are browser-controlled. Avoid large data and secrets accessible to page script. |
| `sessionStorage` | Origin-scoped to a top-level browsing context's page session. | Small state that should survive reloads in that session. | Synchronous; lifetime details follow browser session behavior. It is not a security boundary. |
| Cookies | Sent automatically when a request matches cookie scope and policy. | Server-readable session identifiers and other small state. | Small browser-dependent limits; automatic transmission has privacy and CSRF implications. Configure `Secure`, `HttpOnly`, and `SameSite` as appropriate. |

Storage quotas are not a fixed “5 MB per domain” guarantee. The user agent and storage API determine available capacity and eviction behavior. Use IndexedDB or Cache Storage for larger structured/offline data, and handle quota failures. Cookies are scoped by attributes such as host/domain and path; they do not follow the same-origin policy exactly. A `HttpOnly` cookie is unavailable to page JavaScript, but it still accompanies matching requests according to browser policy.

**Choosing / 如何选择:** use Web Storage for small client-side state; use cookies when the server needs browser-managed request state; use IndexedDB or Cache Storage for larger structured or offline data. Never treat client storage as authorization: the server must validate every privileged request.

## JavaScript Values and Memory / JavaScript 值与内存

ECMAScript defines observable value behavior, not a required stack-versus-heap layout. Engines choose and optimize representations, so “primitives live on the stack and objects live on the heap” is not a language guarantee.

Primitive values such as numbers, strings, booleans, `null`, `undefined`, symbols, and bigints are immutable values. Objects, arrays, and functions have identity; assigning an object to another variable copies the reference to that same object, not a deep copy of its properties.

```js
const first = { count: 1 };
const second = first;
second.count++;
console.log(first.count); // 2: both variables refer to the same object
```

A call stack is a useful model for nested function calls and their execution context; recursion depth is limited by the host/runtime. Dynamic objects and garbage collection are managed by the engine. For JavaScript type semantics, see [JavaScript Types](../../../frontend/javascript/javascript-types.md).

## Garbage Collection / 垃圾回收

JavaScript engines manage memory automatically. A common reachability model is that objects still reachable from live program state must remain available, while unreachable objects may be reclaimed. Collection timing and algorithms are implementation details; cycles can be reclaimed when the whole cycle is unreachable.

V8 has used generational collection with marking, sweeping, compaction, and concurrent or parallel work. That is an engine-specific implementation, not a promise about every JavaScript engine or a fixed algorithm for all V8 versions.

## Closures and Memory / 闭包与内存

A closure retains access to bindings from its lexical environment. A closure is not inherently a leak; a leak-like retention occurs when a long-lived reference keeps data or resources reachable after the application no longer needs them. Engines may optimize environments, so do not infer exact memory use from source-level scope alone.

Clean up resources whose lifetime is longer than a function call: event listeners, timers, subscriptions, observers, workers, and retained DOM references. In React, effect cleanup is one way to release a subscription when its owner no longer needs it.

## Investigating Memory Growth / 排查内存增长

A steadily rising heap graph is a clue, not proof by itself: allocation bursts, delayed collection, caching, and retained objects can look different. Reproduce the same interaction, take comparable heap snapshots, inspect retaining paths, and check whether detached DOM nodes or listeners remain reachable. Chrome DevTools provides heap snapshots and allocation tools; verify behavior in the browser version being investigated.

## WeakMap and WeakSet / 弱引用集合

`WeakMap` associates values with object keys without making those keys strongly reachable through the map; `WeakSet` tracks object membership under the same weak-key idea. Entries are intentionally not enumerable, because garbage collection can remove keys at implementation-chosen times. They are useful for object metadata or caches that should follow an object's lifetime, but they are not deterministic eviction policies.

## From URL to Pixels / 从输入 URL 到页面呈现

A navigation is a useful sequence to reason about, but browsers may reuse cached data, DNS results, preconnected sockets, service-worker responses, or existing HTTP/2 and HTTP/3 connections. Fetching and parsing can overlap; there is no universal one-request-at-a-time timeline.

1. **Navigate and fetch:** the browser interprets the URL, applies navigation and cache rules, resolves a host if needed, establishes or reuses a connection, and sends an HTTP request. HTTPS authenticates the server and protects the connection using the negotiated TLS/QUIC security protocol; the old “encrypt a random key with the server's public key” description is not a general modern TLS handshake.
2. **Parse the response:** HTML bytes can be parsed as they arrive. The parser builds the DOM and discovers stylesheets, scripts, images, and other resources. External classic scripts may block parsing; `defer`, `async`, and module scripts have different execution rules.
3. **Style and layout:** the browser computes styles for applicable DOM nodes and calculates geometry. Stylesheets can delay rendering because their rules affect layout and paint.
4. **Paint and composite:** the browser paints visual output and may composite layers. These stages and their scheduling are implementation details and can repeat as resources load or scripts change the document.

JavaScript can run during parsing or later according to script type and scheduling. A DOM change may require style recalculation, layout, paint, or compositing, depending on what changed. Image dimensions can reserve layout space and reduce shifts, but they do not guarantee a particular rendering sequence.

## Style, Layout, Paint, and Compositing / 样式、布局、绘制与合成

A visual update may require one or more browser rendering stages:

- **Style recalculation:** determine the computed styles affected by a change.
- **Layout (often called reflow):** calculate geometry and positions when layout-affecting inputs change.
- **Paint (often called repaint):** draw visual content into paint records or layers.
- **Compositing:** combine layers for display; some animations may update here without rerunning layout or paint, depending on browser and page state.

A layout change usually leads to paint, while a paint-only change need not trigger layout. The scope and cost depend on the document, changed property, browser, and rendering path; avoid treating a fixed property list or “whole page reflow” as a performance law.

Useful practices are to measure first, batch DOM reads before writes to avoid forced synchronous layout, reserve image dimensions when known, and use `requestAnimationFrame` to schedule visual updates. A block formatting context can affect layout relationships but is not a universal optimization. CSS animations and `transform`/`opacity` may be compositor-friendly, but verify with browser performance tools instead of assuming every animation is cheap.

## `defer` and `async` on Scripts / Script 的 `defer` 与 `async`

For external classic scripts, both attributes allow fetching in parallel with HTML parsing, but they change execution timing:

| Script form | Fetch | Execution |
|---|---|---|
| Classic, no attribute | Parsing pauses while fetching, then pauses again to execute. | In document order at the script position. |
| Classic `defer` | Fetches in parallel. | After parsing completes, in document order, before `DOMContentLoaded`. |
| Classic `async` | Fetches in parallel. | As soon as the script is ready; execution order relative to other async scripts is not guaranteed. |
| Module script | Module graph fetches in parallel. | Deferred by default; `defer` has no effect. `async` makes the module execute when its graph is ready. |

These rules describe parser-inserted scripts. Dynamic script insertion and other loading mechanisms have their own rules. Use `defer` when classic scripts depend on document order; use `async` for independent scripts whose execution order does not matter.

## `HTMLCollection` and `NodeList` / HTMLCollection 與 NodeList

`HTMLCollection` contains element nodes and is live. `NodeList` can contain different node types, and its liveness depends on the API that returned it. For example, `childNodes` returns a live NodeList, while `querySelectorAll()` returns a static NodeList.

For this markup:

```html
<p id="p1"><em>hello</em> hello <b>bold</b><!-- comment --></p>
```

- `p.children` returns the element children (`em` and `b`) as an `HTMLCollection`.
- `p.childNodes` includes element, text, and comment nodes in a live `NodeList`.
- `p.tagName` is an element-specific name; `nodeName` is available on all nodes. Name casing depends on the document type (HTML versus XML).

Because a live collection reflects DOM changes while it is being read, copy it to an array when the algorithm needs a stable snapshot.

## Browser and Node.js Event Loops / 浏览器与 Node.js 事件循环

JavaScript execution is run-to-completion within a job, but hosts schedule tasks and asynchronous callbacks around it. “Macrotask” is informal; the HTML Standard describes task queues and microtask checkpoints.

### Browser / 浏览器

After a task finishes, the browser performs a microtask checkpoint, which drains queued Promise reactions and `queueMicrotask()` callbacks. Rendering may happen after that checkpoint when the browser has an opportunity; there is no promise that it paints between every task. A long task or an endlessly replenished microtask queue can delay input and rendering.

```js
console.log('Start');
setTimeout(() => console.log('Timeout'), 0);
new Promise(resolve => {
  console.log('Promise executor');
  resolve();
}).then(() => console.log('Promise reaction'));
console.log('End');
```

Typical browser output:

```text
Start
Promise executor
End
Promise reaction
Timeout
```

The Promise executor runs synchronously; its reaction is a microtask. The timer callback becomes eligible later, but a zero delay is not an exact execution time.

### Node.js / Node.js

Node.js uses libuv event-loop phases for timers, pending callbacks, poll, check, and close callbacks, with internal idle/prepare work. Phase details and timer behavior depend on Node.js/libuv versions. Node.js 20+ uses libuv 1.45+, which changed when timers run relative to the poll phase; do not present one universal ordering for timers and `setImmediate()`.

Promise reactions and `queueMicrotask()` share the microtask queue. `process.nextTick()` uses a separate queue and is drained before that queue after a CommonJS operation. At the top level of an ES module, evaluation itself runs through the microtask queue, so the observed order differs:

```js
Promise.resolve().then(() => console.log('promise'));
queueMicrotask(() => console.log('microtask'));
process.nextTick(() => console.log('nextTick'));
```

The Node.js v26.10 documentation checked on 2026-10-15 gives this top-level order; the local runtime check used Node.js v26.11.1:

- CommonJS (`.cjs`): `nextTick`, `promise`, `microtask`.
- ES module (`.mjs`): `promise`, `microtask`, `nextTick`.

Treat the output as scoped to module format and Node version. Node.js marks `process.nextTick()` as legacy and recommends `queueMicrotask()` for most deferral. Recursively filling the next-tick or microtask queue can starve I/O. JavaScript execution is not the same as all Node work being single-threaded: the runtime and operating system also perform I/O and background work.

## Processes, Threads, and Node.js / 进程、线程与 Node.js

A process has its own address space and operating-system resources. Threads execute within a process and may share memory; the exact model depends on the runtime. Browser Web Workers and Node.js `worker_threads` run JavaScript outside the current main thread, while Node.js child processes provide stronger process isolation and communicate through IPC or other channels.

Use asynchronous I/O for I/O-bound work. Consider `worker_threads` for CPU-heavy JavaScript when sharing a process is suitable; use child processes when isolation or a separate process lifecycle matters. Spawning one process per request is usually too expensive for a production hot path; use a bounded worker pool or a managed service when the workload warrants it.

### Node.js `fork()` / Node.js 子进程

`child_process.fork()` starts another Node.js process with an IPC channel. This CommonJS teaching example sends one computation request and waits for the reply; it omits production concerns such as timeouts, request validation, process reuse, and shutdown.

```js
// server.cjs
const http = require('node:http');
const { fork } = require('node:child_process');
const { join } = require('node:path');

const server = http.createServer((req, res) => {
  if (req.url !== '/compute') {
    res.writeHead(404).end();
    return;
  }

  const child = fork(join(__dirname, 'compute.cjs'));
  child.once('message', result => {
    res.setHeader('Content-Type', 'application/json');
    res.end(JSON.stringify(result));
  });
  child.once('error', () => res.writeHead(500).end('Worker failed'));
  child.send({ type: 'sum', limit: 10_000 });
});

server.listen(3000);
```

```js
// compute.cjs
process.once('message', request => {
  if (request?.type !== 'sum' || !Number.isSafeInteger(request.limit) || request.limit < 0) {
    process.send?.({ error: 'invalid request' }, () => process.disconnect());
    return;
  }
  let sum = 0;
  for (let i = 0; i < request.limit; i++) sum += i;
  process.send?.({ sum }, () => process.disconnect());
});
```

### Node.js `cluster` / Node.js 集群进程

`cluster` starts child processes that can share a server port. The example shows explicit worker creation; it does not guarantee even traffic distribution, automatic recovery, graceful draining, or high availability. Those require configuration and operational monitoring.

```js
const cluster = require('node:cluster');
const http = require('node:http');
const { availableParallelism } = require('node:os');

if (cluster.isPrimary) {
  for (let i = 0; i < availableParallelism(); i++) cluster.fork();
  cluster.on('exit', worker => {
    console.error(`worker ${worker.process.pid} exited`);
  });
} else {
  http.createServer((req, res) => res.end('hello')).listen(8000);
}
```

`cluster.isMaster` is a deprecated alias; use `cluster.isPrimary` in current Node.js. For a single process with worker threads, see the [Node.js worker threads documentation](https://nodejs.org/api/worker_threads.html).

## JavaScript Bridge to a Native App / WebView 与原生应用的 JSBridge

A WebView does not automatically gain arbitrary device privileges. A native bridge deliberately exposes a small allowlist of native operations to page code. The message transport and API shape depend on the iOS/Android/WebView version and host app; examples from one platform are not a universal Web API.

A bridge contract should define readiness, supported methods and versions, request IDs, argument validation, asynchronous replies, timeouts, and error shapes. The native side must authorize each operation and validate every payload; hiding an API name in JavaScript is not access control. Avoid passing secrets in a custom URL, where they can enter logs or history.

A synthetic promise-based contract might look like this:

```js
// Pseudocode: the host app must implement and secure this bridge contract.
const version = await bridge.call('device.getVersion', {});
```

A custom URL scheme or hidden iframe can sometimes trigger a native navigation handler, but it does not guarantee a readable response or bypass browser origin, authentication, or privacy rules. Prefer a documented message-handler or WebMessagePort interface provided by the target WebView when available.

## HTTP Caching / HTTP 缓存

HTTP caches use freshness and validators together. `Cache-Control` controls freshness and revalidation policy; `Expires` is an older absolute freshness time and is ignored when a valid `max-age` takes precedence. `ETag` and `Last-Modified` can let a client revalidate a stale response; an unchanged representation can receive `304 Not Modified`.

For content-addressed assets whose URL changes when bytes change, a long freshness lifetime can work well:

```http
Cache-Control: public, max-age=31536000, immutable
```

For a stable URL whose content may change, require revalidation and provide a validator:

```http
Cache-Control: no-cache
ETag: "content-version-7"
```

`no-cache` permits storage but requires validation before reuse; `no-store` is the directive that asks caches not to store the response. Choose shared-cache directives only when the representation is safe for every cache that may receive it. See [HTTP Protocols and WebSockets](../../../engineering-foundations/networking/http-protocols-and-websockets.md) and RFC 9111 for the full cache model.

## Updating Hybrid-App Templates / 更新混合应用模板

A WebView app may download HTML, JavaScript, and CSS bundles independently of the native app. The update policy should be explicit rather than assuming every app checks at launch or every few minutes.

A practical flow is:

1. Publish an immutable, versioned bundle and record compatible native/API versions.
2. Fetch a small manifest according to a freshness or user-triggered policy; do not make a slow network check block app startup.
3. Download in the background, verify integrity and origin, and reject an incompatible or partial bundle.
4. Switch versions atomically only after validation; retain the last known-good bundle for rollback.
5. Keep authenticated data and privileged actions behind the native/server boundary. Loading files through `file://` is not by itself a security isolation guarantee.

The manifest format, signature, storage location, and rollback mechanism depend on the app's threat model and WebView platform.

## DOM Event Propagation and React / DOM 事件传播与 React

DOM events may travel through capture, target, and bubble phases. A listener registered with capture enabled observes the event on the way down; a bubbling event then travels back through ancestors. `stopPropagation()` changes propagation, while `preventDefault()` cancels a cancelable default action; they do different things.

React exposes event props such as `onClick` and `onClickCapture`. React 17 moved most delegated event listeners from `document` to the React root container, and some events use different handling. Do not describe all React events as identical cross-browser wrappers or claim that every handler is attached to `document`; use the React version's event documentation for details.

## Multi-Tab Communication / 多标签页通信

Choose a channel based on whether tabs need transient messages, shared computation, persistent state, or a server connection. Same-origin rules and browser storage partitioning apply to browser-local channels.

### `BroadcastChannel` / 广播频道

For transient messages between same-origin browsing contexts, `BroadcastChannel` is often the simplest API. Messages are structured-cloned; the sender does not receive its own message. Validate message shape and close the channel when the page no longer needs it.

```js
const channel = new BroadcastChannel('app-sync');
channel.addEventListener('message', event => {
  if (event.data?.type === 'selection-changed' && typeof event.data.id === 'string') {
    console.log('selection changed:', event.data.id);
  }
});
channel.postMessage({ type: 'selection-changed', id: 'item-7' });
// On teardown: channel.close();
```

### `localStorage` / 本地存储事件

The `storage` event fires in other documents using the same storage area; it does not fire in the document that performed the write. It is useful for small state changes, not as a high-throughput messaging queue.

```js
window.addEventListener('storage', event => {
  if (event.key === 'changeInfo' && event.newValue !== null) {
    console.log(JSON.parse(event.newValue));
  }
});

// In another same-origin tab:
localStorage.setItem('changeInfo', JSON.stringify({ id: 100, name: 'Item 100' }));
```

### `SharedWorker` / 共享 Worker

A `SharedWorker` can coordinate same-origin contexts that connect to the same worker. It runs outside the page's main thread, but browser support and lifecycle behavior should be checked for the target browsers. Use a worker when shared logic or state justifies its added lifecycle and failure handling.

```js
// In each tab
const worker = new SharedWorker('worker.js');
const port = worker.port;
port.start();
port.onmessage = event => console.log(event.data);
port.postMessage({ type: 'hello' });
window.addEventListener('pagehide', () => {
  port.postMessage({ type: 'disconnect' });
}, { once: true });
```

A `pagehide` disconnect is cooperative and best effort. The browser `MessagePort` interface has no standard `onclose` event for detecting a peer that disappears without sending it; if crash cleanup matters, define a separate liveness or lease policy. `messageerror` reports deserialization failure, not peer closure.

```js
// worker.js
const ports = new Set();
onconnect = event => {
  const port = event.ports[0];
  ports.add(port);
  port.start();
  port.onmessage = message => {
    if (message.data?.type === 'disconnect') {
      ports.delete(port);
      port.close();
      return;
    }
    for (const recipient of ports) {
      if (recipient !== port) recipient.postMessage(message.data);
    }
  };
  port.onmessageerror = () => {
    // This example retires a port after a message cannot be deserialized.
    ports.delete(port);
    port.close();
  };
};
```

### WebSocket / WebSocket

WebSocket is a client-server full-duplex connection, not a browser-local tab channel. It can carry server-originated messages after the handshake; the server must authenticate clients and validate the handshake `Origin` against its policy. The browser API does not use CORS preflight, but that does not make a WebSocket endpoint safe to accept from every origin.

### `postMessage` Between a Page and an Iframe / 页面与 iframe 通信

`postMessage` is designed for cross-origin Window messaging; it does not disable CORS or grant access to the other page's DOM. Use an exact `targetOrigin`, then check both `event.origin` and `event.source` and validate the message data before acting on it.

```js
const expectedOrigin = 'https://child.example';
const frame = document.querySelector('iframe');

frame.contentWindow.postMessage({ type: 'get-status' }, expectedOrigin);
window.addEventListener('message', event => {
  if (event.origin !== expectedOrigin || event.source !== frame.contentWindow) return;
  if (event.data?.type !== 'status') return;
  console.log('status:', event.data.value);
});
```

The child should apply the same checks to messages from its expected parent. Avoid `'*'` for messages containing private data or actions.

## Rendering 100,000 Data Entries / 渲染十万条数据

First clarify whether the user needs all records, a count, a search, or a viewport of results. For large datasets, prefer server-side filtering, sorting, and cursor or page-based pagination so the client does not download data it cannot use. A separate middleware layer is justified only when it provides a needed boundary, aggregation, or integration—not merely because the data set is large.

Receiving and transforming 100,000 small records may be feasible on some devices; creating a DOM node for every record can be expensive in memory, style, layout, and accessibility navigation. Measure on target devices and use the smallest technique that meets the interaction:

- **Pagination or incremental loading:** fetch only the next needed slice and expose clear loading, error, and continuation states. Cursor pagination is often more stable than offset pagination when records change, but depends on the API and ordering requirements.
- **Virtualized list/grid:** keep only visible rows and a small overscan window in the DOM while maintaining scroll geometry. Account for variable-height items, keyboard navigation, focus, screen readers, and scroll restoration; virtualization is not automatically more accessible or faster for every list.
- **Chunked processing or a Web Worker:** move expensive client-side transforms away from the main thread when computation—not DOM count—is the bottleneck. A worker does not make a huge rendered DOM cheap.
- **Aggregation:** if users need a trend, count, or summary, return a server-computed aggregate rather than transferring every raw record.

Avoid promising a fixed item-count threshold: row complexity, device memory, data shape, and interaction all matter. Profile network transfer, scripting, rendering, and memory separately.

## Mobile Tap Responsiveness / 移动端点击响应

The historical 300 ms tap delay was used by some mobile browsers to distinguish a possible double-tap zoom. It is not a universal modern-browser behavior. A mobile-optimized viewport (`width=device-width`, with a suitable initial scale) removes the delay in many current browsers while preserving pinch zoom. Test the target browser/device matrix rather than adding FastClick by default.

For a specific control where double-tap zoom should be disabled while ordinary panning and pinch zoom remain available, `touch-action: manipulation` can express that intent:

```css
button, .single-tap-control {
  touch-action: manipulation;
}
```

Do not globally disable zoom with `user-scalable=no` or `maximum-scale=1`; that harms accessibility. The right behavior depends on the element and browser, and pointer-event behavior should be tested with assistive technology and touch input.
