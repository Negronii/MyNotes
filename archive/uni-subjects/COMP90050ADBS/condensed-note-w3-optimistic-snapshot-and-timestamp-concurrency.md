# 乐观验证、快照隔离与时间戳排序怎样处理并发冲突？

一个账户约束要求 `A+B≥0`，初始 `A=B=100`。两笔事务各自读取两行、判断扣款后仍满足约束，然后分别改写不同的账户行。若二者都能提交，最终值会是多少？这组运行会在 SI 小节继续使用；OCC 改用 `A/B→C` 的版本重验例，时间戳排序则用单项 `A` 展示过时读写。三组输入分别突出跨行约束、读写集验证和操作时间戳。

## 乐观验证怎样把冲突检查推迟到提交前？

optimistic concurrency control（乐观并发控制）适合冲突相对少、读和计算耗时较长的工作：事务先读取并计算，暂不长时间持锁；准备提交时再验证自己使用的数据是否仍有效。抽象流程是“读取—计算—验证—提交写入”。若验证失败，就放弃本次尝试并基于新状态重算。

下面沿用课程的 A、B 输入与 C 输出，但把每个观察到的值与同一次读取所得版本配对，而不只比较值：`A=(8,v4)`、`B=(5,v7)`、`C=(12,v3)`。事务用 A、B 计算 `C_new=A+B`；C 是写入目标，它的旧值/版本 `12@v3` 用于确认计算期间目标没被改写。此处是一个带版本标签的教学协议：事务先无锁读取、计算；每次读取都从当时的已提交版本同时取得值和对应版本标签，不能将未提交值与版本号配在一起。

准备提交时，对读集减去写集后的纯读项（本例 A、B）取得共享锁 `S(A),S(B)`，对写集（本例 C）取得排他锁 `X(C)`，随后重查版本是否仍分别为 `v4`、`v7`、`v3`。持有这些锁直到写入和提交完成，才确保验证通过后数据不能被另一遵守协议的写者抢先改变。

所有会修改这些数据的写者都必须取得冲突的 `X` 锁，并与值在同一提交中更新版本；否则本协议无法发现它们的写入。任一版本变化，就不写结果、释放锁并从头重读重算。短锁缩短了计算期间的锁占用，但验证仍可能等待；资源顺序需统一以避免验证阶段死锁。Kung 与 Robinson 的原始 OCC 是非锁式验证思路，下面这组加短锁的步骤是课程示意，并非他们原算法的实现。

> [!example] 一次验证失败后怎样重算
> 第一次输入配对为 `A=(8,v4)`、`B=(5,v7)`、写入目标 `C=(12,v3)`，所以候选结果是 `C_new=13`。计算期间另一个事务把 `B` 改为 `6@v8`。提交尝试取得 `S(A),S(B),X(C)` 后发现 B 的令牌已变；本次不发布 C，C 仍是 `12@v3`，然后释放锁并中止本次尝试。重启后重读三项：`A=(8,v4)`、`B=(6,v8)`、`C=(12,v3)`，重算得到 14，再取得同一组锁并复验三个版本；都匹配后写 `C=14@v4` 并提交。一次验证取得这组锁并通过后，相关锁一直持有到提交，其他合规写者不能在验证与发布之间改动这些输入或目标。

若只比较值而不比较版本，`B` 可能从 5 改成 6 又改回 5；当前值虽然相等，版本仍能揭示中间发生过修改；若契约只依赖当前数值，值恢复后不一定有错，但不能据值相等证明从未改动。这类“变了又回来”现象称为 ABA 问题。版本号、写序列号或其他足以证明未被修改的令牌，可以识别它。上面的方案是讲解读集验证的教学实现；其锁授予、令牌比较、结果写入和提交必须处于同一受保护的事务边界。版本令牌须由所有相关写者维护，且锁管理器必须确实拦住未遵守读写协议的并发修改。否则只比较令牌并不能形成原子验证，也不能自动获得可串行化的通用算法。

## 快照隔离为什么会出现写偏斜？

经典定义的 snapshot isolation（快照隔离，SI）让事务从固定的已提交快照读取数据，并能看到自己的写入；遵循 first-committer-wins（先提交者获胜）时，并发事务改写同一数据项不能都提交。产品可以在提交前更早检测：例如 PostgreSQL 18 的 `REPEATABLE READ` 中，若 `UPDATE` 遇到快照建立后被别的事务更新的行，而对方仍在运行，本事务会等待；若对方已经提交（包括等待后提交），本事务报 `40001` 并回滚；若对方回滚，则可继续尝试更新原有行。此检查针对写集重叠，不能替代所有跨行约束的串行化检查。

回到开头的约束。假设两笔事务都从同一个快照 `S0` 读取 `A=100、B=100`，各自检查扣款后总额仍 `≥0`，再分别把其中一行扣 200；没有数据库约束、范围锁或串行化检查来保护这个跨行条件：

| 步骤 | T1 | T2 | 数据库已提交状态 |
| --- | --- | --- | --- |
| 0 |  |  | A=100，B=100，合计 200 |
| 1 | 从 S0 读 A=100、B=100；计算 A'=-100，合计 0，约束通过 |  | A=100，B=100 |
| 2 |  | 从 S0 读 A=100、B=100；计算 B'=-100，合计 0，约束通过 | A=100，B=100 |
| 3 | 写 A=-100 并提交 |  | A=-100，B=100，合计 0 |
| 4 |  | 写 B=-100 并提交；T1 没有写 B，故没有同一行写冲突 | A=-100，B=-100，合计 -200 |

两笔事务分别写 `A` 与 `B`，所以常见的同一行“先提交者获胜”检查不会发现冲突；但两笔事务读了对方将要改写的数据。冲突图里，`T1` 读 `B` 先于 `T2` 写 `B`，有 `T1 → T2`；`T2` 读 `A` 先于 `T1` 写 `A`，有 `T2 → T1`。形成环，说明该成功结果无法按串行顺序实现。

如果先串行执行 T1，状态会变为 `A=-100、B=100`；T2 随后扣减 B 会得到合计 -200，必须拒绝。先执行 T2 再执行 T1 同理。因此二者不可能在每笔事务都检查最新状态的串行执行中同时成功。这种不同写集共同破坏跨行规则的现象叫 write skew（写偏斜），是 serialization anomaly（可串行化异常）。

课程还用同一组账户对比了单版本锁式执行：`X(A)` 表示对 A 加排他锁，`S(B)` 表示对 B 加共享锁；T1 申请 `X(A)`、`S(B)`，T2 按 `S(A)`、`X(B)` 的同一 A→B 资源顺序申请。先取得 A 锁的一方阻止另一方继续，而不是让两边各占一行；获胜者在覆盖 A、B 两行的锁保护下读取、检查和写入，并把这些锁持到提交。若 T1 先执行，它把 A 写成 -100 后提交；T2 此时才获准读 A，读到当前 `A=-100、B=100`，扣减 B 后合计 -200，于是拒绝。T2 先执行时结果对称。正确性来自锁覆盖所有被检查的数据、持锁跨过检查和写入直到提交，并要求所有相关写者使用相同协议；相同资源顺序有助于避免死锁，但本身不是一致性保证。这个示意属于单版本阻塞模型，不表示 PostgreSQL `REPEATABLE READ` 的固定快照事务等待后会读到新值。

PostgreSQL 18 的 `REPEATABLE READ` 使用事务级固定快照并可允许这类异常；其 `SERIALIZABLE` 级别通过 Serializable Snapshot Isolation（可串行化快照隔离，SSI）跟踪危险的读写依赖，必要时中止一个事务，应用应从事务开始重试并重新执行约束检查。不要把课程抽象的“快照 + 写集校验”伪代码等同于所有产品隔离级别的完整实现。

## 基本时间戳排序怎样拒绝过时读写？

timestamp ordering（时间戳排序）给每笔事务分配唯一、单调递增的逻辑时间戳 `TS(T)`，使最终冲突次序符合时间戳给出的串行顺序。时间戳通常是系统逻辑计数，不必是墙上时钟。对每个数据项 `X`，算法记住：`read_TS(X)` 是成功读取 `X` 的事务中最大的时间戳；`write_TS(X)` 是成功写入 `X` 的事务中最大的时间戳。初始都为 0。

读写许可规则可以直接从“不能让较旧事务排在较新读写之后”推出来：

- `T` 请求读 `X`：若 `TS(T) < write_TS(X)`，说明 `X` 已被时间戳更晚的事务写过；若现在让 `T` 读这个值，就违反规定顺序，因此中止并重启 `T`。否则允许读取，并令 `read_TS(X)=max(read_TS(X),TS(T))`。
- `T` 请求写 `X`：若 `TS(T) < read_TS(X)`，说明有时间戳更晚的事务曾读过 X；它读到的值未必是 `write_TS(X)` 所指的当前版本，但按时间戳顺序，这次旧写本应先于那次读，因此中止。若 `TS(T) < write_TS(X)`，更晚事务已经写过，基本算法同样中止。否则允许写入并更新 `write_TS(X)`。

> [!example] 复算一次过时读取
> `T1` 的 `TS=5`，`T2` 的 `TS=10`。起初 `read_TS(A)=write_TS(A)=0`。T1 读取 A 后，`read_TS(A)=5`。T2 写 A 时 `10≥5` 且 `10≥0`，所以可写并令 `write_TS(A)=10`。之后 T1 再读 A，因 `5<10` 必须中止；否则这个旧事务会观察到一个比自己时间戳更新的写入。

基本时间戳排序在“时间戳顺序与事务操作冲突”的检查处直接拒绝该操作并中止事务，不等这个冲突解决。重试必须开启新事务并分配更大的时间戳，再从头读取和检查；沿用被拒事务的旧时间戳会重复遇到同一拒绝。基本版本若让未提交写入对后续操作可见，可能造成脏读、脏写或级联回滚；仅有冲突可串行化保证不等于可恢复。strict timestamp ordering（严格时间戳排序）会让其他事务等到相关写事务提交或中止后，才读取或覆盖该项，从而避免读取未提交写入造成的级联回滚。

例如 T1 的 `TS=5`，当前 `read_TS(A)=0, write_TS(A)=10`。基本协议对 T1 的盲写先检查 `5<0` 为假，再检查 `5<10` 为真，因此中止。Thomas write rule（Thomas 写规则）在第一项没触发拒绝、而第二项发现旧写时，忽略这次过时写，不改数据也不改 `write_TS(A)`。若改为 `read_TS(A)=7, write_TS(A)=10`，必须先检查的 `5<7` 已成立，说明较新的事务曾读过 A；它不一定读到 TS=10 写入的当前版本，但按时间戳顺序，TS=5 的旧写应先于 TS=7 的读，这次写入会违背该顺序，所以基本协议与 Thomas 变体都中止，不能跳过。比较使用严格小于，所以 TS 相等不会触发拒绝，事务也可按时间戳规则读取自己的写入。Thomas 规则允许某些视图可串行化而非冲突可串行化的历史：与某个串行历史保持相同的读取来源（包括初始值）及最终写入者，不要求每对冲突操作的次序都相同，因而不能直接沿用基本时间戳排序的冲突图判据。Robert H. Thomas 的原论文讨论的是多副本数据库中的多数共识更新；这里借用其忽略过时更新的规则来对照课程的单项时间戳算法，不能把两种协议整体视为同一个实现。

## time-domain versioning（时间域版本模型）与时间戳排序是同一件事吗？

不是。课程还保留了按时间区间保存对象版本的表示。区间左闭右开，`t2` 属于 `V2`，`t3` 属于 `V3`；`[t3,∞)` 表示当前版本尚无结束时点：

```text
<o, <V1,[t1,t2)>, <V2,[t2,t3)>, <V3,[t3,∞)>>
```

它表示对象 `o` 在不同区间对应不同版本，是一个历史版本模型；它不是上节中按事务时间戳拒绝 `read/write` 操作的算法。两者都出现“时间”和“版本”，但一个讲可查询的数据历史，另一个讲并发事务冲突顺序。

课程例子里，T1 在同一个快照中计算员工平均工资；T2 把低于 40,000 的工资提高 10%。若 T1 选取的快照早于 T2 提交，它可在整个聚合期间继续从该快照可见的旧工资版本计算，并在 T2 提交后完成只读事务，前提是所需旧版本仍可读取。多版本并发控制（MVCC）读者读取旧版本不意味着自动中止；若某个特定时间戳验证协议要求拒绝旧版本，则需另行说明该协议的规则。它是课程中的历史表示例，不说明任一产品都支持任意时间区间查询。
